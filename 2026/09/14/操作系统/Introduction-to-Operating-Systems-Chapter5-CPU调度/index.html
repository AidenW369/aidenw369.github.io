二、基本概念

1. CPU–I/O 突发周期（CPU–I/O Burst Cycle）

进程的执行过程本质上是 CPU 突发（CPU burst）与 I/O 突发（I/O burst）交替循环：

进程最终以一次 CPU burst 结束（执行系统终止调用）。

多道程序设计（multiprogramming）的意义：当一个进程在等待 I/O 时，把 CPU 交给另一个进程，从而获得最大的 CPU 利用率。

2. CPU 突发时间的分布

实测统计呈现指数/超指数分布的形状：

  • 短突发数量极多（曲线在左侧出现高峰）
  • 长突发数量很少（右侧长长的低尾巴）

📌 这个分布是本章最重要的"事实前提"：它解释了为什么 SJF 之类"优待短作业"的算法能显著降低平均等待时间，也解释了 I/O 密集型进程（短突发）和 CPU 密集型进程（长突发）需要被区别对待。

3. CPU 调度程序（CPU Scheduler / 短程调度器）

  • 职责：从**就绪队列（ready queue）**中挑选一个进程，把 CPU 核心分配给它。
  • 就绪队列不一定是 FIFO，可以是优先队列、树、无序链表等。

调度发生的四个时机：

编号 状态转换 触发原因举例 是否有选择余地
1 运行 → 等待 发起 I/O、wait() 等子进程 ❌ 无（必须换）
2 运行 → 就绪 时钟中断、被抢占 ✅ 有
3 等待 → 就绪 I/O 完成 ✅ 有
4 终止 进程结束 ❌ 无（必须换）

4. 抢占式 vs 非抢占式

非抢占式（Nonpreemptive / 协作式） 抢占式（Preemptive）
触发时机 仅 1 和 4 还包括 2 和 3
特点 进程一旦获得 CPU，就一直占用，直到自己终止或主动进入等待状态 可以被强行剥夺 CPU
响应性 差，长进程会拖垮交互性 好
实现开销 小 需要定时器、更多上下文切换

现代操作系统（Windows、macOS、Linux、UNIX）几乎全部使用抢占式调度。

5. 抢占式调度与竞争条件（Race Condition）

抢占带来的代价：当多个进程共享数据时，可能产生竞争条件。

典型场景：

  1. 进程 A 正在更新共享数据，写到一半；
  2. A 被抢占，进程 B 被调度运行；
  3. B 读取该数据 → 读到不一致的中间状态。

补充：这个问题还会波及内核数据结构（如就绪队列、打开文件表）。解决办法是第 6 章的进程同步（互斥锁、信号量等）。另外，中断处理期间也必须保证关键代码段不被打断。

6. 分派程序（Dispatcher）

调度器负责"选谁"，分派程序负责"怎么交接"。其工作包括：

  1. 切换上下文（保存旧进程 PCB，恢复新进程 PCB）
  2. 切换到用户模式
  3. 跳转到用户程序中合适的位置，重新启动该程序

分派延迟（dispatch latency）：停止一个进程并启动另一个进程所需的时间。它是纯开销，必须尽可能小（可用 Linux 的 vmstat、/proc/[pid]/status 查看上下文切换次数）。

三、调度准则（Scheduling Criteria）

准则 含义 优化方向
CPU 利用率 让 CPU 尽可能忙 最大化（实际 40%~90%）
吞吐量 Throughput 单位时间内完成的进程数 最大化
周转时间 Turnaround 从提交到完成的总时间 = 等待 + 执行 + I/O 最小化
等待时间 Waiting 在就绪队列中等待的总时长 最小化
响应时间 Response 从提交请求到产生第一次响应的时间 最小化

关键区分：

  • 周转时间关注"整件事什么时候做完"→ 批处理系统关心。
  • 响应时间关注"多久有动静"→ 交互式/分时系统关心。
  • 调度算法通常优化平均值，但有时更应优化最坏情况或方差（响应时间可预测比平均值小更重要）。

四、调度算法

1. 先来先服务 FCFS（First-Come, First-Served）

非抢占，用 FIFO 队列实现，最简单。

例：P1=24, P2=3, P3=3

情形 A：到达顺序 P1, P2, P3

等待时间：P1=0, P2=24, P3=27 → 平均 = (0+24+27)/3 = 17

情形 B：到达顺序 P2, P3, P1

等待时间：P1=6, P2=0, P3=3 → 平均 = (6+0+3)/3 = 3

结论与问题：

  • 平均等待时间严重依赖到达顺序，很不稳定。
  • 护航效应（Convoy effect）：短进程排在长进程后面被迫干等。
  • 典型恶化场景：一个 CPU 密集型进程 + 多个 I/O 密集型进程。CPU 型进程长期霸占 CPU，I/O 型进程全部堵在就绪队列；等它终于让出 CPU 后，I/O 型进程飞快跑完又全部涌向 I/O 设备，导致 CPU 和 I/O 设备双双出现利用率低谷。
  • 不适合分时系统（无抢占，无法保证响应时间）。

2. 最短作业优先 SJF（Shortest-Job-First）

更准确的名称是 SNBF（Shortest-Next-CPU-Burst-First）：比较的是下一次 CPU 突发的长度，不是进程总长度。

例：P1=6, P2=8, P3=7, P4=3

等待时间：P4=0, P1=3, P3=9, P2=16 → 平均 = (3+16+9+0)/4 = 7
（对比：同一组数据用 FCFS 平均等待为 10.25）

性质：

  • ✅ SJF 是最优的——对给定的一组进程，它给出最小的平均等待时间
    • 直觉证明：把短作业挪到长作业前面，短作业减少的等待 > 长作业增加的等待。
  • ❌ 难以实现：无法预知下一次 CPU 突发的长度。
  • ❌ 可能导致长作业饥饿（starvation）。

如何获得突发长度？

  • 直接问用户（批处理系统中让用户申报时限，但用户会谎报）
  • 估计——基于"下一次突发应该和前几次相似"的假设
指数平均（Exponential Averaging）

设：

  • tn = 第 n 次 CPU 突发的实际长度
  • τn+1 = 对下一次突发的预测值
  • α ， 0≤α

τn+1=αtn+(1−α)τn

通常取 α = 1/2（历史与近期各占一半权重）。

特例分析：

α 取值 公式退化为 含义
α = 0 τn+1=τn 最近的历史完全不算，预测值恒定
α = 1 τn+1=tn 只看上一次实际突发，历史全部丢弃

展开式：

tn+(1−α)αtn−1+⋯+(1−α)jαtn−j+⋯+(1−α)n+1τ0

由于 α 和 (1−α) 都 ≤ 1，越久远的项权重越小（呈指数衰减），这正是"指数平均"名称的由来。

预测曲线示例（教材图）：

实际 ti 6 4 6 4 13 13 13 …
预测 τi 10 8 6 6 5 9 11 12

验证（α=1/2）：τ₂ = 0.5×6 + 0.5×10 = 8 ✓；τ₃ = 0.5×4 + 0.5×8 = 6 ✓
可见预测值平滑地追随实际值，但对突变（4 → 13）存在滞后，需要几个周期才能跟上。

3. 最短剩余时间优先 SRTF（Shortest-Remaining-Time-First）

SJF 的抢占版本。核心规则：

每当有新进程进入就绪队列，就重新执行一次 SJF 决策；若新进程的突发时间 < 当前运行进程的剩余时间，则抢占之。

例（引入到达时间与抢占）：

进程 到达时间 突发时间
P1 0 8
P2 1 4
P3 2 9
P4 3 5

逐步推演：

  • t=0：只有 P1，运行。
  • t=1：P2 到达（4）＜ P1 剩余（7）→ 抢占，P2 运行。
  • t=2：P3 到达（9）＞ P2 剩余（3）→ 不抢占。
  • t=3：P4 到达（5）＞ P2 剩余（2）→ 不抢占。
  • t=5：P2 结束。就绪者剩余：P1=7, P3=9, P4=5 → 选 P4。
  • t=10：P4 结束。P1=7 < P3=9 → 选 P1。
  • t=17：P1 结束 → P3 运行至 26。

等待时间 = 完成时间 − 到达时间 − 突发时间：

进程 计算 等待时间
P1 17 − 0 − 8 9
P2 5 − 1 − 4 0
P3 26 − 2 − 9 15
P4 10 − 3 − 5 2

平均等待时间 = [(10−1)+(1−1)+(17−2)+(5−3)]/4 = 26/4 = 6.5

思考题：SRTF 比 SJF 更"最优"吗？

是的——在允许进程陆续到达的情形下，SRTF 给出的平均等待时间不劣于非抢占 SJF（同一组数据用非抢占 SJF 计算为 7.75）。但代价是更多的上下文切换开销，而这个开销在理论分析中通常被忽略。SJF 的"最优性"严格来说只在"所有进程同时到达"的前提下成立。

4. 轮转调度 RR（Round Robin）

专为分时系统设计，是 FCFS + 抢占。

规则：

  • 每个进程获得一小段 CPU 时间，称为时间片/时间量子（time quantum, q），通常 10–100 ms。
  • 时间片用完后，进程被抢占，插入就绪队列尾部。
  • 通过定时器中断在每个时间片结束时触发调度。

性能保证：
若就绪队列中有 n 个进程，时间片为 q，则：

  • 每个进程获得约 1/n 的 CPU 时间，每次最多连续使用 q；
  • 任何进程的等待时间不超过 (n−1)q ← 这是 RR 最重要的性质：响应时间有上界。

时间片大小的权衡：

q 的取值 退化/后果
q → ∞（很大） 退化为 FCFS
q 很小 接近"处理器共享"，但上下文切换过于频繁，开销占比过高

⚠️ q 必须远大于上下文切换时间（经验法则：80% 的 CPU 突发应短于时间片）。
例：若上下文切换耗时 10 μs，q = 100 ms，则开销仅约 0.01%；若 q = 1 ms，开销升至约 1%。

补充例：P1=24, P2=3, P3=3，q = 4

等待时间：P1 = 10−4 = 6，P2 = 4，P3 = 7 → 平均 ≈ 5.66

RR 的特点：

  • 平均周转时间通常比 SJF 长，但响应时间更好——这正是交互系统需要的。
  • 无饥饿，公平性好。
  • 经验规律：如果80% 的 CPU 突发能在一个时间片内完成，平均周转时间会明显改善。

五、算法对比总结

算法 抢占 平均等待时间 响应时间 饥饿 实现难度 适用场景
FCFS 否 差（受顺序影响大） 差 无 极简单 批处理
SJF 否 最优（同时到达） 一般 长作业可能饥饿 需预测 批处理（长程调度）
SRTF 是 更优（有到达时间时） 较好 长作业易饥饿 需预测+抢占 理论基准
RR 是 较差 好（有上界） 无 简单 分时/交互系统

六、易错点与考点提醒

  1. 等待时间 vs 周转时间
    • 周转时间 = 完成时间 − 到达时间
    • 等待时间 = 周转时间 − 突发时间（无 I/O 时）
    • 画完 Gantt 图后用这两个公式核对，比数格子可靠。
  2. SJF 比较的是"下一次 CPU 突发"，不是进程总运行时间。
  3. 抢占时机：SRTF 只在新进程到达或当前进程结束时重新决策，不是每个时钟滴答都比较。
  4. RR 中新到达进程与被抢占进程的入队顺序：教材默认新到达进程先入队，被时间片用完的进程后入队——不同题目可能约定不同，做题前先确认。
  5. 指数平均的 α：α 越大 → 越看重近期；α 越小 → 越平滑、越迟钝。
  6. 护航效应是 FCFS 的专有名词，考试常考其定义与产生条件。

八、优先级调度（Priority Scheduling）

1. 基本规则

  • 每个进程关联一个优先级数字（整数）。
  • CPU 分配给优先级最高的进程。
  • ⚠️ 约定：数字越小，优先级越高（Unix 传统；但不同教材/系统约定相反，做题前务必确认）。
  • 有抢占式和非抢占式两个版本。

2. 与 SJF 的关系

SJF 是优先级调度的特例：其优先级 = 预测的下次 CPU 突发时间的倒数（突发越短 → 优先级越高）。

优先级的来源：

  • 内部：时间限制、内存需求、打开文件数、I/O 突发与 CPU 突发的比值
  • 外部：进程重要性、付费金额、部门、政治因素

3. 示例（非抢占）

进程 突发时间 优先级
P1 10 3
P2 1 1（最高）
P3 2 4
P4 1 5（最低）
P5 5 2

执行顺序：P2 → P5 → P1 → P3 → P4

等待时间：P2=0, P5=1, P1=6, P3=16, P4=18
平均等待时间 = (0+1+6+16+18)/5 = 41/5 = 8.2

4. 核心问题与解法

问题 饥饿 / 无限阻塞（Starvation / Indefinite Blocking）
描述 低优先级进程可能永远得不到执行——只要系统中不断有高优先级进程到来
传闻 1973 年 MIT 关闭 IBM 7094 时，发现一个 1967 年提交的低优先级作业还没运行
解法 老化（Aging）：随着等待时间增长，逐步提高进程的优先级

例：每等待 15 分钟，优先级数值减 1（提高一级）。一个优先级 127 的进程最多等 32 小时就能升到优先级 0。

规则：运行优先级最高的进程；优先级相同的进程之间用 RR 轮转。

十、多级队列（Multilevel Queue）

1. 动机

上面的"优先级 + RR"若用单一队列，每次调度都要遍历查找最高优先级进程 O(n)。改进：按优先级拆成多个独立队列。

2. 结构

调度方法：优先调度最高优先级非空队列中的进程；该队列为空才向下看。

3. 按进程类型分层（更常见的形式）

4. 调度器的定义参数（考点：4 个）

  1. 队列的数量
  2. 每个队列各自的调度算法（如前台用 RR、后台用 FCFS）
  3. 进程进入系统时被放入哪个队列的判定方法
  4. 队列之间的调度方法

队列间调度的两种方式：

  • 固定优先级抢占：高优先级队列非空时，低队列一律不运行 → 简单，但可能饥饿。
  • 时间片分配：如前台队列占 80% CPU（内部 RR），后台占 20%（内部 FCFS）。

5. 缺点

进程一旦被分配到某个队列，就永久固定在该队列中——缺乏灵活性（一个交互进程若被误判为批处理，将永远慢）。开销低，但不够灵活。

十一、多级反馈队列（Multilevel Feedback Queue, MLFQ）

1. 核心改进

进程可以在不同队列之间移动。

这就实现了"根据实际行为动态分类"：

  • CPU 密集型进程（突发长）→ 自动下沉到低优先级队列
  • I/O 密集型 / 交互式进程（突发短）→ 自动留在高优先级队列
  • 等待过久的进程 → 被上调（这正是 aging 的一种实现）

2. 调度器的定义参数（考点：5 个）

  1. 队列的数量
  2. 每个队列的调度算法
  3. 何时将进程升级（upgrade / promote） 的方法
  4. 何时将进程降级（demote） 的方法
  5. 进程进入系统时放入哪个队列的方法

3. 经典示例（三级队列）

队列 算法
Q0 RR，时间片 8 ms
Q1 RR，时间片 16 ms
Q2 FCFS

调度流程：

  1. 新进程进入 Q0，按 RR 服务。
  2. 获得 CPU 后运行 8 ms；若未完成 → 降级到 Q1。
  3. 在 Q1 再按 RR 获得 16 ms；若仍未完成 → 被抢占并降级到 Q2。
  4. 在 Q2 按 FCFS 运行，仅在 Q0、Q1 都为空时才被调度。

💡 设计思想的精妙之处：

  • 短交互任务（如键盘响应）在 Q0 内就能完成 → 响应极快（近似 SJF 的效果，却无需预知突发长度）。
  • 长计算任务逐级下沉 → 获得更长的时间片，减少切换开销，同时不干扰交互任务。
  • MLFQ 是最通用也最复杂的调度算法，是现代 OS（如早期 Windows、Solaris）的原型。

十二、线程调度（Thread Scheduling）

1. 关键区分

在支持线程的系统上，被调度的是内核级线程，而不是进程。

用户级线程本身不能直接被内核调度，必须映射到内核线程（LWP, Lightweight Process）上。

2. 两种竞争范围（Contention Scope）

PCS（进程竞争范围） SCS（系统竞争范围）
全称 Process-Contention Scope System-Contention Scope
适用模型 多对一、多对多 一对一（Windows、Linux）
调度者 线程库 内核
竞争范围 竞争发生在同一进程内部的线程之间 竞争发生在系统中所有线程之间
决定依据 通常由程序员设置的优先级决定 由内核调度算法决定
结果 线程库把用户级线程调度到可用的 LWP 上 内核线程被调度到可用 CPU 上

记忆：PCS 是"内部选拔赛"（选出代表去占用 LWP），SCS 是"全国总决赛"（所有线程抢 CPU）。

十四、多处理器调度（引入）

当有多个 CPU 可用时，CPU 调度变得复杂得多——不再只是"选哪个进程"，还要决定"放到哪个 CPU 上"。

"多处理器"可能指以下任一架构：

十六、多处理器调度：SMP 与就绪队列组织

1. 对称多处理（SMP）

SMP（Symmetric Multiprocessing）：每个处理器都是"自调度的"（self-scheduling）。

即：不存在一个"主控 CPU"统一发号施令，每个处理器各自运行调度程序，从就绪队列中挑选线程来执行。这是现代系统的标准做法。

📌 补充对照：非对称多处理（AMP） 是让一个主处理器负责所有调度决策、I/O 和其他系统活动，其余处理器只执行用户代码。优点是简单（只有一个核访问系统数据结构，无需同步），缺点是主处理器成为性能瓶颈。现已基本被 SMP 取代。

2. 就绪队列的两种组织方式

(a) 共享队列 (b) 每核私有队列
结构 所有线程放在一个公共就绪队列 每个处理器有自己的私有队列
负载均衡 天然均衡（谁空闲谁来取） 可能不均衡，需要额外的负载均衡机制
竞争问题 严重：多个 CPU 同时访问同一队列，需要加锁 → 成为瓶颈；还可能两个 CPU 选中同一线程，或线程丢失 无竞争，无锁开销
缓存亲和性 差（线程每次可能落到不同核） 好（线程倾向留在同一核）
实际采用 较少 ✅ 绝大多数现代 SMP 系统（Linux、Windows、Solaris）

💡 权衡本质：(b) 用"可能不均衡"换取"无锁 + 高缓存命中"，再通过负载均衡算法补上短板。

十七、多核处理器（Multicore Processors）

1. 发展趋势

把多个处理器核心放在同一块物理芯片上。

优势：

  • 更快（核间通信走片上互连，远快于跨芯片总线）
  • 功耗更低（共享缓存、更短的信号路径）

2. 内存停顿（Memory Stall）——多线程核的动机

处理器访问内存时，常常要等待数据从内存取回（cache miss、内存访问速度远慢于 CPU）。这段等待就是 memory stall（内存停顿）。

解决思路：给每个核配多个硬件线程——当一个线程发生内存停顿时，立刻切换到另一个线程执行，用别的线程的 C 填补这个线程的 M。

十八、多线程多核系统（Multithreaded Multicore System）

1. 双硬件线程的交错执行

两个线程交错（interleave）：thread0 停顿时 thread1 计算，反之亦然，物理核心的利用率大幅提升。

注意：这不增加实际计算能力（C 的总量没变），只是填补空隙，因此加速比通常在 1.2~1.3 倍，而非 2 倍。

2. 芯片多线程 CMT（Chip-Multithreading）

CMT 为每个核分配多个硬件线程。Intel 称之为超线程（hyperthreading），学名 SMT（同步多线程）。

通式：逻辑 CPU 数 = 核数 × 每核硬件线程数。

3. 两级调度（Two Levels of Scheduling）

级别 决策者 决策内容
Level 1 操作系统 选择哪个软件线程在哪个逻辑 CPU 上运行（即本章学的 RR、优先级、MLFQ 等算法）
Level 2 每个物理核（硬件） 决定哪个硬件线程真正占用物理核心。常用策略：轮转，或基于"紧迫度事件（urgency）"的动态优先级

💡 两级不必知道彼此：OS 层可以用任何调度算法；硬件层的切换开销极小（寄存器组是复制的，无需保存恢复）。但OS 若能感知处理器拓扑会调度得更好——例如两个计算密集线程应分到不同物理核，而不是同一个核的两个硬件线程。

十九、负载均衡（Load Balancing）

1. 为什么需要

在 SMP 中，必须让所有 CPU 都保持有活干，否则效率浪费。负载均衡试图让工作负载均匀分布在所有处理器上。

注意：负载均衡只对"每核私有队列"结构才有意义；共享队列结构天然均衡（CPU 空闲就来取）。

2. 两种迁移方式（考点）

方式 触发者 机制
推迁移（Push migration） 周期性任务 定期检查每个处理器的负载，发现某 CPU 过载时，把任务推到负载较轻的 CPU 上
拉迁移（Pull migration） 空闲处理器 空闲的处理器主动从繁忙处理器的队列中拉取一个等待任务过来

二者并不互斥，常并行实现。例如 Linux CFS 和 FreeBSD 的 ULE 调度器都同时使用推、拉两种方式。

3. "均衡"的两种定义

  • 每个队列中的线程数量大致相等；
  • 各处理器上优先级的总和大致相等（更合理，考虑了任务轻重）。

二十、处理器亲和性（Processor Affinity）

1. 概念来源：缓存

当一个线程在某个处理器上运行过后，该处理器的缓存中就保存了这个线程访问过的内存内容（“缓存已被暖热”）。我们称该线程对这个处理器有亲和性（affinity）。

若把线程迁移到另一个处理器：

  1. 原处理器的缓存内容必须作废（invalidate）；
  2. 新处理器的缓存必须重新填充（repopulate）；
  3. 代价非常高昂。

2. ⚠️ 与负载均衡的根本矛盾

负载均衡会破坏处理器亲和性：为了均衡负载而迁移线程，该线程就丢失了原处理器缓存中的全部内容。

这是多处理器调度中最经典的取舍（trade-off）：

现实中的调度器必须在两者之间取得平衡——只有当不均衡足够严重、收益超过缓存失效代价时，才执行迁移。

3. 两种亲和性

类型 含义
软亲和性（Soft affinity） 操作系统尽量让线程保持在同一处理器上，但不做保证——线程仍可能因负载均衡被迁走。这是大多数系统的默认行为
硬亲和性（Hard affinity） 允许进程指定一组它可以运行的处理器，OS 必须遵守

补充：Linux 提供 sched_setaffinity() 系统调用（及命令 taskset）实现硬亲和性；Windows 有 SetThreadAffinityMask()。实时任务、高性能计算常用硬亲和性来避免迁移抖动。

二十一、NUMA 与 CPU 调度

1. NUMA 架构

NUMA = Non-Uniform Memory Access（非一致内存访问）

  • 每个 CPU（或 CPU 组）有自己的本地内存，访问快（fast access）；
  • 访问其他 CPU 的内存要经过互连总线，慢（slow access）。

2. NUMA 感知调度

如果操作系统是 NUMA 感知的（NUMA-aware），它会把内存分配在离线程运行的 CPU 最近的位置。

即 CPU 调度器与内存分配器必须协同工作：

  • 线程在哪个 CPU 上运行 → 它的内存就分配在那个 CPU 的本地内存；
  • 更进一步，调度器应尽量不要把线程迁移到"远离其内存"的 CPU。

💡 NUMA 使亲和性问题升级：原先迁移只损失缓存（可重建），在 NUMA 上迁移还会让所有内存访问永久变慢（除非同时迁移页面）。因此 NUMA 系统上的负载均衡必须更保守。

二十二、实时 CPU 调度（Real-Time CPU Scheduling）

1. 两类实时系统（核心区分）

软实时（Soft real-time） 硬实时（Hard real-time）
保证 关键实时任务拥有最高优先级，但不保证何时被调度 任务必须在其截止期限（deadline）前被服务完成
违约后果 服务质量下降（如视频卡顿） 系统失败（等同于没有完成）
举例 多媒体播放、在线游戏 汽车刹车系统、飞控、工业控制、心脏起搏器

📌 常见误解澄清：实时 ≠ 快，而是 可预测（predictable）。硬实时系统宁可慢但确定，也不要平均快而偶尔超时。

2. 事件延迟（Event Latency）

事件延迟 = 从事件发生到事件被服务所经过的时间。

影响实时性能的两种延迟：

延迟 定义
中断延迟（Interrupt latency） 从中断到达 CPU 到开始执行中断服务例程（ISR） 的时间
分派延迟（Dispatch latency） 调度程序把当前进程移出 CPU 并切换到另一个进程所需的时间

二者都必须有界且尽量小，硬实时系统通常要求微秒级。

二十三、中断延迟（Interrupt Latency）详解

构成（三段）：

  1. 完成当前指令 / 内核临界区：若内核正在更新内核数据结构，可能关中断，必须等它开放中断；
  2. 判定中断类型：确定是哪个设备、跳转到哪个处理程序；
  3. 保存当前任务状态（上下文切换）。

⚠️ 实时系统的设计原则：必须最小化内核中禁止中断的时间。长时间关中断是硬实时的大敌。

二十四、分派延迟（Dispatch Latency）详解

冲突阶段（Conflict Phase）——分派延迟中最耗时的部分

分派延迟主要由冲突阶段和分派阶段组成，其中冲突阶段包含两个工作：

  1. 抢占任何在内核态运行的进程（Preemption of any process running in kernel mode）
  2. 低优先级进程释放高优先级进程所需的资源（Release by low-priority process of resources needed by high-priority processes）

分派阶段（dispatch phase）：真正把高优先级实时进程调度上 CPU。

💡 补充：为什么冲突阶段是关键

  • 第 1 项 要求内核必须是可抢占的（preemptive kernel）。传统非抢占内核中，一个系统调用可能运行很久而无法被打断，导致实时任务无限期等待。因此实时 OS 必须提供抢占点或完全可抢占内核。

  • 第 2 项 正是优先级反转（priority inversion）

    问题：高优先级进程 H 需要的锁被低优先级进程 L 持有，而 L 又被中等优先级进程 M 抢占，结果 H 被 M 间接阻塞。

    • 解法：优先级继承协议（priority-inheritance protocol）——让持有资源的 L 临时继承 H 的高优先级，使其尽快跑完并释放资源。

  • 著名案例：1997 年 NASA "火星探路者号"探测器的系统反复重启，根因就是优先级反转。

二十五、基于优先级的实时调度（Priority-based Scheduling）

1. 实时调度的两个层次要求

二十六、速率单调调度（Rate Monotonic Scheduling, RMS）

1. 规则

优先级按周期的倒数（即速率）分配：

  • 周期越短 → 速率越高 → 优先级越高
  • 周期越长 → 优先级越低

采用静态优先级 + 抢占式策略：优先级一旦分配就不再改变（static priority）。

直觉：周期短的任务"来得频繁、deadline 紧"，理应优先。

2. 成功示例

参数：P1: p₁ = 50, t₁ = 20；P2: p₂ = 100, t₂ = 35
→ P1 周期更短，P1 优先级高于 P2。

CPU 利用率：U = 20/50 + 35/100 = 0.40 + 0.35 = 0.75

Gantt 图：

推演要点：

  • t=0：P1、P2 同时到达，P1 优先 → P1 运行 0~20（完成，deadline 50 ✓）
  • t=20：P2 运行 20~50，做了 30 个单位（还差 5）
  • t=50：P1 的新周期到来，抢占 P2 → P1 运行 50~70
  • t=70：P2 恢复，跑完剩余 5 个单位，70~75（deadline 100 ✓）
  • 之后模式在 100 处重复。

✅ 所有任务均满足截止期限。

3. 错过截止期限的示例（RMS 的局限）

参数：P1: p₁ = 50, t₁ = 25；P2: p₂ = 80, t₂ = 35
→ P1 周期短，仍是高优先级。

CPU 利用率：U = 25/50 + 35/80 = 0.50 + 0.4375 = 0.9375

Gantt 图：

推演：

  • t=0~25：P1 运行完成（deadline 50 ✓）
  • t=25~50：P2 运行 25 个单位（还差 10）
  • t=50：P1 新周期抢占 → P1 运行 50~75
  • t=75~80：P2 只跑了 5 个单位，到 t=80 时还差 5 个单位

❌ P2 在 t = 80 错过了它的截止期限。

4. RMS 的理论结论（重要补充）

  • RMS 是静态优先级策略中的最优者：若 RMS 都无法调度，则任何静态优先级算法都不能。

  • Liu & Layland 界限：n 个周期任务，若 U≤n(21/n−1) 则 RMS 一定可调度。

    • n=1：100%；n=2：82.83%；n=∞：收敛到 ln 2 ≈ 69.3%
    • 上面失败例子中 U = 93.75% > 82.83%，超出保证范围，故可能失败（注意：超出不代表一定失败，只是不保证）。

  • 局限：CPU 利用率有上界，无法充分利用处理器。

二十七、最早截止期限优先（Earliest-Deadline-First, EDF）

1. 规则

按截止期限分配优先级：

  • 截止期限越早 → 优先级越高
  • 截止期限越晚 → 优先级越低

这是动态优先级（dynamic priority）：每当一个新进程变为可运行，它必须宣告其 deadline，调度器据此重新调整优先级。

2. 示例

参数：P1: p₁ = 50, t₁ = 25；P2: p₂ = 80, t₂ = 35（与 RMS 失败例子完全相同）

Gantt 图：

关键推演：

  • t=0：P1 的 deadline=50，P2 的 deadline=80 → P1 先跑 0~25
  • t=25~60：P2 运行，完成全部 35 个单位（deadline 80 ✓）
  • t=50：P1 第二周期到达，deadline=100；此时 P2 的 deadline=80 更早，P1 不抢占 P2（这是与 RMS 最本质的区别！）
  • t=60~85：P1 运行 25 个单位（deadline 100 ✓）
  • t=80：P2 第二周期到达，deadline=160
  • 继续交替……

✅ 所有截止期限都被满足——EDF 成功调度了 RMS 失败的场景。

优点 说明
理论最优 只要 U ≤ 1（即 100%），EDF 就一定能调度成功
不要求周期性 进程无需是周期性的，也不要求 CPU 时间恒定，只需在变为可运行时宣告 deadline
CPU 利用率高 可达 100%，远优于 RMS 的 69%~83%
缺点 说明
开销大 每次任务到达都要重新计算优先级并重排

二十八、比例分享调度（Proportional Share Scheduling）

规则

系统中共分配 T 份（shares），某应用获得 N 份（N < T），这就保证该应用能得到 N / T 的总处理器时间。

示例：T = 100 份

  • A 分得 50 份 → 50% CPU
  • B 分得 15 份 → 15% CPU
  • C 分得 20 份 → 20% CPU
  • 剩余 15 份可分配给新进程

必须配合准入控制：若新进程 D 申请 30 份，而只剩 15 份，则拒绝其进入系统——否则已有进程的保证就被破坏。

💡 与 Linux CFS 的关系：CFS 本质上就是一种比例分享调度（按 nice 值确定权重份额）。

三十、操作系统实例之一：Linux 调度

1. 2.5 版本之前

运行标准 UNIX 调度算法的变体。问题：对 SMP 支持差，且随任务数增加而性能下降（O(n)）。

2. 版本 2.5：O(1) 调度器

特性 说明
时间复杂度 常数级 O(1) ——选择下一个任务的时间与任务数无关
类型 抢占式、基于优先级
两个优先级范围 实时：0 ~ 99；nice 值：100 ~ 140
映射 映射到全局优先级，数值越小优先级越高
时间片 优先级越高，时间片 q 越大
任务状态 时间片有剩余 = active（可运行）；时间片耗尽 = expired（不可运行），必须等所有其他任务都用完各自的时间片
数据结构 每 CPU 一个 runqueue，内含两个优先级数组（active / expired），任务按优先级索引
数组交换 当 active 数组为空时，两个数组直接交换指针（这正是 O(1) 的来源）

❌ 缺点：交互式进程的响应时间不佳——这是 O(1) 调度器最终被替换的直接原因。

3. 版本 2.6.23 起：完全公平调度器（CFS）

CFS = Completely Fair Scheduler

(1) 调度类（Scheduling Classes）
  • 每个调度类有特定的优先级；
  • 调度器从最高优先级的调度类中挑选最高优先级的任务；
  • 标准包含两个类：default（CFS 本身） 和 real-time，可自行添加其他类。
(2) 核心思想：按比例而非固定时间片

时间片不再是固定的时间分配量，而是基于 CPU 时间的"比例（proportion）"。

  • 比例由 nice 值（-20 ~ +19） 计算得出，数值越低优先级越高（默认 0）。

  • 目标延迟（target latency）：每个任务至少应运行一次的时间区间。

    • 活动任务数增加时，target latency 可相应增大（但有最小值下限，防止切换过频）。

  • 例：target latency = 10 ms，2 个任务各得 5 ms；10 个任务则各得 1 ms。

(3) 虚拟运行时间（vruntime）—— CFS 的灵魂

CFS 为每个任务维护变量 vruntime（虚拟运行时间）。

  • vruntime 关联一个基于优先级的衰减因子（decay factor）：

    • 优先级越低 → 衰减率越高（vruntime 增长越快 → 越快被"用完额度"）

  • 普通默认优先级（nice = 0）→ 虚拟运行时间 = 实际运行时间

    • 高优先级（nice < 0）→ vruntime 增长慢于实际时间

  • 决策规则：选择 vruntime 最小的任务运行。

💡 精妙之处：CFS 用"谁欠得最多就先还谁"取代了"谁优先级高谁先跑"。优先级不再决定顺序，而是决定虚拟时钟走得快慢——高优先级任务的时钟走得慢，于是能获得更多真实 CPU 时间。

(4) CFS 的实现：红黑树

每个可运行任务被放入一棵红黑树（red-black tree）——以 vruntime 为键的平衡二叉搜索树。

  • 任务变为可运行时加入树；被阻塞（如等待 I/O）时从树中移除。
  • 左侧 = 获得 CPU 时间较少（vruntime 小）；右侧 = 已获得较多 CPU 时间。
  • 按二叉搜索树性质，最左节点（leftmost）的键值最小，即 CFS 认为优先级最高的任务。
  • 红黑树是平衡的，找最左节点需 O(lg N)；但 Linux 将该值缓存在变量 rb_leftmost 中，因此实际选择下一个任务只需读取缓存值 → O(1)。
(5) Linux 的实时调度
  • 按 POSIX.1b 实现，实时任务使用静态优先级。
  • 实时与普通任务共同映射到全局优先级方案：
  • nice = −20 → 全局优先级 100
  • nice = +19 → 全局优先级 139
  • 数值越小优先级越高；实时任务（0~99）总是优先于所有普通任务（100~139）。
(6) 负载均衡与 NUMA 感知

Linux 支持负载均衡，同时也是 NUMA 感知的。

调度域（Scheduling Domain）：

一组可以相互进行负载均衡的 CPU 核心。

  • 调度域按共享的资源（如缓存） 来组织，形成层次结构；
  • 目标：阻止线程在不同调度域之间迁移（跨域迁移代价最大）。
  • domain₀ 内 core₀、core₁ 共享 L2 缓存 → 在此域内迁移代价最低，可频繁均衡；
  • domain₀ 与 domain₁ 共享 L3 缓存 → 上一级域，迁移代价中等，均衡频率较低；
  • 跨 NUMA 节点迁移 → 代价最高，只在严重不均衡时才做。

💡 这正是"负载均衡 vs 处理器亲和性"矛盾的工程化解决方案：按共享层次分级，越共享越愿意迁移。

三十一、操作系统实例之二：Windows 调度

1. 基本机制

Windows 使用基于优先级的抢占式调度。

  • 最高优先级的线程总是下一个运行；
  • 负责调度的模块称为分派程序（dispatcher）；
  • 线程会一直运行，直到发生以下三种情况之一：
    1. 阻塞（blocks）
    2. 用完时间片（uses time slice）
    3. 被更高优先级的线程抢占（preempted）
  • 实时线程可以抢占非实时线程；
  • 若没有可运行线程，则运行空闲线程（idle thread）。

2. 32 级优先级方案

  • 每个优先级各有一个队列；
  • 分派程序从最高优先级的非空队列中取线程。

3. Win32 优先级类（Priority Classes）

进程可属于的六个优先级类：

优先级类 说明
REALTIME_PRIORITY_CLASS 唯一的实时类，优先级固定不变
HIGH_PRIORITY_CLASS 高
ABOVE_NORMAL_PRIORITY_CLASS 高于普通
NORMAL_PRIORITY_CLASS 普通（默认）
BELOW_NORMAL_PRIORITY_CLASS 低于普通
IDLE_PRIORITY_CLASS 空闲

⚠️ 除 REALTIME 外，其余全部是"可变类（variable）"——其优先级会被动态调整。

线程在类内的相对优先级（7 级）：

数值优先级 = 优先级类 + 相对优先级 的组合。

4. 动态优先级调整规则（考点）

情形 调整
时间片用完（quantum expires） 降低优先级，但绝不低于基准优先级（base priority）
从等待中释放（补充） 提升优先级，提升幅度取决于等待的对象（等键盘 I/O 提升多，等磁盘 I/O 提升少）
前台窗口进程（补充） Windows 会给当前前台进程更大的时间片（通常 3 倍），改善交互体验

💡 设计意图：I/O 密集型 / 交互式线程因频繁阻塞而获得提升 → 响应快；CPU 密集型线程因耗尽时间片而被降低 → 不影响交互。这与 MLFQ 的思想一脉相承。

1. 完整对照表（行 = 相对优先级，列 = 优先级类）

相对优先级 ＼ 优先级类 real-time high above normal normal below normal idle priority
time-critical 31 15 15 15 15 15

above normal 25 14 11 9 7 5
normal（基准） 24 13 10 8 6 4
below normal 23 12 9 7 5 3

2. 读表要点（高频考点）

  1. 数值优先级 = 优先级类（列）+ 相对优先级（行） 交叉决定。

  2. 基准优先级（base priority）= 该类中 NORMAL 行的值。
    例：NORMAL 类的基准 = 8；HIGH 类的基准 = 13。
    → 时间片耗尽时优先级下降，但绝不会低于这个基准值。

  3. time-critical 和 idle 两行是"封顶/触底"行，不遵循 ±1 的规律：

    • 非实时类的 time-critical 一律为 15（可变类的最高值）
    • 非实时类的 idle 一律为 1（优先级 0 保留给内存管理线程）
    • 实时类的 time-critical = 31（系统最高），idle = 16（实时类下限）

  4. 实时类占 16~31，可变类占 1~15，二者严格隔离——任何实时线程都高于任何可变线程。

  5. 中间五行呈规律的 ±1 阶梯：以 normal 行为中心，向上 +1、+2，向下 −1、−2。

    • 例外：real-time 列的 highest = 26（不是 25+1=26 ✓，规律成立），但 time-critical 直接跳到 31。

  6. idle priority 类的用途：屏幕保护程序、后台索引、统计分析等——只在系统完全空闲时才运行。

💡 动态调整回顾：只有可变类（1~15）会被动态调整。

  • 时间片耗尽 → 优先级 降低（不低于 base）
  • 从等待中唤醒 → 优先级 提升（等键盘 I/O 提升大，等磁盘 I/O 提升小）
  • 前台窗口进程 → 时间片 延长（通常 3 倍）

三十三、操作系统实例之三：Solaris 调度

1. 基本特征

Solaris 采用基于优先级的调度，提供六个调度类，每个类有自己的调度算法。

类 全称 说明
TS Time Sharing（分时） 默认类，使用多级反馈队列（MLFQ）
IA Interactive（交互） 用于图形界面应用，与 TS 算法相同但会给窗口焦点进程优先级提升
RT Real Time（实时） 提供有保证的响应时间
SYS System（系统） 内核线程专用（调度程序、页面守护进程等），优先级固定不变
FSS Fair Share（公平分享） 使用 CPU 份额（shares） 而非优先级，即比例分享调度
FP Fixed Priority（固定优先级） 优先级范围与 TS 相同，但不动态调整

⚠️ 一个线程在同一时刻只能属于一个类。

分派表（dispatch table）是"可加载的（loadable）"——系统管理员可以配置修改。

三列的含义（核心考点）
列 含义

三条规律（必须理解）

① 优先级越高 → 时间片越短

💡 为什么反直觉地"高优先级给短时间片"？
因为高优先级在 Solaris 中意味着交互性强（频繁 I/O）。这类线程只需要很短的 CPU 时间就会主动阻塞，给长时间片没意义；而低优先级的 CPU 密集型线程给长时间片可以减少上下文切换开销。

② 用完时间片 → 优先级降低（惩罚 CPU 密集型）

（低优先级区间如 0、5、10，expired 后仍为 0——已经触底）

③ 从睡眠返回 → 优先级大幅提升（奖励 I/O 密集型 / 交互型）

这保证了交互式线程（等键盘、等鼠标、等磁盘）一旦被唤醒就能立刻获得高优先级抢占 CPU，从而获得极佳的响应时间。

🎯 这张表就是"多级反馈队列"的具体参数实例——完美对应 MLFQ 的两个关键参数：何时降级（expired 列）、何时升级（return from sleep 列）。

3. Solaris 全局优先级结构

全局优先级区间 类
160 – 169 中断线程（interrupt threads） ← 最高
100 – 159 实时线程（RT）
60 – 99 系统线程（SYS）
0 – 59 FSS、FX、TS、IA（四类共享同一区间）

⚠️ Solaris 的全局优先级：数值越大 = 优先级越高（与 Linux、Windows 相反，注意区分！）

4. 调度流程

调度器把各类特有的优先级转换为"每线程的全局优先级（global priority）"，然后：

  • 优先级最高的线程下一个运行；
  • 该线程一直运行，直到：
    1. 阻塞（blocks）
    2. 用完时间片（uses time slice）
    3. 被更高优先级线程抢占（preempted）
  • 同一优先级有多个线程时，用 RR（轮转）选择。

📌 与 Windows 的机制高度相似：都是"全局优先级 + 抢占 + 同级 RR + 三种让出条件"，区别只在优先级方向和类的划分。

三十四、算法评估（Algorithm Evaluation）

核心问题

如何为一个操作系统选择 CPU 调度算法？

步骤：① 确定评价准则（criteria）→ ② 用准则评估各算法。

准则示例：

  • “在最大响应时间为 1 秒的约束下，最大化 CPU 利用率”
  • “使周转时间与总执行时间成线性比例”

四种评估方法（由简到繁、由粗到精）：

三十五、方法一：确定性建模（Deterministic Modeling）

1. 定义

属于解析评估（analytic evaluation） 的一种：
取一个特定的、预先确定的工作负载，计算各算法在该负载下的性能表现。

2. 示例：5 个进程，均在时刻 0 到达

进程 突发时间
P1 10
P2 29
P3 3
P4 7
P5 12

① FCFS —— 平均等待时间 28 ms

等待时间：0, 10, 39, 42, 49 → (0+10+39+42+49)/5 = 28 ms

② 非抢占 SJF —— 平均等待时间 13 ms

执行顺序按突发时间排序：P3(3) → P4(7) → P1(10) → P5(12) → P2(29)
等待时间：P3=0, P4=3, P1=10, P5=20, P2=32 → (0+3+10+20+32)/5 = 13 ms

③ RR（q = 10）—— 平均等待时间 23 ms

等待时间：P1=0, P2=(10−0)+(40−20)… → 计算得平均 23 ms

结论：SJF (13) < RR (23) < FCFS (28) —— 本例中 SJF 最优。

3. 优缺点（考点）

优点 缺点
简单、快速 需要精确的输入数字
给出明确的数值可供比较 结论只适用于这一组特定输入，不能推广
适合描述算法、举例教学 真实系统的负载是随机变化的，无法预先知道

💡 若要有用，必须在大量样本上反复运行确定性建模，才能得出有普遍意义的趋势。

三十六、方法二：排队模型（Queueing Models）

1. 基本思想

用概率分布来描述进程的到达，以及 CPU 突发和 I/O 突发的分布。

  • 通常假设为指数分布（exponential），用均值（mean） 来刻画；
  • 可计算出平均吞吐量、利用率、等待时间等。

排队网络分析（queueing-network analysis）：

把计算机系统描述为一个服务器网络，每个服务器（CPU、磁盘等）都带有一个等待进程队列。
已知到达率（arrival rate） 和服务率（service rate），即可计算出利用率、平均队列长度、平均等待时间等。

2. Little 公式（Little’s Law）★ 必考

符号定义：

  • n = 平均队列长度（average queue length）
  • W = 队列中的平均等待时间（average waiting time）
  • λ = 进入队列的平均到达率（average arrival rate）

推导直觉：在稳态（steady state） 下，离开队列的进程数必须等于到达队列的进程数，因此：

​ n=λ×W

通用性：对任何调度算法和任何到达分布都成立——这是 Little 公式最强大的地方。

教材例题：

若平均每秒到达 7 个进程（λ = 7），队列中通常有 14 个进程（n = 14），则：

W=nλ=147=2 秒

📝 变式：三个量知其二即可求第三个。考试常给 λ 和 W 求 n，或给 n 和 W 求 λ。

3. 局限

  • 数学计算可能非常复杂；
  • 分布假设（如指数分布）可能不符合实际；
  • 为了让数学可解，往往要做不切实际的简化假设；
  • 结果只是近似，准确性存疑。

三十七、方法三：仿真（Simulations）

1. 为什么需要

排队模型有局限，仿真更为准确。

2. 做法

  • 编写计算机系统的程序化模型（programmed model）；
  • 时钟是一个变量（clock is a variable）——每次推进这个变量，修改系统状态；
  • 运行过程中收集统计数据，反映算法性能。

3. 驱动数据的三种来源

来源 说明 问题
随机数生成器 按照给定的概率分布生成进程到达、突发时间、I/O 等事件 只给出事件的频率分布，丢失了事件发生的顺序关系
数学/经验定义的分布 分布可由数学定义（均匀、指数、泊松），也可由实测经验数据定义 同上
跟踪磁带 / 跟踪文件（Trace tapes / trace files） 记录真实系统中真实事件的发生序列 最准确，但需要大量存储空间，且监视程序本身会影响系统

4. 仿真评估流程图

流程解读：

  1. 从真实进程执行中采集事件序列，录成跟踪磁带（如 CPU 突发 10、I/O 213、CPU 12……）；
  2. 同一条跟踪磁带分别喂给多个仿真器；
  3. 每个仿真器实现不同的调度算法（FCFS / SJF / RR q=14）；
  4. 分别得到各自的性能统计数据，进行公平对比。

💡 关键优势：使用同一份输入数据比较不同算法，排除了负载差异的干扰，结论具有可比性。

5. 局限

  • 仿真器本身可能设计复杂、开销大（数小时的 CPU 时间）；
  • 仿真越精细，编程工作量越大；
  • 仍然只是模型，精度有限。

三十八、方法四：实际实现（Implementation）

1. 做法

即使仿真也只有有限的精度——唯一完全准确的方法就是：
把新调度器真正实现出来，放到真实系统中测试。

2. 代价

问题 说明
高成本（high cost） 需要把算法写进操作系统内核，并修改依赖它的用户程序
高风险（high risk） 在生产系统上试验可能造成故障；用户也不喜欢系统频繁变动
环境各异（environments vary） 在 A 环境测出的结论未必适用于 B 环境

3. 应对：可配置的调度器

最灵活的调度器可以按站点（per-site）或按系统（per-system）进行修改，或提供 API 来调整优先级。

例子：

  • Solaris 的可加载分派表（loadable dispatch table）；
  • Linux 的 nice、sched_setscheduler()；
  • Windows 的 SetPriorityClass()；
  • POSIX 的 pthread_attr_setschedpolicy()。

⚠️ 但仍然：环境各异（but again environments vary）。
而且另一个隐患：用户会针对调度器的行为"调优"自己的程序，导致算法在实验室的表现与真实部署后大相径庭（这是一种"古德哈特定律"效应）。

四十一、易错点与考点提醒

  1. 优先级数值方向必须分清：
    • Linux：小 = 高（0 最高）
    • Windows：大 = 高（31 最高）
    • Solaris：大 = 高（169 最高）
  2. Windows 优先级表的两条"异常行"：time-critical 在非实时类恒为 15，idle 恒为 1。
  3. Windows 的 base priority 就是 NORMAL 行的值，降级不得低于它。
  4. Solaris 分派表的反直觉规律：优先级越高，时间片越短。常出选择题。
  5. Solaris 的 return from sleep 跃升幅度极大（priority 0 → 50），体现对交互式线程的强力奖励。
  6. Solaris 六个类的缩写要能对应：TS（默认，MLFQ）、IA、RT、SYS、FSS、FP。
  7. Little 公式 n = λ × W 必须记牢，并能做三量互求的计算。注意 W 是在队列中等待的时间，不含服务时间。
  8. Little 公式适用于任何调度算法和任何到达分布——这句话本身是判断题常客。
  9. 确定性建模的两大缺点：需精确输入 + 结论只对该输入有效。
  10. 跟踪磁带（trace tape）的价值：保留真实事件的顺序，而随机数生成器只保留频率分布。
  11. 仿真图的要点：同一条 trace tape 喂给多个不同算法的仿真器，从而公平比较。
  12. 实际实现的三大问题：高成本、高风险、环境各异。
