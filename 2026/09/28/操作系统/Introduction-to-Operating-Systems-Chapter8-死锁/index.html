死锁（Deadlocks）

一、本章目标

本章讲解使用互斥锁时死锁如何产生，死锁的四个必要条件，以及如何在资源分配图中识别死锁。之后介绍处理死锁的几类方法：预防、避免（银行家算法）、检测和恢复。

二、系统模型

系统由若干资源类型 R₁, R₂, …, Rₘ 组成，例如 CPU 周期、内存空间、I/O 设备。每种资源类型 Rᵢ 有 Wᵢ 个实例。

线程使用资源的固定流程是：申请（request）→ 使用（use）→ 释放（release）。

信号量导致死锁的例子

两个信号量 S1、S2 初值都为 1：

如果 T1 拿到 S1、T2 拿到 S2，那么两者都会卡在第二个 wait 上，互相等待对方释放，形成死锁。

三、死锁的特征：四个必要条件

以下四个条件同时成立时才可能发生死锁：

条件 含义
互斥 (Mutual exclusion) 一个资源一次只能被一个线程使用
占有并等待 (Hold and wait) 线程已持有至少一个资源，同时又在等待其他线程持有的资源
不可抢占 (No preemption) 资源只能由持有者在完成任务后主动释放
循环等待 (Circular wait) 存在等待链 {T₀, T₁, …, Tₙ}：T₀ 等 T₁ 的资源，T₁ 等 T₂ 的资源……Tₙ 等 T₀ 的资源

记忆要点：这四个是必要条件，只要破坏其中任意一个，死锁就不会发生。

四、资源分配图（Resource-Allocation Graph）

1. 组成

顶点分为两类：线程集合 T = {T₁, …, Tₙ}，画成圆圈；资源类型集合 R = {R₁, …, Rₘ}，画成方框，框内的圆点表示实例数。

边分为两类：

  • 请求边：Tᵢ → Rⱼ，表示线程在等待该资源
  • 分配边：Rⱼ → Tᵢ，表示该资源的一个实例已分配给线程

2. 例题分析（图 1：无死锁）

资源：R₁ 有 1 个实例，R₂ 有 2 个，R₃ 有 1 个，R₄ 有 3 个。

  • T₁ 持有 1 个 R₂，等待 R₁
  • T₂ 持有 1 个 R₁、1 个 R₂，等待 R₃
  • T₃ 持有 1 个 R₃

结论：图中没有环，所以没有死锁。 T₃ 不等待任何资源，可以执行完并释放 R₃。随后 T₂ 获得 R₃，执行完后释放 R₁ 和 R₂，T₁ 再获得 R₁，最终所有线程都能完成。

3. 有死锁的图（图 2 / 图 3）

在图 1 的基础上，T₃ 又申请 R₂，于是增加了一条请求边 T₃ → R₂。此时图中出现两个环：

  • T₁ → R₁ → T₂ → R₃ → T₃ → R₂ → T₁
  • T₂ → R₃ → T₃ → R₂ → T₂

R₂ 的两个实例都已被 T₁、T₂ 占用，所以 T₃ 拿不到 R₂；T₂ 在等 T₃ 的 R₃，T₁ 在等 T₂ 的 R₁。三个线程全部阻塞，发生死锁。

4. 有环但无死锁的图（图 4）

图中有环：T₁ → R₁ → T₃ → R₂ → T₁。

但是 R₁、R₂ 各有 2 个实例，另外的实例分别被 T₂ 和 T₄ 持有，而这两个线程不在等待任何资源。T₄ 执行完释放 R₂ 后，T₃ 就能获得 R₂（或者 T₂ 释放 R₁ 后，T₁ 就能获得 R₁），环随之被打破，所以没有死锁。

5. 基本结论（重点）

  • 没有环 → 一定没有死锁
  • 有环时：
    • 如果每类资源只有一个实例 → 一定死锁
    • 如果每类资源有多个实例 → 只是可能死锁（图 3 是死锁，图 4 不是）

五、处理死锁的方法

  1. 确保系统永不进入死锁状态

    ，包括两种方式：

    • 死锁预防（Prevention）
    • 死锁避免（Avoidance）

  2. 允许进入死锁状态，然后检测并恢复（Detection & Recovery）

  3. 忽略问题，假装死锁从不发生。这是包括 Linux、Windows 在内的大多数操作系统的实际做法，由应用程序开发者自己处理。

六、死锁预防（Prevention）

核心思路：破坏四个必要条件中的至少一个。

破坏的条件 做法 问题
互斥 可共享资源（如只读文件）不需要互斥 不可共享的资源（如互斥锁）必须互斥，通常无法破坏
占有并等待 ① 线程开始执行前一次性申请全部资源；② 只在不持有任何资源时才能申请 资源利用率低，可能饥饿
不可抢占 线程申请的资源无法立即满足时，释放其已持有的全部资源，并把这些资源加入它的等待列表；只有能同时拿回旧资源和新资源时才重启 只适合状态容易保存和恢复的资源（如 CPU 寄存器、内存），不适合互斥锁
循环等待 给所有资源类型规定一个全序，线程必须按编号递增的顺序申请资源 最常用、最实用

循环等待的例子

给每个互斥锁分配唯一编号：first_mutex = 1，second_mutex = 5，线程必须按编号从小到大加锁。

thread_two 不允许这样写。否则 thread_one 持有 first 在等 second，thread_two 持有 second 在等 first，就会形成循环等待，导致死锁。正确写法是 thread_two 也先锁 first_mutex 再锁 second_mutex。

七、死锁避免（Avoidance）

1. 基本思想

系统需要预先获得额外信息。最简单也最常用的模型是：每个线程事先声明它对每类资源的最大需求量。

避免算法在每次分配时动态检查资源分配状态，确保永远不会出现循环等待。

资源分配状态由三部分决定：可用资源数、已分配资源数、各线程的最大需求。

2. 安全状态（Safe State）

线程申请资源时，系统要判断立即分配之后系统是否仍处于安全状态，只有安全才分配。

定义： 如果存在一个包含所有线程的序列 <T₁, T₂, …, Tₙ>，使得对每个 Tᵢ，它还可能申请的资源都能由"当前可用资源 + 所有 Tⱼ（j < i）持有的资源"满足，那么系统处于安全状态，这个序列称为安全序列。

直观理解：

  • 如果 Tᵢ 的需求不能立即满足，它就等待排在它前面的 Tⱼ 全部完成
  • Tⱼ 完成后释放资源，Tᵢ 获得所需资源，执行、归还资源后终止
  • Tᵢ 终止后，Tᵢ₊₁ 再获得所需资源，依此类推

3. 安全、不安全与死锁的关系

  • 安全状态 → 一定不会死锁
  • 不安全状态 → 可能死锁（不一定会死锁）
  • 死锁状态是不安全状态的一个子集

避免策略的本质：确保系统永远不进入不安全状态。

4. 避免算法的选择

资源情况 使用的算法
每类资源只有单个实例 资源分配图算法（带需求边）
每类资源有多个实例 银行家算法

八、资源分配图算法（单实例资源）

1. 新增"需求边"（Claim Edge）

需求边 Tᵢ ⇢ Rⱼ 用虚线表示，意思是线程 Tᵢ 将来可能申请 Rⱼ。（注：课件文字写成了"process Tj"，应为 Tᵢ。）

三种边的转换关系：

线程开始执行前，它所有的需求边必须已经在图中声明好。

2. 分配规则

只有当请求边转换为分配边之后，图中（把需求边也算进去）不形成环时，才允许分配；否则线程必须等待。环检测的复杂度约为 O(n²)。

九、资源分配图算法的判定规则（补充）

这部分是对第八节的补充。假设线程 Tᵢ 申请资源 Rⱼ，系统只有在把这条请求边改成分配边之后，图中（包括需求边）不会形成环时，才批准这次申请；否则 Tᵢ 必须等待，即使 Rⱼ 当前是空闲的。

这个算法只适用于每类资源只有一个实例的情况。资源有多个实例时，要改用银行家算法。

十、银行家算法（Banker’s Algorithm）

1. 适用条件与基本约定

银行家算法用于每类资源有多个实例的情况，它对线程有以下要求：

  • 每个线程必须事先声明自己对每类资源的最大需求量
  • 线程申请资源时可能需要等待
  • 线程拿到全部所需资源后，必须在有限时间内归还

名字的由来：银行不会把现金一次性贷出，导致无法满足所有客户的最大需求。

2. 数据结构

设 n 为线程数，m 为资源类型数：

名称 维度 含义
Available 长度 m 的向量 Available[j] = k 表示 Rⱼ 当前有 k 个可用实例
Max n × m 矩阵 Max[i,j] = k 表示 Tᵢ 最多会申请 k 个 Rⱼ
Allocation n × m 矩阵 Allocation[i,j] = k 表示 Tᵢ 当前已分到 k 个 Rⱼ
Need n × m 矩阵 Need[i,j] = k 表示 Tᵢ 还可能需要 k 个 Rⱼ

关键公式：

Need[i,j]=Max[i,j]−Allocation[i,j]

向量比较约定： X ≤ Y 表示 X 的每一个分量都 ≤ Y 的对应分量。例如 (1,0,2) ≤ (3,3,2) 成立，但 (3,3,0) ≤ (2,3,0) 不成立。

3. 安全性算法（Safety Algorithm）

这个算法用来判断当前状态是否安全。

理解要点：Work 表示"模拟过程中手头可用的资源"。每找到一个能被满足的线程，就假设它运行结束并归还资源，Work 随之变大。复杂度为 O(m × n²)。

4. 资源请求算法（Resource-Request Algorithm）

设 Requestᵢ 为线程 Tᵢ 的请求向量，Requestᵢ[j] = k 表示 Tᵢ 想要 k 个 Rⱼ。

口诀：先查 Need，再查 Available，然后试分配，最后看安全。

5. 例题

5 个线程 T₀ ~ T₄，3 类资源：A 有 10 个实例，B 有 5 个，C 有 7 个。

T₀ 时刻快照：

线程 Allocation (A B C) Max (A B C) Need = Max − Alloc
T₀ 0 1 0 7 5 3 7 4 3
T₁ 2 0 0 3 2 2 1 2 2
T₂ 3 0 2 9 0 2 6 0 0
T₃ 2 1 1 2 2 2 0 1 1
T₄ 0 0 2 4 3 3 4 3 1

Available = (3, 3, 2)

（1）验证安全序列 <T₁, T₃, T₄, T₂, T₀>
步骤 选中线程 Need ≤ Work？ Work 变化
初始 — — (3,3,2)
1 T₁ (1,2,2) ≤ (3,3,2) ✓ + (2,0,0) = (5,3,2)
2 T₃ (0,1,1) ≤ (5,3,2) ✓ + (2,1,1) = (7,4,3)
3 T₄ (4,3,1) ≤ (7,4,3) ✓ + (0,0,2) = (7,4,5)
4 T₂ (6,0,0) ≤ (7,4,5) ✓ + (3,0,2) = (10,4,7)
5 T₀ (7,4,3) ≤ (10,4,7) ✓ + (0,1,0) = (10,5,7)

所有线程都能完成，系统处于安全状态。最终 Work 等于资源总量 (10,5,7)，可以用来检验计算是否正确。安全序列不唯一。

（2）T₁ 请求 (1, 0, 2)
  1. Request ≤ Need₁：(1,0,2) ≤ (1,2,2) ✓
  2. Request ≤ Available：(1,0,2) ≤ (3,3,2) ✓
  3. 试分配后：Available = (2,3,0)，Allocation₁ = (3,0,2)，Need₁ = (0,2,0)
  4. 运行安全性算法：
选中线程 Work 变化
— (2,3,0)
T₁：(0,2,0) ≤ (2,3,0) ✓ → (5,3,2)
T₃：(0,1,1) ≤ (5,3,2) ✓ → (7,4,3)
T₄：(4,3,1) ≤ (7,4,3) ✓ → (7,4,5)
T₀：(7,4,3) ≤ (7,4,5) ✓ → (7,5,5)
T₂：(6,0,0) ≤ (7,5,5) ✓ → (10,5,7)

存在安全序列 <T₁, T₃, T₄, T₀, T₂>，所以批准 T₁ 的请求。

（3）课后思考题（在 T₁ 请求被批准后的状态下）

T₄ 请求 (3, 3, 0) 能否批准？

Request ≤ Need₄，即 (3,3,0) ≤ (4,3,1) ✓；但 Request ≤ Available，即 (3,3,0) ≤ (2,3,0) ✗，A 类资源不够。

结论：不能批准，T₄ 必须等待（因为资源不足，根本不用进入安全检查）。

T₀ 请求 (0, 2, 0) 能否批准？

Request ≤ Need₀，即 (0,2,0) ≤ (7,4,3) ✓；Request ≤ Available，即 (0,2,0) ≤ (2,3,0) ✓。

试分配后：Available = (2,1,0)，Allocation₀ = (0,3,0)，Need₀ = (7,2,3)。

用 Work = (2,1,0) 逐个检查：

  • T₀ 需要 (7,2,3) ✗
  • T₁ 需要 (0,2,0) ✗（B 只有 1 个）
  • T₂ 需要 (6,0,0) ✗
  • T₃ 需要 (0,1,1) ✗（C 为 0）
  • T₄ 需要 (4,3,1) ✗

没有任何线程能满足，状态不安全。结论：不能批准，T₀ 必须等待，恢复原状态。

注意这个例子说明：资源够用 ≠ 可以分配，还必须保证分配后仍然安全。

十一、死锁检测（Deadlock Detection）

如果既不预防也不避免，就允许系统进入死锁状态，然后需要两样东西：检测算法和恢复方案。

1. 单实例资源：等待图（Wait-for Graph）

构造方法： 从资源分配图中去掉资源节点，把边合并。如果原图中有 Tᵢ → Rq → Tⱼ，就在等待图中画 Tᵢ → Tⱼ，表示 Tᵢ 在等待 Tⱼ 释放资源。

判定规则： 系统定期在等待图中搜索环，有环就说明存在死锁。环检测需要 O(n²) 次操作，n 是图中顶点数。

图例分析（Image 1）：

资源分配图 (a) 中的边关系：

请求关系 资源持有者 等待图中的边
T₁ → R₁ R₁ → T₂ T₁ → T₂
T₂ → R₃ R₃ → T₅ T₂ → T₅
T₂ → R₄ R₄ → T₃ T₂ → T₃
T₂ → R₅ R₅ → T₄ T₂ → T₄
T₃ → R₅ R₅ → T₄ T₃ → T₄
T₄ → R₂ R₂ → T₁ T₄ → T₁

对应的等待图 (b) 中存在两个环：

  • T₁ → T₂ → T₄ → T₁
  • T₁ → T₂ → T₃ → T₄ → T₁

因为每类资源只有一个实例，有环即死锁，死锁涉及 T₁、T₂、T₃、T₄。T₅ 不在环上，它可以正常执行完毕。

2. 多实例资源：检测算法

等待图只适用于单实例资源。多实例时使用类似银行家算法的矩阵方法。

数据结构：

名称 含义
Available 长度 m 的向量，表示每类资源的可用数量
Allocation n × m 矩阵，表示每个线程当前持有的资源
Request n × m 矩阵，Request[i][j] = k 表示 Tᵢ 当前正在申请 k 个 Rⱼ

算法步骤：

复杂度为 O(m × n²)。

与安全性算法的区别（重点）：

对比项 安全性算法（避免） 检测算法（检测）
比较对象 Need（将来最多还需要多少） Request（当前实际申请多少）
Finish 初始化 全部为 false 不持有任何资源的线程直接设为 true
结论含义 判断是否可能死锁（安全/不安全） 判断是否已经死锁，并找出死锁线程

为什么检测算法只看 Request？这是一种乐观假设：只要满足线程当前的请求，它就能运行完并归还资源。如果它之后又申请更多资源，下次检测时自然会发现。

Finish 初始化的原因：不持有任何资源的线程，不可能是造成别人等待的一方，因此不会处在死锁环中。

3. 检测算法例题

5 个线程 T₀ ~ T₄，3 类资源：A 有 7 个实例，B 有 2 个，C 有 6 个。

线程 Allocation (A B C) Request (A B C)
T₀ 0 1 0 0 0 0
T₁ 2 0 0 2 0 2
T₂ 3 0 3 0 0 0
T₃ 2 1 1 1 0 0
T₄ 0 0 2 0 0 2

Available = (0, 0, 0)

4. 检测算法何时调用

调用时机和频率取决于两个因素：死锁发生的频率，以及死锁发生时需要回滚多少线程（每个互不相交的环至少要回滚一个）。

两种极端做法：

  • 每次申请无法立即满足时就调用： 能准确找出"导致"死锁的那个线程，但开销很大。
  • 随意或低频调用（比如每小时一次，或 CPU 利用率降到某个阈值以下时）：开销小，但资源图中可能已经积累了很多环，无法判断是哪个线程"引起"了死锁。

十二、死锁恢复（Recovery from Deadlock）

1. 方法一：终止线程（Process Termination）

有两种做法：

做法 优点 缺点
终止全部死锁线程 一定能解除死锁，简单直接 代价大，已完成的计算全部作废
一次终止一个，直到环消除 损失较小 每终止一个都要重新运行检测算法，开销大

选择终止顺序时考虑的因素：

  1. 线程的优先级
  2. 线程已经计算了多久，还要多久才能完成
  3. 线程已经使用了哪些资源
  4. 线程完成还需要哪些资源
  5. 总共需要终止多少个线程
  6. 线程是交互式还是批处理

基本原则：选择代价最小的线程终止。

2. 方法二：抢占资源（Resource Preemption）

逐步从某些线程那里抢走资源，分给其他线程，直到死锁解除。需要解决三个问题：

问题 说明
选择牺牲者（Selecting a victim） 选哪个线程、抢哪些资源，目标是代价最小
回滚（Rollback） 被抢占的线程无法正常继续，需要回退到某个安全状态再重新开始。最简单的做法是完全回滚（直接重启）
饥饿（Starvation） 同一个线程可能总被选为牺牲者。解决办法是把回滚次数计入代价，被回滚越多次的线程越不容易再被选中

十三、全章知识框架与易错点

1. 四种策略对比

策略 核心思想 典型方法 代价
预防 破坏四个必要条件之一 资源编号，按序申请 资源利用率低，限制多
避免 每次分配前判断是否安全 资源分配图算法（单实例）、银行家算法（多实例） 需要预知最大需求，每次分配都要计算
检测 + 恢复 允许死锁，定期检测后处理 等待图（单实例）、检测算法（多实例）；终止线程或抢占资源 检测开销，恢复时有损失
忽略 认为死锁很少发生 大多数通用操作系统的做法 死锁发生时需人工处理

2. 算法与复杂度汇总

算法 适用场景 复杂度
资源分配图环检测 避免，单实例 O(n²)
银行家算法中的安全性算法 避免，多实例 O(m × n²)
等待图环检测 检测，单实例 O(n²)
检测算法 检测，多实例 O(m × n²)

3. 易错点

  1. 银行家算法第一步检查的是 Request ≤ Need，超过说明线程违规，应报错而不是等待。
  2. Request ≤ Available 成立，也不代表可以分配，还要通过安全性检查（参考 T₀ 请求 (0,2,0) 的例子）。
  3. 安全性算法用 Need，检测算法用 Request，不要混淆。
  4. 检测算法中，不持有资源的线程初始就设为 Finish = true。
  5. 安全序列可能不唯一，只要找到一个就说明安全。
  6. 计算完成后，可以检查最终 Work 是否等于资源总量，以此验证计算是否正确。
  7. 等待图只能用于单实例资源；多实例时有环不一定死锁，必须用检测算法。
