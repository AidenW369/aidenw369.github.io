二、操作系统服务（OS Services）

操作系统的本质：为程序的执行提供环境，并向用户和程序提供服务。服务分成两大类。

2.1 面向用户的服务（方便用户）

服务 说明
用户界面 UI CLI（命令行）、GUI（图形）、Touch-screen（触屏）、Batch（批处理）
程序执行 把程序装入内存并运行，能正常或异常结束（异常时指示错误）
I/O 操作 运行中的程序可能需要访问文件或 I/O 设备；用户程序不能直接操作 I/O，必须由 OS 代劳
文件系统操作 读/写/创建/删除文件与目录、搜索、列出文件信息、权限管理
通信 同一台机器内或跨网络的进程间信息交换。两种方式：共享内存（Shared Memory）与消息传递（Message Passing，由 OS 搬运数据包）
错误检测 持续感知 CPU、内存、I/O 设备、用户程序中的错误，并采取恰当动作以保证计算的正确性与一致性
调试设施 帮助用户和程序员更高效地使用系统

🔎 扩展：共享内存 vs 消息传递

  • 共享内存：速度快（无内核介入的数据拷贝），但需要程序员自己做同步（信号量/互斥锁）。
  • 消息传递：适合分布式/跨机器，天然避免竞争，但每条消息都要经过内核，开销大。
  • 现代高性能场景（如 Redis、数据库）大量使用共享内存 + 无锁结构。

2.2 面向系统自身的服务（保证系统高效运行）

服务 说明
资源分配 多用户/多任务并发时，把 CPU 周期、主存、文件存储、I/O 设备分配给各方
记账/日志（Logging） 记录哪个用户使用了多少、何种资源（用于计费、审计、调优）
保护与安全 保护：确保对系统资源的所有访问都受控，并发进程互不干扰；安全：抵御外部入侵，需要用户认证，并防止外部 I/O 设备的非法访问

🔎 保护（Protection）≠ 安全（Security）

  • 保护是内部问题：控制已授权用户/进程的访问边界（如页表权限位、文件 rwx）。
  • 安全是外部问题：判断"你是不是你说的那个人"（认证、加密、防火墙）。

三、用户与操作系统的接口

3.1 命令行解释器（CLI / Shell）

  • 允许直接输入命令。

  • 实现位置：有时在内核中，有时作为系统程序（现代 UNIX/Linux 是后者）。

  • 可有多种"风味"（flavors）——即各种 shell：sh、bash、zsh、csh、ksh、fish。

  • 主要工作循环：取一条命令 → 执行它（read-parse-execute loop）。

  • 命令的两种实现方式：

    1. 内建命令（built-in）：解释器代码里自带（如 cd、exit、export）。

    2. 外部程序名

      • ✅ 优势：新增功能不需要修改 shell，只要把新程序放进 $PATH 即可。

🔎 为什么 cd 必须是内建命令？
因为子进程改变工作目录不会影响父进程（shell 自身）。cd 必须由 shell 进程自己调用 chdir() 系统调用才有效。

3.2 图形用户界面（GUI）

  • 用户友好的桌面隐喻（desktop metaphor）。

  • 通常配合鼠标、键盘、显示器。

  • 图标代表文件、程序、动作等；鼠标不同按键触发不同动作（显示信息、弹出选项、执行功能、打开目录=文件夹）。

  • 诞生于 Xerox PARC（施乐帕洛阿尔托研究中心），后被 Apple Lisa/Macintosh 商业化。

  • 现代系统通常

    CLI + GUI 并存：

    • Windows：GUI 为主 + cmd/PowerShell。
    • macOS：Aqua GUI + UNIX(Darwin/XNU) 内核 + 各种 shell。
    • Unix/Linux：CLI 为主 + 可选 GUI（CDE、KDE、GNOME）。

3.3 触屏接口

  • 鼠标不可用或不适用。
  • 基于手势（gestures） 进行动作与选择：点按、长按、滑动、捏合。
  • 文本输入靠虚拟键盘。
  • 支持语音命令（Siri / Google Assistant）。

🔎 CLI vs GUI 该选谁？

  • CLI：可脚本化、可组合（管道）、远程/低带宽友好、可重复可审计 → 服务器、运维、开发。
  • GUI：学习曲线低、直观、适合空间型任务（绘图、排版） → 桌面终端用户。

四、系统调用（System Calls）

4.1 基本概念

  • 系统调用 = OS 所提供服务的编程接口。
  • 通常用高级语言编写（C/C++）。
  • 程序大多不直接使用系统调用，而是通过更高层的 API（应用程序编程接口） 访问。
  • 三大主流 API：
API 适用平台
Win32 API Windows
POSIX API 几乎所有 UNIX、Linux、macOS
Java API Java 虚拟机（JVM）
  • ⚠️ 教材中的系统调用名字是泛化的（generic），真实系统上名字可能不同。

4.2 三个概念的区分（重点，易考）

概念 含义 例子
API 程序员看到的函数签名与语义约定 read(int fd, void *buf, size_t count)
System Call 真正进入内核的入口，靠调用号标识 Linux x86-64 上 read = 0 号
ABI 二进制层面的约定（参数放哪个寄存器、栈如何对齐） System V AMD64 ABI

API 与系统调用不是一一对应的：

  • printf() → 内部可能多次调用 write()（带缓冲）。
  • malloc() → 平时只在用户态管理堆，只有堆不够时才调 brk()/mmap()。
  • getpid() 在 Linux 上可通过 vDSO 在用户态完成，根本不陷入内核。

通过 man read 查看 UNIX/Linux 的 read() 接口：

🔎 为什么返回值是 ssize_t 而不是 size_t？
size_t 是无符号的，无法表示 −1。ssize_t 是有符号版本，这样才能用 −1 报错。

🔎 短读（short read）陷阱：read() 返回值可能小于 count 而并非出错（管道、socket、信号打断）。正确写法必须循环读取，直到累计够数或返回 0/−1。

4.5 系统调用的实现

  • 每个系统调用关联一个编号（number）。
  • 系统调用接口维护一张按编号索引的表（system call table）。
  • 接口负责：调用内核中对应的系统调用 → 返回状态与返回值。
  • 调用者无需知道系统调用如何实现，只需遵守 API 并理解 OS 会做什么。
  • 大部分 OS 接口细节被 API 隐藏，由运行时支持库（run-time support library） 管理——即编译器附带的函数库（如 glibc）。

4.6 API–系统调用–OS 关系（截图 5）

完整流程（以 open() 为例）：

  1. 用户程序调用库函数 open()。
  2. 库函数把系统调用号放入约定寄存器，把参数按 ABI 摆好。
  3. 执行陷入指令（x86-64: syscall；ARM: svc），CPU 切换到内核态。
  4. 内核统一入口读取调用号 i，查系统调用表，跳转到 sys_open()。
  5. 内核执行，检查权限与参数合法性。
  6. 返回结果到寄存器，执行 sysret，切回用户态。
  7. 库函数检查返回值，若为负则设置 errno 并返回 −1。

🔎 为什么必须"陷入"而不是直接 call？
因为内核代码运行在特权级 0（ring 0），用户程序在 ring 3。普通跳转无法提升特权级。陷入指令是硬件提供的受控的、单一入口的提权通道，内核借此保证只能从合法入口进入并做完整的参数校验。

4.7 系统调用参数传递

需要传递的信息往往不止"调用号"本身，具体类型和数量因 OS 和调用而异。三种通用方法：

方法 描述 优点 缺点
① 寄存器传参 最简单，参数直接放寄存器 最快 参数可能比寄存器多，数量受限
② 块/表传参 参数存入内存中的一个块（block）或表（table），把块的地址放进一个寄存器传给 OS 不限参数数量和长度 多一次内存访问
③ 栈传参 程序把参数压（push） 入栈，OS 从栈中弹出（pop） 不限参数数量和长度 需要访问用户栈，需校验

考点：块方法与栈方法都不限制参数的数量和长度。
块/表方法被 Linux 和 Solaris 采用（用于参数超过寄存器数量时）。

4.8 通过表传递参数（截图 6）

流程：用户程序把参数集中放在内存地址 X 处 → 把 X 装入寄存器 → 发起 13 号系统调用 → OS 跳到 13 号调用的代码 → 从寄存器拿到 X → 从表 X 中取参数。

🔎 真实的 Linux x86-64 约定

用途 寄存器
系统调用号 rax
第 1–6 个参数 rdi, rsi, rdx, r10, r8, r9
返回值 rax

注意第 4 个参数用 r10 而非普通函数调用的 rcx——因为 syscall 指令会用 rcx 保存返回地址。
参数超过 6 个的调用（如 mmap 早期版本）就用结构体指针，正是"表传参"的实践。

⚠️ 为什么内核必须校验用户传来的指针？ 若不校验，用户可以传一个内核地址进来诱导内核读写自身内存——这是经典提权漏洞。Linux 用 copy_from_user() / copy_to_user() 做安全拷贝。

六、系统调用的六大类型

系统调用按功能可分为 6 大类（考试常考的分类框架）。

6.1 进程控制（Process Control）

功能 说明
创建进程、终止进程 create process / terminate process
结束、中止 end（正常结束）/ abort（异常中止）
装入、执行 load / execute
获取/设置进程属性 优先级、最大执行时间等
等待时间 wait for time
等待事件、发出事件信号 wait event / signal event
分配与释放内存 allocate / free memory
出错时转储内存 Dump memory（core dump，用于事后分析）
调试器 定位 bug、单步执行（single step）
锁 管理进程间对共享数据的访问

🔎 end / abort 的区别：end 是程序自己认为完成了，正常退出；abort 是出错被迫终止，通常伴随 core dump。这对应 FreeBSD 例子里的退出码：0 = 无错，>0 = 错误码。

6.2 文件管理（File Management）

create file / delete file / open / close / read / write / reposition（重定位读写指针，即 lseek）/ get and set file attributes（属性：名字、类型、权限、时间戳）

6.3 设备管理（Device Management）

request device（请求，即独占）/ release device（释放）/ read / write / reposition / get and set device attributes / 逻辑地挂载或卸载设备（attach / detach）

🔎 UNIX 的哲学：一切皆文件。设备被抽象成 /dev 下的文件，所以文件管理与设备管理的系统调用高度重合（都用 open/read/write/close）。差异部分由万能接口 ioctl() 兜底。

6.4 信息维护（Information Maintenance）

get/set time or date / get/set system data（系统数据，如版本、可用内存、用户数）/ 获取与设置进程、文件或设备的属性

🔎 注意一个深刻差异：Windows 用 CreateProcess() 一步创建并加载新程序；UNIX 用 fork() + exec() 两步。

  • fork() 复制当前进程得到子进程（父子分别返回子进程 PID 和 0）。
  • exec() 用新程序覆盖当前进程的内存映像。
  • 分开的好处：在 fork() 与 exec() 之间可以做重定向、改权限、设环境变量——这正是 shell 实现 ls > out.txt 和管道的关键窗口。
  • UNIX 中"用户程序 → 系统程序"这些功能上等价的调用，正说明"系统调用名是泛化的"这句话。

八、标准 C 库示例（截图 2）

C 程序调用 printf() 库函数，而 printf() 内部调用 write() 系统调用。

要点：

  • 标准 C 库为许多 UNIX/Linux 版本提供了系统调用接口的一部分。
  • C 库拦截（intercepts）printf() 调用，转而发起必要的一个或多个系统调用。
  • C 库拿到 write() 的返回值后，再传回给用户程序。

🔎 为什么要多一层库？

  1. 可移植性：同一份 C 源码在不同 OS 上链接不同的库即可。
  2. 性能：printf 有缓冲（stdout 连终端时行缓冲，连文件时全缓冲），把多次小写合并成一次 write，大幅减少陷入内核的次数。
  3. 易用：格式化、错误码转换（errno）等杂活由库完成。

⚠️ 经典现象：printf 后程序崩溃，输出"丢了"——因为还在库的缓冲区里没 flush。解决：fflush(stdout) 或用 write() 直写。

十二、为什么应用程序是操作系统相关的

在一个系统上编译的应用，通常不能在另一个 OS 上执行。 三个根本原因：

  1. 系统调用不同 —— 每个 OS 提供自己独有的系统调用（对比 fork() vs CreateProcess()）。
  2. 文件（二进制）格式不同 —— ELF vs PE vs Mach-O。
  3. CPU 指令集不同 —— x86-64 vs ARM（教材在 ABI 处点出）。

让应用跨多个 OS 的三种途径

方案 原理 例子
解释型语言 用 Python、Ruby 等编写，只要目标平台有解释器即可 Python 脚本
含虚拟机的语言 应用运行在 VM 之中 Java（JVM）、C#（CLR）
标准语言 + 分别编译 用标准语言（如 C）写，在每个 OS 上分别编译 跨平台 C/C++ 项目

三种方案的代价：解释型和 VM 型牺牲性能；分别编译则要为每个平台维护构建并处理平台差异（#ifdef _WIN32）。

ABI（Application Binary Interface）

ABI 是 API 在体系结构层面的等价物，它定义了在给定的 OS、给定的体系结构/CPU 上，二进制代码的不同组成部分如何互相接口。

ABI 规定的内容：

  • 参数用哪些寄存器传递、多余的怎么压栈
  • 返回值放哪里
  • 栈帧布局与对齐要求
  • 基本数据类型的大小与字节序（long 是 4 还是 8 字节？）
  • 目标文件与可执行文件的二进制格式

API vs ABI 一句话区分：

  • API 保证源代码级兼容——源码不用改，重新编译即可。
  • ABI 保证二进制级兼容——编译好的 .o/.so 不用重编就能链接运行。

十三、操作系统的设计与实现

13.1 设计原则

  • OS 的设计与实现不是一个可"求解"的问题，但有些方法已被证明成功。
  • 不同 OS 的内部结构差异极大。
  • 设计从定义目标与规格说明开始，受硬件选择和系统类型影响。

两类目标（重点对比）

用户目标 (User goals) 系统目标 (System goals)
提出者 最终用户 设计者、实现者、维护者
内容 使用方便、易学、可靠、安全、快速 易于设计、实现、维护，以及灵活、可靠、无错、高效
性质 模糊、难以量化 相对具体，但同样无统一解

规格说明与设计 OS 是一项高度创造性的软件工程任务——没有教科书式的标准答案。

13.2 策略与机制（Policy and Mechanism）⭐

定义 例子
策略 Policy 需要做什么？ 每 100 秒中断一次

  • Macintosh 早期系统：机制与策略深度绑定，改起来极难。

14.1 宏内核结构 —— 最初的 UNIX

  • 受硬件功能限制，最初的 UNIX 结构化程度很低。
  • UNIX 由两个可分离的部分组成：系统程序与内核。
  • 内核 = 系统调用接口以下、物理硬件以上的一切。
  • 内核提供文件系统、CPU 调度、内存管理及其他 OS 功能——在同一个层次上塞进了大量功能。

十五、分层方法（Layered Approach）

15.1 基本思想（截图 1）

  • 操作系统被划分成若干层（levels），每一层建立在更低层之上。
  • 最底层（layer 0）是硬件；最高层（layer N）是用户接口。
  • 借助模块化，层的划分要满足：每一层只使用更低层的功能（操作）和服务。

15.2 优点与困难

优点 困难
构造与调试简单：调试第 N 层时，可假定 0~N−1 层已正确 层的定义困难：某层必须只用到更低层的服务，但依赖关系常有循环
信息隐藏：上层不必知道下层如何实现，只需知道接口 效率低：一个系统调用要穿透多层，每层都做参数检查与传递，累积开销大
易于替换某一层的实现 分层过细反而增加复杂度

🔎 经典的"循环依赖"难题：
虚拟内存层需要用磁盘驱动来做换页 → 磁盘驱动层应该在虚存层之下；
但磁盘驱动的缓冲区又想使用虚拟内存 → 虚存层又应在其下。这就无法分层了。

因此纯分层 OS 在实践中很少见。真正成功的分层案例是 网络协议栈（TCP/IP 五层模型） 和 THE 系统（Dijkstra，1968）——后者是分层思想的鼻祖。

现代趋势：层数变少但更粗（宏内核 + 少量抽象层），在效率与结构之间折中。

十六、微内核（Microkernel）

16.1 核心思想

把尽可能多的东西从内核移到用户空间。

  • Mach 是微内核的代表。
  • macOS 的内核（Darwin）部分基于 Mach。
  • 用户模块之间通过消息传递（message passing） 通信。

优点 (Benefits) 缺点 (Detriments)

🔎 为什么微内核慢？
宏内核中，应用调 read() → 陷入内核 → 文件系统函数调用 → 返回，共 2 次模式切换。
微内核中，应用 → 消息发给内核 → 内核转发给文件系统服务器 → 文件系统再发消息给磁盘驱动服务器 → 层层返回，可能需要 8 次以上模式切换 + 多次数据拷贝。

历史八卦：1992 年 Tanenbaum（MINIX，微内核）与 Linus Torvalds（Linux，宏内核）就此展开著名论战。Tanenbaum 说"Linux 是过时的设计"，Linus 说"理论优雅比不上能跑得快"。结果两者都对：Linux 赢得了通用计算，而微内核赢得了高可靠领域。

微内核的现实胜利：

  • QNX：汽车电子、核电站控制。
  • L4 / seL4：seL4 是世界上第一个经过形式化验证（数学证明无 bug）的 OS 内核，用于航空航天与军用。
  • Google Fuchsia 的 Zircon 内核。
  • 手机基带处理器普遍跑 L4。

十七、模块（Modules）

许多现代 OS 实现可装载内核模块（LKM, Loadable Kernel Modules）：

特征 说明
采用面向对象的方法 封装 + 已知接口
每个核心组件相互独立 文件系统、驱动、网络协议各成一块

分层 微内核 模块

十八、混合系统（Hybrid Systems）

⭐ 核心结论：大多数现代操作系统都不是单一的纯粹模型。 混合方式组合多种方法，以同时满足性能、安全、可用性需求。

系统 混合方式
Linux / Solaris 内核在内核地址空间 → 属宏内核；加上模块化以动态装入功能

🔎 Windows 的"子系统人格"：早期 NT 通过用户态子系统同时支持 Win32、OS/2、POSIX 三套 API，用户程序像与不同 OS 对话。现代体现是 WSL1（在 NT 内核上翻译 Linux 系统调用）。不过 WSL2 已改为跑真正的 Linux 内核虚拟机。

21.2 构建 Linux 的具体步骤 ⭐

步骤 命令 说明

二十二、操作系统调试（OS Debugging）

22.1 概念

调试 = 发现并修复错误（bug），同时也包括性能调优（performance tuning）。

手段 说明
日志文件（log files） OS 生成，包含错误信息

⭐ 考点：core dump vs crash dump

  • core dump = 用户进程崩溃 = 进程内存
  • crash dump = 内核/系统崩溃 = 内核内存（Windows 上就是"蓝屏"时写的 MEMORY.DMP）

22.2 Kernighan 定律 ⭐

“调试的难度是最初写代码的两倍。因此，如果你写代码时用尽了聪明才智，那么按定义，你就不够聪明去调试它。”
——Brian Kernighan

启示：写内核代码要追求清晰而非炫技。过度优化和"聪明"的技巧会让日后（尤其是别人）无法维护。这也呼应了前面的"系统目标：易于设计、实现、维护"。

🔎 eBPF 是什么？为什么革命性？
eBPF 允许把一段经过验证器安全检查的小程序装入运行中的内核，挂到内核任意探测点上，安全地采集数据——无需修改内核源码、无需加载模块、无需重启。

  • 安全：验证器保证程序必然终止（无无限循环）、不越界访问，因此不会让内核崩溃。
  • 高效：JIT 编译成本地机器码，开销极低，可用于生产环境。
  • 通用：如今已远超观测领域——网络（Cilium 的 XDP 高速转发）、安全（Falco 运行时检测）、负载均衡（Facebook Katran）都基于 eBPF。

有人称 eBPF 是"Linux 内核里的 JavaScript"——它让内核变得可编程，某种意义上实现了微内核追求的可扩展性，却不牺牲宏内核的性能。这可以看作本章"OS 结构演进"的一个当代结局。

二十六、全章结构总览

26.1 五种结构横向对比 ⭐（必考）

结构 核心思想 代表系统 优点 缺点
简单 / 无结构 功能不分层，接口与实现混杂 MS-DOS 小、快 无保护，易崩溃
宏内核 (Monolithic) 所有功能在一个内核地址空间 传统 UNIX、Linux 性能高，函数直接调用 庞大难维护；一处出错全盘崩

微内核 (Microkernel) 内核只留 IPC/内存/调度，其余移到用户态 Mach、QNX、L4 易扩展、易移植、可靠、安全 消息传递性能开销大

混合 (Hybrid) 组合以上多种 Windows、macOS、Linux 平衡性能/安全/可用性 结构复杂
