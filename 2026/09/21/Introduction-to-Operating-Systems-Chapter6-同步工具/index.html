同步工具（Synchronization Tools）

一、背景

多个进程可以并发执行，并且可能在任何时刻被中断，导致某段操作只完成了一部分。当多个进程并发访问共享数据时，就可能出现数据不一致。因此需要某种机制，保证相互协作的进程有序执行。

第4章的有界缓冲区（Bounded Buffer）问题已经展示过这种情况：生产者和消费者同时更新共享的 counter，引发了竞争条件。

二、竞争条件（Race Condition）

定义：多个进程并发访问和操作同一共享数据，最终结果取决于访问发生的具体顺序。

例子：fork() 分配 PID（图1）

进程 P0 和 P1 同时调用 fork() 创建子进程，两者都要读取内核变量 next_available_pid（下一个可用的进程号）。

两个进程都在变量更新之前读到了 2615，结果同一个 PID 被分配给了两个不同的进程。

结论：必须有机制阻止 P0 和 P1 同时访问 next_available_pid。

三、临界区问题（Critical-Section Problem）

1. 基本概念

设系统中有 n 个进程 {P0, P1, …, Pn-1}。每个进程都有一段**临界区（critical section）**代码，在这段代码里进程可能修改公共变量、更新表格或写文件。核心要求是：一个进程在临界区内执行时，其他进程都不能进入各自的临界区。

临界区问题就是要设计一个协议来实现这一点。

2. 进程的一般结构

3. 解决方案必须满足的三个条件 ⭐

条件 含义
互斥（Mutual Exclusion） 如果 Pi 在临界区内执行，其他进程都不能进入临界区
前进（Progress） 如果临界区空闲，且有进程想进入，那么选择下一个进入者的决定不能被无限期推迟。只有不在剩余区的进程才能参与这个决定
有限等待（Bounded Waiting） 一个进程提出进入请求后、请求被批准前，其他进程进入临界区的次数必须有上限，避免饥饿

前提假设：每个进程都以非零速度执行，但对 n 个进程之间的相对速度不作任何假设。

四、基于中断的方案

在进入区关中断，在退出区开中断。这种方案存在以下问题：

  1. 临界区很长怎么办？ 如果临界区代码要运行一小时，这段时间内系统无法响应中断，比如时钟和 I/O。
  2. 饥饿：有些进程可能永远进不了临界区。
  3. 多 CPU 下失效：关中断只对当前 CPU 有效，其他 CPU 上的进程仍然可以访问共享数据。

五、软件方案 1：严格轮换

适用于两个进程，前提是 load/store 指令是原子的。两个进程共享一个变量 int turn;，表示轮到谁进入临界区。

正确性分析：

  • 互斥：满足。 Pi 只有在 turn == i 时才能进入，而 turn 不可能同时等于 0 和 1。
  • 前进：不满足。 两个进程必须严格交替进入。假设 turn == j，但 Pj 在剩余区里不想进入，那么 Pi 即使临界区空闲也进不去，会被一个不参与竞争的进程阻塞。
  • 有限等待：满足。 由于严格交替，最多等待对方进入一次。

六、Peterson 解法 ⭐

同样适用于两个进程，前提是 load/store 指令是原子的。两个进程共享两个变量：

  • int turn;：表示轮到谁进入临界区
  • boolean flag[2];：flag[i] = true 表示 Pi 准备好进入临界区

正确性（三个条件都可证明满足）：

  1. 互斥：Pi 进入临界区的条件是 flag[j] == false 或 turn == i。如果两者同时想进，turn 只能是一个值，所以只有一个能进入。
  2. 前进：如果对方不想进（flag[j] == false），Pi 可以直接进入，不会被无关进程阻塞。
  3. 有限等待：Pi 最多等待 Pj 进入一次。因为 Pj 下次再申请时会把 turn 设为 i，从而让出机会。

理解要点：flag 表达"我想进"，turn 用来决定"冲突时谁让步"。后写 turn 的一方会让步。

七、Peterson 解法与现代体系结构

1. 为什么会失效？

为了提高性能，处理器和编译器可能重排没有数据依赖关系的指令。

  • 对单线程程序，重排不影响结果。
  • 对多线程程序，重排可能导致不一致或出乎意料的结果。

所以 Peterson 解法适合用来演示算法思想，但在现代体系结构上不保证正确。理解它失效的原因，有助于更好地理解竞争条件。

2. 重排示例

两个线程共享 boolean flag = false; int x = 0;

预期输出是 100。但 flag 和 x 之间没有依赖关系，Thread 2 的两条语句可能被重排为先执行 flag = true 再执行 x = 100，这时输出可能是 0。

3. Peterson 解法中的重排

假设 process0 中 flag[0] = true 和 turn = 1 被重排：

  1. P0 先执行 turn = 1（flag[0] 还没设置）
  2. P1 执行 turn = 0, flag[1] = true，检查发现 flag[0] == false，于是进入 CS
  3. P0 执行 flag[0] = true，检查发现 turn == 0（不等于 1），也进入 CS

结果：两个进程同时处于临界区，互斥被破坏！ 解决办法是使用内存屏障（Memory Barrier）。

八、内存屏障（Memory Barrier）

1. 内存模型

内存模型是计算机体系结构对应用程序做出的内存保证，分为两类：

  • 强有序（Strongly ordered）：一个处理器对内存的修改立即对其他所有处理器可见。
  • 弱有序（Weakly ordered）：一个处理器对内存的修改不一定立即对其他处理器可见。

2. 内存屏障指令

内存屏障是一条强制把内存修改**传播（可见）*给所有其他处理器的指令。执行时，系统保证*屏障之前的所有 load/store 都已完成，之后的 load/store 才会执行。因此即使指令被重排，屏障也能保证之前的 store 已写入内存并对其他处理器可见。

3. 修正后的示例

  • Thread 1：保证 flag 的读取先于 x 的读取。
  • Thread 2：保证对 x 的赋值先于对 flag 的赋值。
  • 结果：一定输出 100。

九、同步的硬件支持

许多系统为实现临界区提供硬件支持。

单处理器可以关中断，让当前代码不被抢占地执行。但这在多处理器上效率太低，使用这种方式的操作系统也难以扩展。

本章介绍的硬件支持形式包括：

  1. 硬件指令（Test-and-Set、Compare-and-Swap）
  2. 原子变量（Atomic variables）

硬件指令是指能够**原子地（不可中断地）**测试并修改一个字的内容，或交换两个字内容的特殊指令。

十、test_and_set 指令 ⭐

它有三个特性：原子执行；返回参数的原值；把参数的新值设为 true。

注：幻灯片中 return rv: 是笔误，应为 return rv;。

使用 test_and_set 的解法

共享布尔变量 lock，初始为 false。

工作原理：lock == false 时，调用返回 false，进程进入临界区，同时 lock 被设为 true。其他进程调用时返回 true，只能继续自旋等待。

它能解决临界区问题吗？

  • 互斥：✅ 满足，因为指令是原子的，只有一个进程能拿到 false。
  • 前进：✅ 满足，锁空闲时总有进程能进入。
  • 有限等待：❌ 不满足。释放锁后哪个进程抢到是随机的，某个进程可能一直抢不到，产生饥饿。

十一、compare_and_swap 指令（CAS）⭐

它有三个特性：原子执行；返回 value 的原值；只有当 \*value == expected 时，才把 value 设为 new_value，也就是说只在满足条件时才交换。

使用 CAS 的解法

共享整数 lock，初始为 0。

工作原理：第一个调用 CAS 的进程发现 lock == 0，把它设为 1，返回 0，于是进入临界区。其他进程得到的返回值是 1，只能自旋等待。

它能解决临界区问题吗？ 与 test_and_set 相同：满足互斥和前进，但不满足有限等待。

十二、满足有限等待的 CAS 算法 ⭐

共享数据为 boolean waiting[n];（初始全为 false）和 int lock;（初始为 0）。

进入临界区的两种方式：

  1. key == 0：CAS 成功，Pi 自己抢到了锁。
  2. waiting[i] == false：上一个离开临界区的进程直接把进入权交给了 Pi。这时锁不释放，而是"传递"下去。

三个条件分析：

  • 互斥：只有第一个执行 CAS 的进程能得到 key == 0，其他进程只能等别人把 waiting 设为 false，而每次退出最多交接给一个进程。
  • 前进：退出的进程要么释放锁（lock = 0），要么让一个等待进程进入，不会让临界区空闲却无人能进。
  • 有限等待：退出时按循环顺序 (i+1, i+2, …, n-1, 0, …, i-1) 扫描等待者，所以任何等待的进程最多等待 n−1 轮就能进入临界区。

十三、各方案对比总结

方案 互斥 前进 有限等待 主要问题
关中断 单CPU ✅ — ❌ 多CPU无效；临界区长时影响系统
严格轮换（turn） ✅ ❌ ✅ 必须交替进入
Peterson 解法 ✅ ✅ ✅ 仅限两进程；现代架构需内存屏障
test_and_set 锁 ✅ ✅ ❌ 可能饥饿；忙等
compare_and_swap 锁 ✅ ✅ ❌ 可能饥饿；忙等
有限等待 CAS ✅ ✅ ✅ 代码较复杂；仍是忙等

十四、原子变量（Atomic Variables）

1. 基本概念

像 compare-and-swap 这样的硬件指令，通常被当作构建其他同步工具的基础组件。原子变量就是其中之一：它为整数、布尔值等基本数据类型提供原子的（不可中断的）更新操作。

例如，设 sequence 是一个原子变量，increment() 是作用于它的操作。执行 increment(&sequence); 可以保证 sequence 的自增不会被打断。

2. 用 CAS 实现 increment()（图1）⭐

执行过程：

  1. 先把 *v 的当前值读到 temp。

  2. 调用

    • 如果 *v 仍等于 temp，说明期间没有其他线程修改过它，于是写入 temp+1。CAS 返回原值 temp，循环条件为假，更新成功并退出。
    • 如果 *v 已被其他线程改掉，CAS 不做交换并返回新值，这个值不等于 temp，于是重新读取并重试。

理解要点：这是典型的**"读取 → 比较 → 失败则重试"模式，也叫乐观并发**。它不加锁，而是靠冲突时重试来保证正确。

局限：原子变量只能保证单个变量更新的原子性，不能解决所有竞争条件，例如需要同时更新多个变量的情况。

十六、信号量（Semaphore）⭐⭐

1. 定义

信号量是比互斥锁更强大、更灵活的同步工具。信号量 S 是一个整型变量，除初始化外，只能通过两个**不可分割（原子）**的操作访问：wait() 和 signal()，它们最初分别叫 P() 和 V()（源自荷兰语）。

对 S 的检查和修改（S <= 0 与 S--）必须不可中断地完成。

2. 信号量的类型

  • 计数信号量（Counting semaphore）：取值范围不受限制，常用于管理有多个实例的资源，初值等于可用资源数。
  • 二值信号量（Binary semaphore）：取值只能是 0 或 1，作用等同于互斥锁。

计数信号量也可以用二值信号量来实现。

3. 信号量的用法 ⭐

用法一：解决临界区问题（互斥）

用法二：控制执行顺序（同步）

要求：P1 中的语句 S1 必须在 P2 中的语句 S2 之前执行。

由于 synch 初值为 0，P2 必须等到 P1 执行完 S1 并调用 signal(synch) 后才能执行 S2。

记忆口诀：互斥初值为 1，同步（前驱关系）初值为 0，资源计数初值为资源数。

4. 信号量的实现问题

必须保证不能有两个进程同时对同一个信号量执行 wait() 和 signal()。这样，信号量的实现本身又变成了一个临界区问题：wait 和 signal 的代码要放在临界区中。

这时在实现代码中仍可能出现忙等待，但由于实现代码很短，如果临界区很少被占用，忙等待也很少。然而，应用程序可能在临界区里花费很长时间，所以用忙等待实现信号量不是好方案。

5. 无忙等待的信号量实现 ⭐⭐

思路：让每个信号量关联一个等待队列，进程等不到资源时阻塞自己，而不是自旋。

它依赖两个由操作系统提供的基本操作：

  • block()：把调用该操作的进程放入相应的等待队列，进程状态由运行态变为等待态。
  • wakeup(P)：从等待队列中移出进程 P，把它放入就绪队列。

要点理解：

  • 与忙等待版本不同，这里先减后判断，所以 value 可以为负数。
  • 当 value 为负时，其绝对值等于正在等待该信号量的进程数。
  • signal 中的条件是 value <= 0：自增后如果仍 ≤ 0，说明原来是负数，队列中一定有等待的进程。
  • 等待队列可以采用 FIFO 策略，以保证有限等待。

6. 信号量的使用问题

信号量操作如果使用不当，会导致严重错误，而且难以发现：

错误用法 后果
signal(mutex) … wait(mutex)（顺序颠倒） 多个进程可以同时进入临界区，破坏互斥
wait(mutex) … wait(mutex)（把 signal 写成 wait） 进程会永久阻塞，造成死锁
遗漏 wait(mutex) 和/或 signal(mutex) 破坏互斥，或导致永久阻塞

这些问题促使人们设计了更高层次的同步结构：管程。

十七、管程（Monitors）⭐⭐

1. 定义

管程是一种高层抽象，为进程同步提供了方便而有效的机制。它具有三个特点：

  • 它是一种抽象数据类型（ADT），内部变量只能被管程内部的过程访问。
  • 任一时刻管程内只能有一个进程处于活动状态，这种互斥由管程自动保证，程序员无需显式编写。
  • 程序员只需关注同步逻辑，降低了出错的可能性。

十八、条件变量（Condition Variables）⭐⭐

1. 为什么需要条件变量

仅靠管程的互斥还不够。有时进程进入管程后，发现某个条件不满足（比如缓冲区为空），需要等待。条件变量就提供了这种"在管程内等待某个条件"的能力。

2. 定义与操作

条件变量只允许两种操作：

  • x.wait()：调用该操作的进程被挂起，直到另一个进程调用 x.signal()。
  • x.signal()：恢复一个（如果有的话）调用过 x.wait() 而被挂起的进程。如果没有进程在 x 上等待，则该操作不起任何作用。

3. 条件变量的 signal 与信号量的 signal 的区别 ⭐

信号量 signal(S) 条件变量 x.signal()
无进程等待时 S++，状态会被记住，影响之后的 wait 没有任何效果，信号"丢失"
是否有值 有整数值 没有值，只有等待队列

4. 带条件变量的管程（图4）

在管程的共享数据区中，每个条件变量（x、y）都有自己的等待队列。在 x 上调用 wait() 的进程进入 x 的队列，在 y 上调用的进入 y 的队列。这些队列与外部的入口队列是分开的。

5. signal 之后谁运行？

假设进程 P 调用 x.signal()，唤醒了在 x 上等待的进程 Q。为保证管程内只有一个活动进程，P 和 Q 不能同时运行，有两种策略：

  • Signal and wait：P 等待，直到 Q 离开管程或等待另一个条件。
  • Signal and continue：Q 等待，直到 P 离开管程或等待另一个条件。

下文基于信号量的实现采用的是 signal and wait 策略。

6. 条件变量使用示例

要求 P1 的 S1 在 P2 的 S2 之前执行。创建一个管程，含过程 F1、F2，分别由 P1、P2 调用；使用一个条件变量 x 和一个布尔变量 done（初值 false）。

为什么需要 done 变量？ 因为条件变量的 signal 不会被记住。如果 P1 先执行完 x.signal()，而此时 P2 还没调用 x.wait()，这个信号就丢失了。P2 之后再 wait 就会永远阻塞。所以必须用 done 记录"S1 已完成"这个状态。

注：幻灯片中写的"condition variable x initialized to 0"不太严谨。条件变量本身没有值，真正需要初始化的是 done = false。

3. 管程也不能完全防止误用

管程只保证管程内部的正确性，并不能保证进程按正确顺序调用管程操作。以下误用仍可能发生：

  • release() … acquire()：顺序颠倒
  • acquire() … acquire()：重复获取，导致自己被阻塞
  • 遗漏 acquire() 和/或 release()

二十一、活性（Liveness）⭐⭐

1. 定义

进程在尝试获取互斥锁、信号量等同步工具时，可能要无限期地等待。这违反了本章开头提出的前进和有限等待条件。

活性（Liveness）*指系统必须满足的一组性质，用来*保证进程能够向前推进。无限期等待就是一种活性失效（liveness failure）**。

2. 死锁（Deadlock）⭐

定义：两个或多个进程无限期地等待一个事件，而这个事件只能由这些等待进程中的某一个引发。

示例：S 和 Q 是两个初值为 1 的信号量。

死锁过程：

  1. P0 执行 wait(S)，得到 S；P1 执行 wait(Q)，得到 Q。
  2. P0 执行 wait(Q)，必须等 P1 执行 signal(Q)。
  3. P1 执行 wait(S)，必须等 P0 执行 signal(S)。
  4. 双方都在等对方释放资源，这两个 signal() 永远不会执行，于是 P0 和 P1 死锁。

根本原因：两个进程以相反的顺序申请资源，形成了循环等待。一种简单的预防方法是让所有进程按相同的顺序申请资源。（死锁会在第8章详细讨论。）

3. 饥饿（Starvation）

定义：无限期阻塞，也就是某个进程可能永远无法从它所挂起的信号量队列中被移出。

例如，如果信号量等待队列按 **LIFO（后进先出）**顺序唤醒，最早进入队列的进程可能一直得不到唤醒。

死锁与饥饿的区别：死锁是一组进程互相等待，全体都无法推进；饥饿是某个进程一直得不到机会，而其他进程仍在正常运行。

4. 优先级反转（Priority Inversion）⭐

定义：一种调度问题，低优先级进程持有高优先级进程所需的锁，导致高优先级进程被迫等待。

典型场景：设三个进程的优先级为 L < M < H。

  1. L 持有资源 R 的锁。
  2. H 请求 R，只能等待 L 释放。
  3. 此时 M 就绪，由于 M 优先级高于 L，M 抢占了 L。
  4. 结果：一个与 R 无关的中优先级进程 M，间接地让高优先级进程 H 等待了更长时间。优先级关系实际上被"反转"了。

解决方法：优先级继承协议（Priority-inheritance protocol）

所有正在访问高优先级进程所需资源的进程，临时继承该高优先级，直到用完资源为止。用完后恢复原来的优先级。

在上例中，L 会临时继承 H 的优先级，所以 M 无法抢占 L。L 用完 R 后恢复原优先级，H 随即获得 R 并运行。

著名实例：1997 年 NASA 火星探路者号（Mars Pathfinder）就因为优先级反转导致系统反复重启，后来通过启用优先级继承得以解决。
