同步问题实例

本章先讲三个经典同步问题（有界缓冲区、读者-写者、哲学家就餐），再讲操作系统（Windows、Linux）和编程接口（POSIX）提供的同步工具。经典问题常用来检验新提出的同步机制是否有效。

一、有界缓冲区问题（Bounded-Buffer / 生产者-消费者）

共享数据

信号量 初值 含义
mutex 1 互斥访问缓冲区
full 0 已装满的槽位数
empty n 空闲槽位数

缓冲区共有 n 个槽位，每个放一个数据项。

生产者与消费者

要点

两者结构对称：生产者消耗 empty、增加 full，消费者反过来。先 wait 资源信号量（empty/full），再 wait mutex，顺序不能颠倒。 如果先拿 mutex 再等 empty，缓冲区满时生产者会持锁阻塞，消费者进不来，形成死锁。

二、读者-写者问题（Readers-Writers）

问题描述

多个并发进程共享一个数据集。读者只读不改，写者可读可写。要求允许多个读者同时读，但写者必须独占访问。

共享数据

变量 初值 作用
rw_mutex 1 读者与写者、写者与写者之间互斥
mutex 1 保护 read_count 的更新
read_count 0 当前正在读的读者数

写者

读者

核心思想

“第一个进来的读者关门，最后一个离开的读者开门”。中间的读者不需要再碰 rw_mutex，因此可以并发读。

变体与饥饿

第一类读者-写者问题（即上面的解法）是读者优先：只要持续有读者到来，写者可能永远写不了，因此写者会饥饿。第二类读者-写者问题是写者优先：一旦有写者就绪，新到的读者就不许再进入，这时读者可能饥饿。两种都可能导致饥饿，于是又衍生出更多变体。实际系统中常由内核直接提供**读写锁（reader-writer lock）**来解决。

三、哲学家就餐问题（Dining-Philosophers）

问题描述（见图1）

N 位哲学家围坐圆桌，中间一碗米饭，相邻两人之间各放一根筷子（5 人则 5 根）。哲学家在思考和吃饭之间交替，彼此不交流。吃饭时要一根一根地拿起左右两根筷子，两根都拿到才能吃，吃完两根都放下。

以 5 人为例，共享数据是米饭（数据集）和 semaphore chopstick[5]，每个初值为 1。

1. 简单信号量解法

这个算法的问题（课件提问）：可能死锁。 如果 5 位哲学家同时饿了、同时拿起左手筷子，每个人都会永远等待右手那根，已被邻居拿走，谁也吃不上。

常见改进思路有三种：最多只允许 4 人同时上桌；只有左右两根都空闲时才一次性拿起（在临界区内拿）；采用非对称策略，奇数号先拿左再拿右，偶数号先拿右再拿左。

四、Windows 内核同步

在单处理器上，Windows 用中断屏蔽保护全局资源；在多处理器上用自旋锁，而且持有自旋锁的线程不会被抢占。

面向用户态，Windows 提供调度器对象（dispatcher objects），可以充当互斥锁、信号量、事件和定时器。其中事件（event）的作用类似条件变量，定时器在时间到期时通知一个或多个线程。

调度器对象有两种状态：**signaled（有信号）**表示对象可用，线程获取时不会阻塞；**nonsignaled（无信号）**表示对象不可用，线程会阻塞。

五、Linux 同步

在 2.6 版本之前，Linux 内核通过禁用中断来实现短临界区；从 2.6 版本开始，内核完全可抢占。

Linux 提供的工具包括信号量、原子整数、自旋锁，以及信号量和自旋锁各自的读写版本。在单 CPU 系统上，自旋锁被替换为启用/禁用内核抢占（单核上自旋没有意义，因为持锁者不运行就不会释放锁）。

原子变量（见图3）

atomic_t 是原子整数类型，其上的操作不可被打断。

原子操作 效果
atomic_set(&counter, 5); counter = 5
atomic_add(10, &counter); counter = counter + 10
atomic_sub(4, &counter); counter = counter − 4
atomic_inc(&counter); counter = counter + 1
value = atomic_read(&counter); value = 12

按顺序执行后结果为 5 + 10 − 4 + 1 = 12。原子变量适合计数器这类简单场景，比加锁开销小。

七、Java 同步

Java 提供了丰富的同步机制，主要有四类：Java 管程（synchronized）、可重入锁（ReentrantLock）、信号量（Semaphore）**和**条件变量（Condition）。

1. Java 管程（synchronized）

基本规则：

  • 每个 Java 对象都关联一把锁。
  • 如果方法被声明为 synchronized，调用线程必须先拥有该对象的锁才能执行。
  • 如果锁被其他线程占有，调用线程必须等待，直到锁被释放。
  • 线程退出 synchronized 方法时自动释放锁。

入口集（entry set）：试图获取一把不可用的锁的线程会被放入该对象的入口集中排队，等待锁的拥有者（owner）释放锁。

等待集（wait set）：每个对象除入口集外还有一个等待集。线程调用 wait() 时依次发生三件事：

  1. 释放该对象的锁；
  2. 线程状态设为阻塞（blocked）；
  3. 线程被放入该对象的等待集。

notify() 的作用： 线程调用 wait() 通常是在等待某个条件成立。另一个线程调用 notify() 时：

  1. 从等待集中任意选出一个线程 T；
  2. 把 T 从等待集移到入口集；
  3. 把 T 的状态从阻塞改为可运行（runnable）。

之后 T 可以重新竞争锁，拿到锁后再检查它等待的条件是否已经成立。

两个集合的关系：

注意区分：入口集里的线程在等锁，等待集里的线程在等条件。被 notify 的线程并不是立刻运行，而是先回到入口集重新抢锁。

3. 可重入锁（ReentrantLock）

作用类似互斥锁。"可重入"指已经持有锁的线程可以再次获取同一把锁而不会自己把自己锁死（内部计数，加锁几次就要释放几次）。

要点： unlock() 放在 finally 中，保证即使 try 块中抛出异常，锁也一定会被释放，避免锁永远不释放导致其他线程死等。

与 synchronized 相比，ReentrantLock 需要手动加锁/解锁，但更灵活（例如可以创建多个条件变量）。

八、其他同步方法（Alternative Approaches）

随着多核普及，锁和信号量在可扩展性、易用性上的问题越来越明显（容易死锁、难以组合、锁粒度难把握），于是出现了以下替代方案：事务内存、OpenMP、函数式编程语言。

1. 事务内存（Transactional Memory）

假设函数 update() 必须原子地执行。

传统做法：用互斥锁

事务内存做法：

概念： 内存事务是一组原子执行的内存读写操作。通过 atomic{S} 语法，保证 S 中的语句作为一个整体原子执行。

优势： 由系统（而不是程序员）负责保证原子性。程序员不用手动管理锁，不会因为锁而死锁；系统可以检测到多个事务中哪些操作可以并发执行（例如多个只读访问），并发度更高。（它借鉴了数据库事务的思想：要么全部完成，要么全部不做。）

2. OpenMP（见图12）

OpenMP 是一组支持并行编程的编译器指令和 API。

要点： #pragma omp critical 指令内的代码被当作临界区，原子地执行，同一时刻只有一个线程能进入。优点是使用简单，不需要手动创建和管理锁，由编译器和运行库自动处理。不过它本质上仍类似互斥锁，程序员仍需自己找出可能存在竞争条件的代码段，并且使用不当也可能出现死锁。

3. 函数式编程语言（Functional Programming Languages）

函数式语言与过程式语言（C、Java 等）范式不同：它们不维护状态，变量是不可变的（immutable），一旦赋值就不能再改变。

为什么能帮助同步： 数据竞争的根源是"多个线程同时修改共享的可变数据"。如果数据根本不可变，就不存在数据竞争，也就不需要锁。因此，人们对 Erlang、Scala 等函数式语言处理数据竞争的方式越来越感兴趣。
