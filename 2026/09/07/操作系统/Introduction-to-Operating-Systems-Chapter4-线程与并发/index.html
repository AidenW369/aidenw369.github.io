线程与并发（Threads & Concurrency）

一、概述：为什么需要线程

1.1 动机

现代应用几乎都是多线程的。一个进程内部往往同时存在多个逻辑上独立的任务：

  • 刷新界面显示
  • 后台拉取数据
  • 拼写检查
  • 响应网络请求

如果为每个任务都创建一个进程，代价太高：进程创建是"重量级"的（要复制/新建地址空间、页表、文件描述符表等）；而线程创建是"轻量级"的，只需分配一套执行上下文。内核本身通常也是多线程的。

1.2 线程 vs 进程（对应截图1）

单线程进程与多线程进程的关键区别在于哪些资源共享、哪些资源私有：

资源 单线程进程 多线程进程
code（代码段） 独有 所有线程共享
data（全局/静态数据） 独有 所有线程共享
files（打开文件表） 独有 所有线程共享
registers（寄存器） 一份 每线程一份
stack（栈） 一份 每线程一份
PC（程序计数器） 一份 每线程一份

记忆口诀：线程私有的是"执行状态"（寄存器 + 栈 + PC），共享的是"资源"（代码 + 数据 + 文件）。

线程是 CPU 调度的基本单位，进程是 资源分配的基本单位。

补充拓展：

  • 线程私有的还有：线程 ID（TID）、信号掩码、errno、线程局部存储（TLS，如 C 的 __thread、Java 的 ThreadLocal）。
  • 因为堆和全局区共享，多线程才会出现竞态条件（race condition），需要第5、6章的同步机制。
  • 每个线程栈默认大小不小（Linux 通常 8MB 虚拟地址空间），所以"线程无限开"仍然不现实。

1.3 多线程服务器架构（对应截图2）

典型流程：

  1. 客户端向服务器发送 request
  2. 服务器 创建新线程 来处理该请求
  3. 服务器 立即恢复监听，等待更多客户端请求

好处：主线程永远不被单个耗时请求阻塞，吞吐量和响应性大幅提升。

补充拓展：这种"一请求一线程"（thread-per-request）模型在高并发下会因线程创建开销和上下文切换而退化，实际工程中常改为线程池（见后文隐式线程）或事件驱动 + I/O 多路复用（如 Nginx 的 epoll 模型）。

1.4 多线程的四大好处

好处 含义
Responsiveness（响应性） 部分线程阻塞时程序仍可继续运行，对 UI 尤其重要
Resource Sharing（资源共享） 线程天然共享进程资源，比共享内存或消息传递更简单
Economy（经济性） 创建线程比创建进程便宜；线程切换开销低于进程上下文切换
Scalability（可伸缩性） 可利用多核架构真正并行

为什么线程切换比进程切换便宜？因为同进程内线程切换不需要切换地址空间，无需刷新 TLB（页表缓存），只需保存/恢复寄存器和栈指针。

二、多核编程（Multicore Programming）

2.1 五大挑战

  1. Dividing activities（划分任务）——找出可并发执行的部分
  2. Balance（负载均衡）——各核工作量要均匀，否则木桶效应
  3. Data splitting（数据分割）——数据如何切分给各核
  4. Data dependency（数据依赖）——存在依赖时必须同步
  5. Testing and debugging（测试与调试）——执行路径非确定，bug 难以复现

2.2 并发 vs 并行（对应截图3）⭐ 高频考点

概念 定义 硬件要求
Concurrency（并发） 多个任务都在取得进展 单核即可（靠调度器时间片轮转）
Parallelism（并行） 系统能同时执行多个任务 必须多核/多处理器
  • 单核并发：T₁ T₂ T₃ T₄ T₁ T₂ T₃ T₄ … 在时间轴上交错，任一时刻只有一个线程真正在跑。
  • 多核并行：core 1 跑 T₁ T₃ T₁ T₃…，core 2 跑 T₂ T₄ T₂ T₄…，同一时刻有两个线程真正在跑。

关系：并行一定是并发，但并发不一定并行。
Rob Pike 的名言可以帮助理解：并发是"同时处理很多事"（结构上的），并行是"同时做很多事"（执行上的）。

2.3 两种并行类型（对应截图4）

类型 做法 特点 例子
Data parallelism（数据并行） 把同一份数据的不同子集分发到多个核，每个核执行相同操作 数据切分，操作相同 对一个 100 万元素数组求和，每核算 25 万个
Task parallelism（任务并行） 把不同的线程/任务分发到多个核，每个线程执行不同操作 操作切分，数据可能相同 一个核算平均值、一个核算最大值、一个核算标准差

补充拓展：

  • 实际大型程序通常是两者的混合（hybrid）。
  • 数据并行天然更容易扩展（数据变多就多切几块），是 GPU / SIMD（如 SSE、AVX、CUDA）的基础模型。

三、Amdahl 定律（对应截图5、6）⭐ 必考

3.1 公式

​ speedup≤1S+1−SN

  • S：程序中串行部分所占比例
  • 1 − S：可并行部分比例
  • N：处理核心数

3.2 课件例题验算

应用 75% 并行 / 25% 串行，从 1 核到 2 核：

​ speedup≤10.25+0.752=10.25+0.375=10.625=1.6

✅ 与课件的"1.6 倍"一致。

3.3 极限行为

当 N→∞ 时，$\frac{1-S}{N} \to 0 $，因此：

​ speedup→1S

即加速比存在上限，完全由串行部分决定。

S（串行比例） 理论最大加速比
0.50 2×
0.10 10×
0.05 20×
0.01 100×

这正是截图6曲线图所展示的：红线是理想线性加速；S = 0.05（绿）、S = 0.10（蓝）都逐渐弯曲偏离理想线；S = 0.50（粉）几乎立刻压平在 2 附近，加再多核也没用。

3.4 核心结论

串行部分对"增加核心所带来的性能提升"具有不成比例的（disproportionate）压制作用。

即使只有 5% 的串行代码，也会把加速比封顶在 20 倍。因此优化的重点应该是减小 S，而不是一味加核。

3.5 课件的开放问题：“这个定律考虑了当代多核系统吗？”

补充拓展——Amdahl 定律的局限与修正：

  1. Gustafson 定律（Gustafson’s Law）：Amdahl 假设问题规模固定。但现实中核多了，人们往往是去解更大的问题（更高分辨率、更大数据集）。此时串行部分占比会随规模增长而下降，加速比可近似线性增长：
    speedup=N−S⋅(N−1) 这被称为 scaled speedup（可扩展加速比）。
  2. 未计入的现实因素：Amdahl 定律忽略了缓存效应、内存带宽竞争、NUMA 访存差异、同步与通信开销、线程创建代价。有时多核会因为缓存总量变大产生"超线性加速"，有时又因为总线争用远达不到理论值。

四、用户线程与内核线程（对应截图7）

User Threads（用户线程） Kernel Threads（内核线程）
管理者 用户级线程库（user-level library） 操作系统内核
内核是否感知 否 是
创建/切换开销 极小（无需系统调用） 较大（需陷入内核）
能否被内核调度到多核 不能（内核看不见） 能

三大主流线程库：

  • POSIX Pthreads（可实现为用户级或内核级）
  • Windows threads
  • Java threads（依赖底层宿主 OS 的线程实现）

支持内核线程的系统：几乎所有通用 OS —— Windows、Linux、macOS、iOS、Android。

关键点：用户线程最终必须映射到某个内核线程上才能真正获得 CPU 时间。这个映射关系就是下面的"多线程模型"。

五、多线程模型（Multithreading Models）

5.1 Many-to-One（多对一，M:1）（对应截图8）

  • 多个用户级线程 → 1 个内核线程
  • ❌ 一个线程阻塞会导致所有线程阻塞（因为内核只看到一个可调度实体，它一阻塞整体就停）
  • ❌ 无法在多核上并行，因为同一时刻只有一个线程能进入内核
  • ✅ 线程创建和切换极快（纯用户态操作）
  • 现在很少有系统使用
  • 例子：Solaris Green Threads、GNU Portable Threads

5.2 One-to-One（一对一，1:1）（对应截图9）

  • 每个用户级线程 → 对应一个内核线程
  • 创建一个用户线程就会创建一个内核线程
  • ✅ 并发性比 M:1 强，可真正并行，单个线程阻塞不影响其他线程
  • ❌ 内核线程数量有限、创建有开销，因此每进程线程数常受限制
  • 例子：Windows、Linux

这是当今的事实标准。Linux 的 NPTL（Native POSIX Thread Library）就是 1:1 模型，pthread_create() 底层调用 clone()。

5.3 Many-to-Many（多对多，M:N）（对应截图10）

  • 多个用户线程 → 多个（数量 ≤ 用户线程数）内核线程
  • ✅ 允许 OS 创建"足够数量"的内核线程，兼顾并发性与开销
  • ✅ 开发者可以随意创建大量用户线程，而不担心内核资源耗尽
  • 实现复杂（需要用户态调度器 + 内核协作）
  • 例子：Windows 的 ThreadFiber 包；其他情况下不太常见

5.4 Two-level Model（两级模型）（对应截图11）

  • 与 M:N 类似，但额外允许某个用户线程被"绑定（bound）"到一个专属内核线程上
  • 好处：对延迟敏感或需要保证不被饿死的关键线程，可以享受 1:1 的确定性；其余线程仍走 M:N 的高效路径
  • 历史例子：早期 Solaris（Solaris 9 之前）、IRIX、HP-UX、Tru64 UNIX

5.5 四种模型对比总结

模型 映射 并行能力 阻塞影响 开销 代表
Many-to-One M:1 ❌ 无 一阻全阻 最低 Green Threads
One-to-One 1:1 ✅ 强 互不影响 较高 Windows、Linux
Many-to-Many M:N ✅ 强 互不影响 中等 Windows ThreadFiber
Two-level M:N + 绑定 ✅ 强 互不影响 中等 早期 Solaris

补充拓展 —— M:N 的"复活"：
虽然课件说 M:N “不太常见”，但它在现代语言运行时中以协程/绿色线程的形式大规模回归：

  • Go 的 goroutine：GMP 调度器，是典型的 M:N，可以轻松开百万级 goroutine。
  • Java 21 的虚拟线程（Virtual Threads, Project Loom）：把大量虚拟线程复用到少量平台线程上。
  • Rust 的 tokio、Kotlin 协程、Python asyncio：思路一致。

它们避开了当年 M:N 失败的坑（主要是阻塞式系统调用的处理），因为运行时把阻塞 I/O 都改写成了异步方式。

六、线程库（Thread Libraries）

6.1 什么是线程库

线程库（thread library） 为程序员提供创建和管理线程的 API，屏蔽底层细节。

两种实现方式：

实现方式 特点
完全在用户空间实现（library entirely in user space） 库的代码和数据结构都在用户空间；调用库函数只是本地函数调用，不涉及系统调用，开销小
内核级库，由 OS 支持（kernel-level library） 库的代码和数据结构位于内核空间；调用 API 会触发系统调用（陷入内核），开销大但内核可感知调度

这与第五节的"用户线程 / 内核线程"直接对应：用户空间库通常对应 M:1 或 M:N 模型；内核级库通常对应 1:1 模型。

三大主流线程库：POSIX Pthreads、Windows Threads、Java Threads。

七、Pthreads

7.1 基本概念

  • POSIX 标准 IEEE 1003.1c 定义的线程创建与同步 API
  • 可以实现为用户级，也可以实现为内核级（标准不强制）
  • ⭐ 它是"规范（specification）“而不是"实现（implementation）”
  • 标准只规定线程库的行为（函数签名、语义、返回值）
  • 具体怎么实现由各家库开发者决定
  • 常见于 UNIX 系统：Linux、macOS（Solaris、FreeBSD 等亦然）

补充：Linux 上的实现是 NPTL（Native POSIX Thread Library），采用 1:1 模型，pthread_create() 底层调用 clone() 系统调用。编译时需要链接：gcc prog.c -lpthread。

要点：

九、Java 线程

9.1 基本机制

  • Java 线程由 JVM 管理
  • 通常用底层 OS 提供的线程模型来实现（在 Linux/Windows 上即 1:1，映射到原生内核线程）
  • 两种创建方式：
  1. 继承 Thread 类（extends Thread）
  2. 实现 Runnable 接口（implements Runnable）
  • ⭐ 标准做法是实现 Runnable 接口

为什么推荐 Runnable 而不是继承 Thread？

  1. Java 是单继承的，继承了 Thread 就不能再继承别的类；实现接口不占用继承名额。
  2. 职责分离：Runnable 表达的是"要做的任务"，Thread 表达的是"执行任务的载体"，二者解耦。
  3. 同一个 Runnable 对象可以交给多个线程或线程池复用，而 Thread 对象只能 start() 一次。

十二、隐式线程（Implicit Threading）

12.1 为什么需要隐式线程

随着应用中线程数量不断增长，显式线程（explicit threading） 带来的问题越来越突出：

  • 程序正确性更难保证（竞态、死锁、可见性问题随线程数呈组合爆炸）
  • 线程的创建、销毁、调度、负载均衡全部要手写，代码冗长易错

隐式线程的核心思想：

把线程的创建与管理交给编译器和运行时库，而不是程序员。

程序员只负责标识出"可以并行的任务"，至于开几个线程、哪个线程执行哪个任务、什么时候回收，全部由框架决定。

十三、线程池（Thread Pools）

13.1 基本思路

预先创建若干线程放入"池"中，让它们在池里等待任务到来。

有请求时不新建线程，而是从池中取一个空闲线程执行；任务完成后线程不销毁，回到池中继续等待。

13.2 三大优点 ⭐

  1. 更快：用一个已存在的线程来服务请求，通常比新建线程要快一些（省去了内核创建 TCB、分配栈的开销）。
  2. 限流：可以把应用中的线程总数限制在池的大小之内，防止请求暴增时线程数失控耗尽系统资源。
  3. 解耦：把"要执行的任务"与"创建任务的机制"分离开，从而可以采用不同的执行策略。
  • 例如：任务可以被安排周期性运行（scheduled to run periodically）。

回顾第七节的多线程服务器架构：那里是"一请求一线程"，在高并发下会因线程创建开销和上下文切换崩溃。线程池正是它的工业级修正版。

补充：如何确定池的大小？

  • CPU 密集型任务：线程数 ≈ 核心数（或核心数 + 1）
  • I/O 密集型任务：线程数可远大于核心数，因为线程大部分时间在阻塞等待
  • 经验公式：线程数 = 核心数 × (1 + 等待时间/计算时间)
  • 现代实现（如 GCD、.NET）会动态调整池大小

Windows API 也支持线程池（如 QueueUserWorkItem()、CreateThreadpool() 系列）。

十四、Fork-Join 并行

14.1 基本模型（对应截图3）

多个线程（任务）被 fork（分叉）出去，然后再被 join（合并）回来。

流程：main thread → fork 出多个 task 并行执行 → join 等待全部完成并汇合 → main thread 继续。

注意：这里的 fork 与 UNIX 的 fork() 系统调用不是一回事。UNIX 的 fork() 创建的是新进程；这里的 fork 是创建一个可并行执行的任务（在 Java 中甚至不一定对应一个新线程，而是提交到工作队列）。

14.2 通用算法框架（对应截图4）⭐ 典型的分治（Divide & Conquer）

三个要素：

  1. 阈值判断（threshold）：问题足够小就直接串行求解——避免无限递归和过度切分带来的调度开销
  2. fork：把问题拆成子问题并异步提交
  3. join + combine：等待子结果并归并

14.3 递归展开的任务树（对应截图5）

fork-join 是递归的：每个 task 可以继续 fork 出子 task，形成一棵二叉任务树。

  • 向下（fork）：不断二分，直到叶子节点小于阈值
  • 向上（join）：叶子先算出结果，逐层向上合并，最终汇总到根节点

树的深度决定并行度层次，叶子数约等于最终的并行任务数。

典型适用问题：归并排序、快速排序、数组求和/最大值、矩阵乘法、二叉树遍历、图像分块处理、N 皇后搜索——凡是能"分而治之"的都适合。

十五、OpenMP

15.1 概述（对应截图9）

  • 一组编译制导指令（compiler directives）加上一套 API，支持 C、C++、FORTRAN
  • 面向共享内存环境（shared-memory） 的并行编程
  • 通过标识 parallel regions（并行区域）——即可以并行运行的代码块——来实现并行
  • #pragma omp parallel：创建与核心数相同数量的线程

本质：OpenMP 是编译器层面的隐式线程。程序员只加一行 #pragma 注释，编译器自动生成创建线程、分配工作、同步汇合的代码。如果编译器不支持 OpenMP，#pragma 会被忽略，程序仍能作为串行程序正确运行——这是它极大的优点（增量并行化）。

十七、Grand Central Dispatch（GCD）

17.1 概述

  • Apple 为 macOS 与 iOS 开发的技术
  • 由三部分组成：对 C、C++、Objective-C 语言的扩展 + API + 运行时库
  • 允许开发者标识出并行的代码段
  • 线程的绝大部分细节由 GCD 管理（创建多少线程、何时创建销毁、如何调度，程序员一概不管）

17.3 两类分派队列 ⭐ 高频考点

队列类型 取出规则 说明
serial（串行队列） 按 FIFO 顺序取出，一次只取一个，前一个执行完才取下一个 每个进程默认有一个，称为 main queue（主队列）；程序员可在程序中自行创建额外的串行队列

二十、fork() 与 exec() 的语义

20.1 核心问题

多线程进程调用 fork() 时，是只复制调用它的那个线程，还是复制所有线程？

  • 某些 UNIX 系统提供两个版本的 fork()：
  • 一种只复制调用线程
  • 一种复制进程中的所有线程
  • 选哪个取决于应用行为：
  • 若 fork() 之后立即调用 exec()，复制所有线程毫无意义（马上就被替换掉）→ 用"只复制调用线程"的版本
  • 若子进程 fork() 后不调用 exec()，而是继续作为独立多线程进程运行 → 可能需要复制全部线程

20.2 exec() 的行为

exec() 照常工作：用新程序替换整个进程，包括其所有线程。

补充（POSIX 现实）：现代 POSIX 只保留一种 fork()——只复制调用线程。这带来一个著名陷阱：如果 fork() 时另一个线程正持有锁，子进程中该锁将永远处于锁定状态且无人释放，导致死锁。因此 POSIX 规定：fork() 与 exec() 之间只应调用异步信号安全（async-signal-safe）的函数。pthread_atfork() 可注册回调来缓解此问题。

二十三、线程局部存储（Thread-Local Storage, TLS）

23.1 定义

TLS 允许每个线程拥有自己的一份数据副本。

适用场景：当你无法控制线程的创建过程时特别有用——例如使用线程池时，线程由框架创建复用，你没机会在创建时给每个线程塞私有数据。

二十四、调度器激活（Scheduler Activations）

24.1 要解决的问题

M:M 模型和两级模型都需要在用户线程库与内核之间进行通信，以便维持分配给应用的内核线程数量正确——太少则并行度不足、可能全部阻塞；太多则浪费资源。

24.2 轻量级进程（LWP）

  • 通常在用户线程与内核线程之间引入一个中间数据结构：轻量级进程（lightweight process, LWP）
  • LWP 在用户线程库看来就像一个虚拟处理器（virtual processor），进程可以把用户线程调度到它上面运行
  • 每个 LWP 都关联一个内核线程
  • 核心难题：该创建多少个 LWP？

举例：若一个 CPU 密集型应用运行在单核上，1 个 LWP 足够；但若应用有 5 个可能同时发起阻塞式 I/O 的线程，就需要 5 个 LWP，否则一个阻塞会拖住其他可运行的线程。

24.3 调度器激活的机制 ⭐

Scheduler activations 提供 upcall（向上调用）——一种从内核到线程库中 upcall handler（向上调用处理程序）的通信机制。
这种通信使应用能够维持正确数量的内核线程。

与普通系统调用的方向对比：

机制 方向
系统调用（system call） 用户空间 → 内核（向下）
upcall（向上调用） 内核 → 用户空间线程库（向上）

典型工作流程：

  1. 某个用户线程执行阻塞式系统调用（如读磁盘）
  2. 内核检测到该 LWP 即将阻塞，发起一次 upcall，通知线程库：“你的某个线程要阻塞了”
  3. 线程库的 upcall handler 在另一个 LWP 上运行，把被阻塞线程的状态保存下来，并调度另一个可运行的用户线程到这个新 LWP 上
  4. 当 I/O 完成时，内核再次 upcall 通知线程库该线程可继续运行
  5. 线程库把它标记为可运行，等待调度

效果：应用不会因为一个线程阻塞而浪费并行能力，同时内核线程数量始终与实际需求匹配。

二十五、操作系统实例：Windows 线程

25.1 概览

  • Windows API 是 Windows 应用的主要 API
  • 实现 one-to-one（1:1）映射，内核级线程
  • 每个用户级线程对应一个内核线程

25.2 线程包含的内容

组成 说明
thread id 线程标识符
register set 表示处理器状态的寄存器集合
用户栈与内核栈（分开的两个栈） ⭐ 线程在用户模式运行时用用户栈，在内核模式运行时用内核栈
私有数据存储区 供运行时库和动态链接库（DLL） 使用

⭐ 上下文（context）的定义：寄存器集合、栈、私有存储区 三者合称线程的上下文（context）。这正是线程切换时需要保存/恢复的内容。

为什么要两个栈？ 安全性——内核代码不能信任用户栈（用户可能故意把栈指针指向非法地址）。进入内核态时切换到内核栈，可防止用户破坏内核数据。

二十六、操作系统实例：Linux 线程（对应截图7）

26.1 核心思想

⭐ Linux 把它们称为"任务（tasks）“而不是"线程（threads）”。

在 Linux 内核眼中，进程和线程没有本质区别，都是可调度的 task。区别只在于共享了多少资源。

  • 线程创建通过 clone() 系统调用完成
  • clone() 允许子任务共享父任务（进程）的地址空间
  • 具体共享哪些内容，由标志位（flags） 控制

26.2 clone() 的关键标志

flag 含义
CLONE_FS 共享文件系统信息（当前工作目录、根目录、umask）
CLONE_VM 共享同一内存空间（地址空间）
CLONE_SIGHAND 共享信号处理程序
CLONE_FILES 共享已打开文件的集合

26.3 ⭐ 一个系统调用统一进程与线程

调用方式 效果
clone() 不带任何共享标志 相当于 fork()——创建一个独立进程，所有资源都是副本
clone() 带全部上述标志 创建一个线程——与父任务共享地址空间、文件、信号处理程序
带部分标志 介于两者之间的中间形态（Linux 特有的灵活性）

26.4 task_struct

struct task_struct 指向进程的各个数据结构（这些结构可以是共享的，也可以是独有的）。

关键设计：内核为每个 task 分配一个 task_struct，但 task_struct 内部对内存、文件、信号等资源采用指针引用：

  • 若创建的是线程 → 多个 task_struct 的相应指针指向同一份结构（mm_struct、files_struct 等）
  • 若创建的是进程 → 各指向自己独立的副本

补充：这一设计使 Linux 的线程创建代价极低——只需新建一个 task_struct 并复制若干指针，无需复制页表。pthread_create() 底层正是调用 clone()。此外，Linux 中同一进程的线程共享 TGID（thread group ID），即用户看到的 PID；而每个线程有自己的 PID（内核视角），可通过 gettid() 获取。
