进程（Processes）

一、本章目标

  • 认识进程的组成部分，理解它在操作系统中如何被表示和调度
  • 掌握进程的创建与终止（及对应的系统调用）
  • 对比两种进程间通信（IPC）方式：共享内存 vs 消息传递
  • 会用管道和 POSIX 共享内存编程
  • 理解客户–服务器通信：套接字（socket）与远程过程调用（RPC）

二、进程的概念

进程 = 执行中的程序。单个进程内部的指令按顺序执行，不存在并行执行。

程序 vs 进程

程序（Program） 进程（Process）
性质 被动实体（passive） 主动实体（active）
存放位置 磁盘上的可执行文件 内存中，拥有 PC、寄存器等资源
数量关系 一个程序 可对应多个进程（如多个用户同时运行同一程序）

可执行文件被加载进内存时，程序就变成了进程。启动方式包括：GUI 点击、命令行输入程序名等。

进程的组成部分

部分 内容
text（代码段） 程序指令
data（数据段） 全局变量、静态变量
heap（堆） 运行期动态分配的内存（malloc/new）
stack（栈） 临时数据：函数参数、返回地址、局部变量
当前活动状态 程序计数器 PC、处理器寄存器

三、进程在内存中的布局

对应截图《Process in Memory》与《Memory Layout of a C Program》：

结合 C 代码理解（第2张图）：

代码 所在区域

补充要点：

  • 指针变量 values 本身在栈上，它指向的那 5 个 int 在堆上——这是考试常考的区分点。
  • BSS 段在可执行文件中不占空间，加载时由系统清零，所以未初始化全局变量默认为 0。
  • 栈与堆之间的空白区域是"缓冲带"；两者相撞就是栈溢出/堆耗尽。

四、进程状态

进程执行过程中会不断改变状态：

状态 含义
New（新建） 进程正在被创建
Ready（就绪） 已具备运行条件，等待被分配到 CPU
Running（运行） 指令正在 CPU 上执行
Waiting（等待/阻塞） 等待某事件发生（如 I/O 完成）
Terminated（终止） 执行结束

状态转换图（对应截图3）

五条转换边要记牢：

  1. new → ready：admitted（被接纳）
  2. ready → running：scheduler dispatch（调度器分派）
  3. running → ready：interrupt（时间片用完或被抢占）
  4. running → waiting：发起 I/O 或等待事件
  5. waiting → ready：I/O 或事件完成
  6. running → terminated：exit

⚠️ 注意：没有 waiting → running 这条边——阻塞结束后必须先回到就绪队列排队。同一时刻，一个 CPU 核心上只有一个进程处于 running。

五、进程控制块 PCB（Process Control Block）

又称任务控制块（task control block），是操作系统为每个进程维护的数据结构，进程的"身份证 + 档案"。

对应截图4中的结构：

字段 说明
process state 运行、等待、就绪等
process number（PID） 进程标识符
program counter 下一条要执行的指令地址
CPU registers 所有与该进程相关的寄存器内容
CPU 调度信息 优先级、调度队列指针
内存管理信息 分配给该进程的内存（基址/界限寄存器、页表等）
记账信息 已用 CPU 时间、启动至今的时钟时间、时限
I/O 状态信息 分配的 I/O 设备、打开文件列表

PCB 是上下文切换时保存和恢复的对象，也是内核识别和管理进程的唯一依据。

六、线程（预告，第4章详述）

  • 目前讨论的进程只有单一执行流
  • 若一个进程拥有多个程序计数器，就能同时在多个位置执行 → 这就是线程
  • 需要在 PCB 中为每个线程存储各自的寄存器、程序计数器等细节

八、进程调度

进程调度器（process scheduler） 从可用进程中挑选下一个上 CPU 核心执行的进程。

  • 目标：最大化 CPU 利用率，快速完成进程切换
  • 手段：维护若干调度队列

两类队列（对应截图5）

队列 含义
就绪队列 ready queue 驻留在主存中、已就绪等待执行的所有进程
等待队列 wait queue 等待某个事件（如 I/O）的进程集合

实现方式：队列头保存 head 和 tail 两个指针，把各个 PCB 通过指针串成链表（如 ready queue: PCB₇ → PCB₂；wait queue: PCB₃ → PCB₁₄ → PCB₆）。进程在各队列之间迁移。

调度的整体流程（对应截图6）

进程从 ready queue 被分派到 CPU 后，可能发生四种情况，之后都回到就绪队列：

  1. 发出 I/O 请求 → 进入 I/O 等待队列 → I/O 完成后回到就绪队列
  2. 时间片到期 → 直接回到就绪队列
  3. 创建子进程 → 进入"子进程终止等待队列" → 子进程结束后回到就绪队列（对应 wait()）
  4. 等待中断 → 进入中断等待队列 → 中断发生后回到就绪队列

九、上下文切换（Context Switch）

当 CPU 切换到另一个进程时，系统必须保存旧进程的状态并加载新进程已保存的状态，这个过程称为上下文切换。

流程（对应截图7）

关键结论

  • 进程的"上下文"就存放在它的 PCB 中
  • 上下文切换时间是纯粹的开销（pure overhead）——切换期间系统不做任何有用工作
  • 操作系统和 PCB 越复杂，切换耗时越长
  • 耗时还取决于硬件支持：有些硬件为每个 CPU 提供多组寄存器，可同时装载多个上下文，切换时只需改变寄存器组指针，速度极快

补充：现代 CPU 上下文切换通常在微秒量级，但间接开销（TLB、Cache 失效导致的"缓存污染"）往往比直接的寄存器保存/恢复更昂贵。

十、移动系统中的多任务

系统 特点
iOS（早期版本） 只允许一个进程运行，其他挂起。受屏幕尺寸和 UI 限制： • 单一前台进程——由用户界面控制 • 多个后台进程——在内存中运行但不显示，且受限制 • 限制：只能执行单个短任务、接收事件通知、或特定长任务（如音频播放）
Android 前台与后台都可运行，限制更少。后台进程用 service 执行任务： • 即使后台进程被挂起，service 仍可继续运行 • service 没有用户界面，内存占用小

十一、进程操作（Operations on Processes）

操作系统必须提供两类机制：进程创建与进程终止。

十二、进程创建（Process Creation）

12.1 进程树

父进程创建子进程，子进程又可创建自己的子进程，从而形成进程树（tree of processes）。进程通过进程标识符 pid 被识别和管理。

Linux 进程树示例（截图2）：

  • systemd（pid = 1） 是所有用户态进程的祖先，在系统启动时创建（传统 UNIX 中叫 init）
  • Linux 下可用 ps -el、pstree 查看进程树
  • 补充：getpid() 取自身 pid，getppid() 取父进程 pid

12.2 三个设计维度

① 资源共享（Resource sharing）

  • 父子共享全部资源
  • 子进程共享父进程资源的一个子集
  • 父子不共享任何资源

② 执行方式（Execution）

  • 父子并发执行
  • 父进程等待子进程终止后再继续

③ 地址空间（Address space）

  • 子进程是父进程的副本（duplicate，如 fork()）
  • 子进程装入一个新程序（如 exec()）

12.3 UNIX 的实现

系统调用 作用
fork() 创建新进程，子进程是父进程地址空间的副本
exec() 在 fork() 之后使用，用新程序替换进程的内存空间
wait() 父进程调用，等待子进程终止
exit() 进程终止自己

十三、进程终止（Process Termination）

13.1 正常终止

  • 进程执行完最后一条语句后，调用 exit() 请求操作系统删除自己
  • 通过 wait() 把状态数据（status）返回给父进程
  • 操作系统**回收（deallocate）**进程占用的所有资源

13.2 父进程强制终止子进程

父进程可用 abort() 终止子进程，常见原因：

  1. 子进程超出分配的资源
  2. 分配给子进程的任务不再需要
  3. 父进程正在退出，而操作系统不允许子进程在父进程终止后继续存在

13.3 级联终止（Cascading Termination）

某些操作系统不允许子进程在父进程终止后存活。此时一个进程终止，其所有子进程、孙进程……都必须被终止，这一过程由操作系统发起。

13.4 wait() 与两种"异常"进程

情况 名称 说明
子进程已终止，但父进程没有调用 wait() 僵尸进程（zombie） 进程已结束，但 PCB 仍保留在系统中（保存退出状态），占用进程表项
父进程先终止且未调用 wait() 孤儿进程（orphan） 子进程失去父亲

补充： Linux 中孤儿进程会被 systemd/init (pid=1) 收养，由它定期调用 wait() 回收，因此孤儿最终不会变成永久僵尸。真正危险的是父进程长期运行却不 wait()，僵尸会持续堆积耗尽进程表。

十四、Android 进程重要性层次

移动操作系统常需终止进程以回收内存等系统资源。Android 按重要性由高到低排序：

级别 类型 典型含义（补充）
1（最重要） Foreground process 前台进程 用户当前正在交互的进程
2 Visible process 可见进程 界面可见但不在前台（如被对话框遮挡）
3 Service process 服务进程 运行 service，如后台播放音乐
4 Background process 后台进程 界面不可见，被缓存
5（最不重要） Empty process 空进程 不含任何活动组件，仅作缓存加速重启

Android 从最不重要的开始终止进程。

十五、多进程架构 —— Chrome 浏览器

单进程浏览器的问题： 一个网站出问题，整个浏览器可能挂起或崩溃。

Chrome 采用多进程架构，共 3 类进程：

进程类型 职责
Browser 进程 管理用户界面、磁盘与网络 I/O（只有一个）
Renderer 进程 渲染网页，处理 HTML、JavaScript。每打开一个网站创建一个新的 renderer，运行在**沙箱（sandbox）**中，限制磁盘和网络 I/O，把安全漏洞的影响降到最小
Plug-in 进程 每种插件一个进程

优点： 隔离性好、崩溃互不影响、安全性高。代价： 内存开销大（这也是 Chrome"吃内存"的原因）。

十六、进程间通信（IPC）

16.1 独立进程 vs 协作进程

  • 独立进程（independent）：不影响其他进程，也不被影响
  • 协作进程（cooperating）：可以影响其他进程或被其影响，包括共享数据

16.2 为什么需要协作进程

  1. 信息共享（Information sharing）
  2. 计算加速（Computation speedup）——任务拆分并行执行
  3. 模块化（Modularity）
  4. 便利性（Convenience）

协作进程需要 IPC，共有两种模型：共享内存 与 消息传递。

16.3 两种通信模型对比（截图5）

共享内存 消息传递
数据存放 用户进程地址空间中的共享区 内核中的消息队列
内核参与 仅在建立共享区时参与，之后由用户进程控制 每次收发都要经过内核（系统调用）
速度 快（无系统调用开销） 慢（每条消息需两次上下文切换/拷贝）
同步 需程序员自己保证同步 由系统提供，天然避免冲突
适用 大量数据、单机 少量数据、分布式系统

共享内存的主要难题是：提供机制让用户进程在访问共享内存时同步各自的动作（详见第6、7章）。

十七、生产者–消费者问题

协作进程的经典范式： 生产者进程产生信息，消费者进程消费这些信息（如编译器产生汇编代码 → 汇编器消费）。

两种变体：

变体 生产者 消费者
无界缓冲区（unbounded-buffer） 永不等待 缓冲区空时等待
有界缓冲区（bounded-buffer） 缓冲区满时必须等待 缓冲区空时等待

18.2 竞争条件（Race Condition）

counter++ 和 counter-- 在机器指令层面不是原子操作：

交错执行示例（初始 counter = 5）：

步骤 执行者 指令 结果
S0 生产者 register1 = counter register1 = 5
S1 生产者 register1 = register1 + 1 register1 = 6
S2 消费者 register2 = counter register2 = 5
S3 消费者 register2 = register2 − 1 register2 = 4
S4 生产者 counter = register1 counter = 6
S5 消费者 counter = register2 counter = 4

正确结果应是 5（一增一减），却得到 4（或换个顺序得到 6）。

竞争条件定义： 多个进程并发访问和操纵同一数据，最终结果取决于访问发生的具体顺序。

思考题： 为什么第一个解法（最多填 N−1 个）没有竞争条件？

因为生产者只写 in、只读 out，消费者只写 out、只读 in——不存在两方同时修改同一变量的情况。而 counter 被双方共同修改，才产生竞争。（详见第6章）

十九、IPC —— 消息传递（Message Passing）

进程之间通信不借助共享变量。IPC 设施提供两个基本操作：

  • send(message)
  • receive(message)

消息长度可以是定长或变长（定长实现简单但编程不便，变长反之）。

19.1 通信前提

进程 P 与 Q 要通信，必须：

  1. 在两者之间建立通信链路（communication link）
  2. 通过 send / receive 交换消息

19.2 实现时需回答的问题

  • 链路如何建立？
  • 一条链路能否关联两个以上进程？
  • 每对进程之间可以有多少条链路？
  • 链路的容量是多少？
  • 链路能容纳的消息大小是定长还是变长？
  • 链路是单向还是双向？

19.3 链路的实现层次

层次 形式
物理（Physical） 共享内存、硬件总线、网络
逻辑（Logical） 直接 / 间接；同步 / 异步；自动 / 显式缓冲

二十、直接通信 vs 间接通信

20.1 直接通信（Direct Communication）

进程必须显式命名对方：

链路性质：

  • 链路自动建立
  • 一条链路恰好关联一对通信进程
  • 每对进程之间恰好只有一条链路
  • 链路可以是单向的，但通常是双向的

缺点：硬编码进程名，模块性差——进程标识改变时所有引用都要修改。

20.2 间接通信（Indirect Communication）

消息发送到邮箱（mailbox）、也叫端口（port），并从邮箱接收：

  • 每个邮箱有唯一 id
  • 进程只有共享同一个邮箱时才能通信

操作： 创建新邮箱 → 通过邮箱收发消息 → 删除邮箱

链路性质：

  • 只有进程共享公共邮箱时链路才建立
  • 一条链路可关联多个进程
  • 每对进程可共享多条链路
  • 链路可单向或双向

20.3 邮箱共享问题

场景： P₁、P₂、P₃ 共享邮箱 A，P₁ 发送，P₂ 和 P₃ 都在接收 —— 谁收到消息？

三种解决方案：

  1. 限制一条链路最多关联两个进程
  2. 同一时刻只允许一个进程执行 receive
  3. 由系统任意选择接收者，并通知发送者是谁接收了

二十一、同步（Synchronization）

消息传递可以是阻塞（blocking）**或**非阻塞（non-blocking）：

类型 操作 行为
阻塞 = 同步 Blocking send 发送者阻塞，直到消息被接收
Blocking receive 接收者阻塞，直到有消息可用
非阻塞 = 异步 Non-blocking send 发送后立即继续执行
Non-blocking receive 收到一条有效消息或一个空消息（null）

四种组合均可能。若 send 和 receive 都是阻塞的，则构成"会合"（rendezvous）。

二十二、缓冲（Buffering）

链路上附有一个消息队列，有三种实现方式：

方式 容量 发送者行为
零容量（Zero capacity） 队列长度 0，链路上不排队消息 必须等待接收者取走 → rendezvous
有界容量（Bounded capacity） 有限长度 n 队列满时必须等待；未满则立即返回
无界容量（Unbounded capacity） 无限长度 永不等待

IPC 实例 —— POSIX 共享内存

POSIX 共享内存以**内存映射文件（memory-mapped file）**的方式实现：共享内存对象被表示为一个文件，进程把它映射进自己的地址空间后，像操作普通内存一样读写。

22.1 标准流程（四步）

步骤 系统调用 说明
① 创建/打开共享内存段 `shm_fd = shm_open(name, O_CREAT O_RDWR, 0666);`
② 设置对象大小 ftruncate(shm_fd, 4096); 把共享对象截断/扩展为指定字节数
③ 内存映射 ptr = mmap(0, SIZE, PROT_WRITE, MAP_SHARED, shm_fd, 0); 把文件描述符映射成一个指针
④ 读写 直接用 mmap() 返回的指针 无需系统调用，速度快

补充：MAP_SHARED 表示对该映射区的修改对其他进程可见；若用 MAP_PRIVATE 则是写时复制的私有副本，无法通信。编译时需链接 -lrt。

二十三、IPC 实例 —— Mach

Mach 是微内核操作系统（macOS / iOS 内核 XNU 的基础）。

23.1 核心特征

  • 通信完全基于消息，连系统调用也是消息
  • 每个**任务（task）**创建时自动获得两个端口：
    • Kernel port（内核端口）——与内核通信
    • Notify port（通知端口）——接收事件通知
  • 收发消息统一使用 mach_msg() 函数
  • 通信所需的端口由 mach_port_allocate() 创建

23.2 灵活的发送/接收语义

当邮箱已满时，发送方有四种选择：

  1. 无限期等待
  2. 最多等待 n 毫秒（超时）
  3. 立即返回
  4. 临时缓存一条消息（系统代为暂存，每个发送者最多一条）

Mach 消息 = 消息头 + 消息体。消息头中包含目的端口、本地（回复）端口、消息大小等。

二十四、IPC 实例 —— Windows

Windows 以消息传递为核心，通过**高级本地过程调用（Advanced Local Procedure Call, LPC/ALPC）**设施实现。

  • 只能用于同一台机器上的进程之间（跨机器要用 RPC）
  • 使用端口（port）（类似邮箱）建立和维护通信通道

24.1 建立通信的四步（对应截图6）

  1. 客户端打开子系统**连接端口（Connection Port）**对象的句柄
  2. 客户端发送连接请求（connection request）
  3. 服务器创建两个私有通信端口（Client Communication Port 和 Server Communication Port），并把其中一个的句柄返回给客户端
  4. 客户端与服务器使用各自对应的端口句柄发送消息或回调，并监听回复

24.2 三种消息传递技术（补充）

消息大小 方式
≤ 256 字节 直接把消息拷贝到端口的消息队列中
> 256 字节 通过**共享区对象（Shared Section Object）**传递——避免大数据拷贝（截图中的下方通道）
超大数据 服务器直接读写客户端地址空间的 API

二十五、管道（Pipes）

管道是一根管道/导管（conduit），允许两个进程通信。

25.1 设计管道要考虑的问题

  1. 通信是单向还是双向？
  2. 若是双向，是半双工还是全双工？
  3. 通信进程之间是否必须存在关系（如父子）？
  4. 管道能否跨网络使用？

25.2 两类管道

普通管道 Ordinary Pipe 命名管道 Named Pipe
方向 单向（unidirectional） 双向（bidirectional）
进程关系 必须有父子关系 不需要任何关系
参与进程数 2 个 多个进程可同时使用
生命周期 随创建它的进程结束而消失 独立存在于文件系统中
外部可访问 否，无法从创建它的进程之外访问 是（有名字）
Windows 叫法 匿名管道（anonymous pipe） Named Pipe
支持平台 UNIX、Windows UNIX 和 Windows 均提供

25.3 普通管道（截图7）

  • 以标准的生产者–消费者方式通信
  • 生产者写入写端（write-end），消费者从**读端（read-end）**读取
  • 因此普通管道是单向的

UNIX 实现：

父进程调用 pipe() 后再 fork()，子进程继承文件描述符，于是父子共享同一管道。

使用规范： 每个进程必须关闭不用的那一端（如父写子读：父关 fd[0]，子关 fd[1]），否则读端永远读不到 EOF。

补充：Shell 中的 ls | more 正是普通管道；UNIX 中命名管道用 mkfifo() 创建，也称 FIFO，在文件系统中表现为一个特殊文件。UNIX 的命名管道是半双工的，需要全双工要开两条。

二十六、客户–服务器系统中的通信

两种主要机制：套接字（Sockets） 与 远程过程调用（RPC）。

二十七、套接字（Sockets）

27.1 基本概念

  • 套接字 = 通信的端点（endpoint for communication）
  • 由 IP 地址 + 端口号拼接而成。端口号是包含在数据包开头的一个数字，用于区分主机上的不同网络服务
  • 例：161.25.19.8:1625 指主机 161.25.19.8 上的 1625 端口
  • 通信发生在一对套接字之间
  • 1024 以下的端口是"知名端口（well-known）"，用于标准服务（HTTP 80、SSH 22、FTP 21…）
  • 特殊 IP **127.0.0.1（loopback，回环地址）**指进程所在的本机

客户端端口 1625 由系统自动分配（> 1024），服务器端口 80 是知名端口。

无连接（Connectionless） UDP 不可靠、无序、开销小（DatagramSocket）

二十八、远程过程调用（RPC）

28.1 核心思想

RPC 把网络上不同机器的进程之间的过程调用抽象化——让远程调用看起来像本地函数调用一样。同样使用端口来区分服务。

28.2 存根（Stub）

Stub 是客户端对服务器上实际过程的代理（proxy）。

角色 职责
客户端 stub 定位服务器，并打包（marshall）参数
服务器端 stub 接收消息，**解包（unmarshall）*参数，在服务器上*执行该过程

在 Windows 上，stub 代码由用 **MIDL（Microsoft Interface Definition Language，微软接口定义语言）*编写的规范*编译生成。

28.3 两大技术难题

① 数据表示差异
不同体系结构的字节序不同——大端（big-endian）**与**小端（little-endian）。因此参数用 **XDR（External Data Representation，外部数据表示）**格式统一编码，屏蔽机器差异。

讲义中写作 “XDL”，标准名称应为 XDR。

② 故障语义
远程通信比本地调用有更多的失败场景（网络丢包、服务器宕机、消息重复）。因此系统需保证消息**“恰好一次（exactly once）”**送达，而不仅仅是"最多一次（at most once）"。

  • 至多一次：给每条消息附加时间戳，服务器记录已处理的时间戳，重复消息直接丢弃
  • 恰好一次：在"至多一次"基础上，要求客户端重传直到收到 ACK

③ 绑定问题
操作系统通常提供 rendezvous（会合）服务，也叫 matchmaker（媒人）服务，把客户端和服务器连接起来——即根据过程名动态查询其端口号。

28.4 RPC 执行流程（截图11）

步骤 客户端 消息 服务器
1 用户调用内核，请求向过程 X 发送 RPC 消息
2 内核发消息给 matchmaker 查询端口号 From: client → To: server, Port: matchmaker, Re: 查询 RPC X 的地址 matchmaker 收到消息，查表
3 内核把返回的端口 P 放入用户 RPC 消息中 From: server → To: client, Port: kernel, Re: RPC X, Port: P matchmaker 回复客户端端口 P
4 内核发送真正的 RPC From: client → To: server, Port: P, 监听端口 P 的守护进程收到消息
5 内核收到回复，交给用户 From: RPC, Port: P → To: client, Port: kernel, 守护进程处理请求并发送输出

简化记忆：“两轮消息” —— 第一轮问 matchmaker 要端口，第二轮才是真正的远程调用。

28.5 Socket 与 RPC 对比（补充）

Socket RPC
抽象层次 低——收发原始字节流 高——像调用本地函数
数据格式 程序员自行定义和解析 由 stub 自动 marshall/unmarshall
编程复杂度 高 低
灵活性/性能控制 高 较低
