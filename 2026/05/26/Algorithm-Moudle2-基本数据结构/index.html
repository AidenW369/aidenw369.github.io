基本数据结构

2.1 基本数据结构简介

2.1.1 核心概念梳理

  • 电路交换 vs. 分组交换

    • 传统电话网采用电路交换，通信前需建立一条专用物理通路，资源独占，效率低。
    • 互联网采用分组交换。数据被切分成小包，每个包独立选路，共享网络资源，效率高，但会引入延迟和抖动。

  • 数据包（Packet）与 MTU

    • 数据包是网络传输的基本单元，包含头部（源/目的地址等控制信息）和有效载荷。
    • MTU（最大传输单元）：链路层规定的最大有效载荷。以太网的1500字节是事实标准，但并非绝对（如巨型帧可达9000字节）。

  • TCP 如何保证可靠有序？

    • 确认与重传：接收方收到包后发确认消息，发送方在超时未收到确认时会重传。
    • 序列号：每个字节都有编号，接收方以此按序重组，丢弃重复包。
    • 流量控制与拥塞控制：防止发送方“淹没”接收方或网络，这也是延迟抖动的一大来源。

  • 缓冲区的生产者-消费者模型与流量整形

    • 生产者：网络进程，以变速率将数据包放入队列。多亏了TCP，放入时已是正确顺序。
    • 消费者：播放器进程，以固定码率从队列取出数据解码播放。
    • 缓冲区（队列）：吸收速率波动。作用是流量整形，好比水库——进水忽大忽小，出水则平稳恒定。
    • 初始缓冲：播放前需先蓄积足够数据，以应对后续的网络抖动。

  • 互联网数据包传输

  • 互联网以离散数据包（packets） 传输信息

  • 以太网标准下，单个数据包最大 1500 字节（即MTU）

  • 视频等大文件必须拆分为多个包，各自独立路由，再在目的地重组

2.1.2 为什么不都用 TCP？——实时视频的取舍

教材提到“存储的视频文件”用TCP，这个限制条件非常关键。对于实时视频（如视频会议、直播），情况完全不同：

特性 TCP（适用于点播） UDP（适用于实时通信）
可靠性 绝对可靠，保证送达 尽最大努力交付，不保证可靠
有序性 严格按序 不保证，应用层自己处理
延迟 重传机制引入不可预测的延迟 无连接、无重传，延迟低
控制机制 有复杂的拥塞控制 无，应用层可按需控制发送速率
应用场景 文件传输、网页、点播视频 视频会议、直播、在线游戏、DNS

原因：在实时通话中，一个丢失的音频包已无重传必要，因为它的“时效”已过，强行重传只会造成卡顿。所以宁可短暂花屏/卡音，也要保证低延迟的流畅感。

TCP — Transmission Control Protocol（传输控制协议）

TCP 是一种面向连接、可靠的传输协议。在发送数据之前，需要先通过三次握手建立连接，然后才开始传输。

核心特性：

  • ✅ 可靠交付：确保每个数据包都到达目的地
  • ✅ 有序传输：保证数据按发送顺序重组
  • ✅ 错误检测与重传：丢包会自动重传
  • ✅ 流量控制 & 拥塞控制：防止网络过载
  • ❌ 代价：延迟较高，开销较大

典型应用： 网页浏览（HTTP/HTTPS）、邮件、文件下载、点播视频（YouTube、Netflix）

UDP — User Datagram Protocol（用户数据报协议）

UDP 是一种无连接、不可靠的传输协议。发送方直接把数据"扔出去"，不管对方有没有收到。

核心特性：

  • ✅ 低延迟：无握手，无等待，直接发送
  • ✅ 轻量：头部开销小（8字节 vs TCP的20字节）
  • ❌ 不保证到达：包可能丢失
  • ❌ 不保证顺序：包可能乱序到达
  • ❌ 无重传机制

典型应用： 视频通话（Zoom、FaceTime）、网络直播、在线游戏、DNS查询

对比总结

特性 TCP UDP
全称 传输控制协议 用户数据报协议
连接方式 面向连接（三次握手） 无连接
可靠性 高（保证到达） 低（尽力而为）
顺序保证 ✅ ❌
速度/延迟 较慢 很快
头部开销 20 字节 8 字节
适用场景 准确性优先 速度优先

💡 一个直觉类比

  • TCP 像挂号信——你知道信一定会送到，还能确认签收，但慢一些。
  • UDP 像广播——说出去就算了，不管听众有没有听见，但快。

2.1.3 抖动（Jitter）问题

  • 数据包到达时间不均匀的现象称为网络抖动（Jitter）
  • 原因：网络拥塞、路由路径不同、错误重传等
  • 这是需要缓冲区的根本原因

2.1.4 缓冲区（Buffer）机制

生产者：TCP网络进程，以可变速率向缓冲区写入数据包

消费者：视频播放进程，以固定速率从缓冲区读取数据包

缓冲区起到**“削峰填谷”** 的作用，只要均值速率足够，就能流畅播放

2.1.5 FIFO（先进先出）

  • 缓冲区遵循 FIFO 原则——最早进入的包最先被消费
  • 这保证了视频帧按正确时间顺序播放
  • FIFO 的典型数据结构实现：队列（Queue）

2.2 栈和队列

2.2.1 栈的基本概念

栈是一种遵循**后进先出（LIFO, Last-In First-Out）**原则的容器数据结构。

生活类比：就像自助餐厅里弹簧托盘架上的一叠盘子——最后放上去的盘子，最先被取走。

2.2.2 栈的基本操作

方法 描述
push(o) 将对象 o 插入栈顶
pop() 移除并返回栈顶元素（若栈为空则报错）

2.2.3 基于数组的实现

核心思路

用一个容量为 N 的数组 S 存储元素，同时维护一个整数变量 t 表示栈顶元素的下标。

  • 初始状态（空栈）：t = -1
  • 栈中元素个数：t + 1
  • 栈满条件：t + 1 = N

替代方案：

  • 使用可扩展数组（Extendable Array），随栈增长自动扩容

2.2.4 栈的重要应用

方法调用与递归（Method Stack）

在 C、C++、Java、Python 等语言的运行时环境中，每个线程都维护一个私有的方法栈（Method Stack），用于：

  • 追踪局部变量
  • 保存方法调用信息
关键概念
概念 说明
帧（Frame） 描述当前活跃方法调用的数据单元，存储局部变量、参数及返回信息
程序计数器（Program Counter） 记录当前执行语句的地址，方法调用时保存返回地址
运行中方法 位于方法栈顶部的帧所对应的方法
挂起方法 栈中其余帧对应的方法，等待被调用的方法返回

方法调用流程

参数传递：值传递（Call-by-Value）
  • C、Java 等语言使用值传递
  • 传递的是变量当前的值，而非变量本身
  • 被调用方法修改局部副本，不影响调用方的原始变量

递归（Recursion）

栈天然支持递归：每次递归调用都会在方法栈中创建一个独立的帧，拥有各自的局部变量副本。

⚠️ 注意： 若递归设计不当（无终止条件），方法栈会不断增长，最终耗尽内存，引发 StackOverflow 错误。

正确设计递归的要点：

  1. 确保递归调用处理的是"更小"的子问题
  2. 对"最小"情形进行非递归的特殊处理（Base Case）

2.2.5 队列（Queue）

队列的基本概念

队列是一种遵循**先进先出（FIFO, First-In First-Out）**原则的容器数据结构。

生活类比：就像排队买票——先来的人先被服务，后来的人只能在队尾等待。

  • 元素从队尾（rear） 插入
  • 元素从队头（front） 删除
  • 只有在队列中待得最久的元素才能被取出

队列的基本操作

方法 描述
enqueue(o) 将对象 o 插入队尾
dequeue() 移除并返回队头元素（若队列为空则报错）

基于数组的实现

核心思路

用容量为 N 的数组 Q 存储元素，同时维护两个索引变量：

变量 含义
f (front) 指向队头元素的下标
r (rear) 指向下一个可用空位的下标

初始状态：f = r = 0

空队列条件：f == r

队列元素个数：(N - f + r) mod N

解决方案： 规定队列最多存储 N-1 个元素，保留一个空位。

2.2.6 栈 vs 队列 对比

特性 栈（Stack） 队列（Queue）
原则 LIFO（后进先出） FIFO（先进先出）
插入 push — 从栈顶插入 enqueue — 从队尾插入
删除 pop — 从栈顶删除 dequeue — 从队头删除
典型应用 函数调用、递归、括号匹配 视频缓冲、打印队列、订票系统

2.2.7 扩展补充

其他常见栈的应用场景

  1. 括号匹配：编译器用栈检查 {}、[]、() 是否配对
  2. 表达式求值：中缀转后缀表达式（逆波兰表达式）
  3. 浏览器历史：后退功能本质上是一个栈
  4. 撤销操作（Undo）：文本编辑器的撤销功能
  5. 深度优先搜索（DFS）：图与树的遍历算法
