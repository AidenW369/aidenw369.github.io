在C语言中，带循环的函数就是在函数体内包含循环结构（for、while 或 do-while）的函数，用于重复执行某段逻辑。

while 先判断后执行 条件不确定，可能不执行
do-while 先执行后判断 至少执行一次

6.7 单元测试

单元测试（Unit Testing）是一种软件测试方法，对代码中最小的可测试单元（通常是函数）进行独立验证，确保其行为符合预期。

核心概念

  • 测试用例（Test Case）：针对某个函数的一组输入和预期输出
  • 断言（Assertion）：验证实际结果是否与预期一致，不一致则报错
  • 测试套件（Test Suite）：多个测试用例的集合
  • 测试框架（Test Framework）：提供运行测试、统计结果的基础设施

6.8 函数是如何工作的

调用栈的工作方式

当函数被调用时，系统会在调用栈（Call Stack）**上创建一个**栈帧（Stack Frame），其中包含：

  • 函数的局部变量
  • 参数的副本
  • 返回地址（函数执行完后跳回的位置）

函数返回后，栈帧被销毁，控制权回到 main。

总结

  1. 声明 → 告诉编译器函数的签名
  2. 定义 → 实现函数的具体逻辑
  3. 调用 → 执行函数，传入参数，获取返回值
  4. 栈帧 → 每次调用都在栈上分配独立的内存空间
  5. 返回 → 将结果传回调用者，栈帧销毁

6.10 按指针传递

在C语言中，函数参数的传递默认是按值传递（pass by value）——即函数接收的是变量的副本，对副本的修改不会影响原始变量。

按指针传递则是将变量的内存地址传给函数，函数通过该地址直接操作原始变量。

基本示例

核心概念

int *x 函数参数声明为指针类型
*x 解引用指针，访问/修改原始变量的值

常见使用场景

1. 让函数返回多个值

2. 交换两个变量（经典例子）

3. 传递大型结构体（避免复制开销）

注意事项

  • 传入前用 & 取地址，函数内用 * 解引用
  • 要确保指针不为 NULL，否则解引用会导致程序崩溃
  • C++ 中还有按引用传递（&），更简洁，但C语言没有这个特性，只能用指针模拟

6.13 带数组参数的函数：常见错误

在C语言中，使用数组作为函数参数时，有几个经典且容易犯的错误：

1. 以为可以通过 sizeof 获取数组长度

原因：数组传入函数时会退化为指针（decay to pointer），sizeof(arr) 返回的是指针的大小（通常是 4 或 8 字节），而不是数组的总大小。

正确做法：显式传入长度。

2. 忘记传递数组长度

函数内部无法知道数组有多长，必须额外传一个 len 参数，或者使用哨兵值（如字符串的 \0）。

3. 越界访问

用 <= 而不是 <，导致访问 arr[len]，这是未定义行为（UB）。

4. 修改了调用者的数组却没有声明意图

原因：C 中数组是按引用（传指针）传递的，函数内修改会影响原始数据。

6.14 变量/函数定义的作用域

作用域是指程序中变量或函数名字可被访问的范围。C语言中主要有以下几种作用域：

1. 块作用域（Block Scope）

在 {} 大括号内声明的变量，只在该块内有效。

2. 文件作用域（File Scope）

在所有函数外部声明的变量/函数，从声明处到文件末尾都可访问，即全局变量。

3. 函数作用域（Function Scope）

仅适用于 goto 语句的标签（label），标签在整个函数内可见。

4. 函数原型作用域（Function Prototype Scope）

函数声明（原型）中的参数名，其作用域仅限于该原型声明本身，实际意义不大。

关键修饰符对作用域的影响

修饰符 作用
static（局部） 变量只在本块可见，但生命周期延长到程序结束
static（全局/函数） 限制为文件内可见，不能被其他文件用 extern 访问
extern 声明变量/函数定义在其他文件，扩展可见性

总结

作用域遵循就近原则：内层的同名变量会"遮蔽"（shadow）外层变量，但不会修改外层变量的值。

6.15 参数错误检查

参数错误检查（Parameter Error Checking）是指在函数执行实际逻辑之前，验证传入参数是否合法、有效的编程实践。这是编写健壮 C 程序的重要组成部分。

为什么需要参数检查？

C 语言本身不提供异常机制，也不会自动检查指针是否为空、数组是否越界等问题。一旦传入非法参数，可能导致：

  • 程序崩溃（段错误）
  • 数据损坏
  • 安全漏洞（如缓冲区溢出）

常见的参数检查方式

1. 空指针检查
2. 范围检查（数值合法性）
3. 使用 assert() 宏（调试阶段）

⚠️ assert 在 Release 模式（定义了 NDEBUG）下会被禁用，不适合生产环境的错误处理。

4. 使用 errno 报告错误
5. 枚举/状态码返回

检查策略对比

方式 适用场景 优点 缺点
if 判断 + 返回值 生产代码 灵活，可控 需手动处理
assert() 调试阶段 简洁 Release 下失效
errno 系统/库函数风格 标准化 全局状态，线程不安全
错误码枚举 模块化开发 语义清晰 调用方需检查返回值

最佳实践

  1. 在函数入口集中检查所有参数，避免逻辑分散。
  2. 区分调试断言和运行时检查：assert 用于"不可能发生"的错误，if 用于"可能发生"的错误。
  3. 文档化参数约束，告知调用者哪些值是合法的。
  4. 嵌入式/安全关键系统中，通常要求对所有外部输入进行严格验证。
