操作系统保护机制

1. Goals of Protection（保护目标）

操作系统可视为由多个 Objects（对象） 组成的集合。每个对象拥有唯一名称，并提供一组定义明确的操作。

对象类型 示例
硬件对象（Hardware Objects） CPU、内存、磁盘、打印机、其他设备
软件对象（Software Objects） 文件、程序、进程、信号量

保护目标： 确保每个对象只能被授权进程以许可的方式访问。

例如，对文件的可用操作可能为：

[ Rights(File)={read,write,execute,delete} ]

一个进程可能只有 read 权限，而没有 write 或 delete 权限。

2. Principles of Protection（保护原则）

2.1 Principle of Least Privilege（最小特权原则）

用户、程序和系统组件只应获得完成任务所必需的最低权限。

  • 防止程序获得不必要的权限。
  • 限制 Bug、误操作或安全攻击造成的损失。
  • 可通过静态或动态方式管理权限。
类型 含义 例子
Static（静态） 权限在规定生命周期内保持固定 进程运行期间权限不变
Dynamic（动态） 权限可根据任务变化 Domain Switching、受控权限提升

2.2 Granularity（权限粒度）

对比 Coarse-grained（粗粒度） Fine-grained（细粒度）
权限范围 较大 较小
管理复杂度 较低 较高
开销 较低 较高
安全控制 不够精确 更精确
例子 传统 UNIX 普通用户/root 权限区分 ACL、RBAC、Linux Capabilities

2.3 其他原则

  • Need-to-Know（按需知悉）： 进程仅访问当前工作需要的资源。
  • Compartmentalization（分区隔离）： 将系统组件隔离，分别设置访问限制。
  • Audit Trail（审计日志）： 记录安全相关活动，用于追踪操作及发现异常。
  • Defense in Depth（纵深防御）： 结合多种保护手段，避免依赖单一措施。

3. Protection Rings（保护环）

3.1 基本概念

Protection Rings 按权限等级把系统组件划分为多层：

  • Ring 0： 最内层，最高权限。
  • Ring 1、Ring 2： 中间权限层。
  • Ring N−1： 最外层，最低权限。

在课件的 MULTICS 模型中，设 Di 、 Dj 为对应保护域的权限集合。若 j<i ，则 Ring j 更靠内，具有不低于 Ring i 的权限：

Di⊆Dj(j<i)

可记为：

DN−1⊆⋯⊆D2⊆D1⊆D0

注意： 此包含关系按保护环权限由内向外递减的含义整理；不要把它误解成所有实际操作系统中的保护域都必须形成嵌套集合。

3.2 跨环访问

不同级别之间不能随意访问。通常依靠硬件支持的受控入口，例如：

  • System Call（系统调用）
  • Trap（陷阱）
  • Interrupt（中断）
  • Gate（受控入口）

用户程序通过系统调用请求内核服务，而不是直接执行特权内核操作。

3.3 ARM CPU Architecture（ARM 异常级别）

Exception Level 组件 主要用途
EL0 User Applications 普通应用
EL1 OS Kernel 操作系统内核
EL2 Hypervisor 虚拟化管理
EL3 Secure Monitor 安全监控及安全状态切换
指令 英文全称 主要作用
SVC Supervisor Call 请求操作系统服务
HVC Hypervisor Call 请求 Hypervisor 服务
SMC Secure Monitor Call 请求 Secure Monitor 服务
ERET Exception Return 从异常处理返回

易考点： SVC 面向 OS，HVC 面向 Hypervisor，SMC 面向 Secure Monitor。

4. Android Use of TrustZone

4.1 TrustZone 的作用

ARM TrustZone 提供基于硬件的安全状态隔离，使敏感代码和密钥可在可信环境中处理。

Normal World Secure World
运行普通应用和 OS 运行安全服务和可信软件
处理常规业务 保护密码学操作、密钥等敏感资源

注意： TrustZone 的安全状态与 EL0–EL3 异常级别并非完全相同的概念。

4.2 课件中的 Android 请求路径

  1. 应用请求密码学或身份验证服务。
  2. Framework 通过 HAL 与供应商提供的组件通信。
  3. TZ Daemon 向内核驱动发出请求。
  4. 内核驱动通过 SMC 请求可信环境提供服务。
  5. 敏感操作在受保护的环境中执行。

核心思想： 应用不能随意直接访问可信环境，而要经过受控接口。

5. Domain of Protection（保护域）

5.1 定义

Protection Domain 描述进程当前可访问的对象及其允许执行的操作。

域可以对应用户、进程或过程（User / Process / Procedure）。

Access Right（访问权限） 表示为：

[ AccessRight=\langle Object,RightsSet\rangle ]

其中 RightsSet 是在对象上允许执行的操作集合。

Domain（保护域） 是访问权限的集合：

[ D_i={\langle O_j,R_j\rangle} ]

例如：

[ D_1={\langle O_1,{read,write}\rangle,\langle O_2,{execute}\rangle,\langle O_3,{read,write}\rangle} ]

表示 D1 可以读写 O1 、执行 O2 、读写 O3 。

5.2 域之间的关系

  • 不同域可能共享某些访问权限。
  • 域与进程的关联可为静态或动态。
  • 动态关联支持 Domain Switching（域切换）。
  • 共享某个对象的权限，不意味着两个域的所有权限完全相同。

5.3 UNIX 的域实现

在课件的简化模型中：

[ Domain=UserID ]

机制 作用
setuid 执行指定文件时，可采用文件所有者的有效用户身份
su 切换用户身份或启动另一用户的 Shell
sudo 根据授权以指定用户身份执行命令

这些机制可以用于说明权限身份的切换。

5.4 Android App IDs

Android 通过应用身份隔离资源：

  • 为不同应用分配 UID/GID。
  • 为应用分配私有数据目录，例如 /data/data/<appname>（课件示例）。
  • 使用 UID/GID 和内核权限机制隔离应用。
  • 某些操作可受特殊 GID 限制。
  • Isolated UID 进一步限制某些服务调用。

重点： Android 应用沙箱的一项基础是 Linux 用户身份及文件权限隔离。

6. Access Matrix（访问矩阵）

6.1 定义

Access Matrix 将权限表示为一个二维矩阵：

  • Row（行） = Domain（保护域）
  • Column（列） = Object（对象）
  • Cell（单元格） = Rights Set（权限集合）

[ Access(i,j)=Rights(D_i,O_j) ]

课件示例：

Domain / Object F1 F2 F3 Printer
D1 read — read —
D2 — — — print
D3 — read execute —
D4 read, write — read, write —

6.2 权限判断规则

当进程在 Di 中请求对 Oj 执行操作 op ，只有满足以下条件才允许：

[ op\in Access(i,j) ]

例如 Access(D1,F1)=read ，则允许 read，拒绝 write。

6.3 Mechanism 与 Policy 的分离

  • Mechanism（机制）： 操作系统提供矩阵及执行、检查和保护规则。
  • Policy（策略）： 决定哪些主体以哪些方式访问哪些资源。

访问矩阵可以描述访问控制，但不能独立解决所有信息泄露或约束问题（Confinement Problem）。

7. Dynamic Access Matrix（动态访问矩阵）

动态矩阵支持添加、删除和传播权限，也能将保护域本身视为对象。

7.1 四种特殊权限

权限 作用 记忆
Copy (*) 将某一访问权限复制给别的域 传权
Owner 管理某个对象的权限 管列
Control 修改指定域的权限 管行
Switch 切换到另一个保护域 换域

口诀：Owner 管列，Control 管行，Copy 传权，Switch 换域。

7.2 Domain Switching

把域作为对象加入矩阵：

Domain D1 D2 D3 D4
D1 — switch — —
D2 — — switch switch
D3 — — — —
D4 switch — — —

例如：

[ Access(D_1,D_2)={switch} ]

意味着进程可在授权条件下从 D1 切换到 D2 。

7.3 Copy Rights

read* 表示既可以读取，又可以复制 read 权限。

复制前：

Domain F1 F2 F3
D1 execute — write*
D2 execute read* execute
D3 execute — —

D2 将对 F2 的读取权限复制给 D3 ：

Domain F1 F2 F3
D1 execute — write*
D2 execute read* execute
D3 execute read —

考点： D3 得到的是 read 而非 read*，故不能再转授复制权限。

7.4 Owner Rights

若 D2 对 F2 有 owner 权限，便可以管理对象 F2 的相关访问权限，即修改对应矩阵列的授权条目。

7.5 Control Rights

若：

[ Access(D_2,D_4)={switch,control} ]

则 D2 可以在允许的规则下控制 D4 的访问权限。课件示例中， D4 对 F1 、 F3 的 read, write 被修改为 write。

8. Implementation of Access Matrix（访问矩阵实现）

访问矩阵通常是稀疏矩阵（Sparse Matrix），存储整个二维表并不经济。

8.1 Global Table（全局表）

使用三元组：

[ \langle Domain,Object,RightsSet\rangle ]

例如：

  • 优点： 概念简单。
  • 缺点： 表可能过大，查找和管理较繁琐。

8.2 ACL（访问控制列表）

以 Object（对象） 为中心，每个对象保存可以访问它的域及相应权限。

相当于按访问矩阵的列保存信息。

ACL 回答：Who can access this object?（谁能访问这个对象？）

优势是易于管理和撤销某个对象的授权；缺点是查询一个域对所有对象的权限不够集中。

8.3 Capability List（能力列表）

以 Domain（域） 为中心，列出域可以访问的对象及操作。

相当于按访问矩阵的行保存信息。

Capability List 回答：What can this domain access?（这个域能访问什么？）

Capability 类似受保护的访问凭证或安全指针，不能被进程任意伪造和修改。

8.4 Lock-Key（锁钥匙机制）

  • 每个 Object 保存若干 Lock。
  • 每个 Domain 持有若干 Key。
  • 若 Key 匹配对象的 Lock，则可授权访问。

8.5 实现方式比较

方式 组织方式 主要优点 主要缺点
Global Table 全局三元组 简单直接 表大，查找成本高
ACL 按对象 / 列 管理对象授权和撤销方便 域的全部权限分散
Capability List 按域 / 行 域的权限信息集中 撤销和追踪较难
Lock-Key 锁与钥匙匹配 灵活，可通过换锁/钥匙处理撤销 需要保护和管理匹配凭证

8.6 ACL + Capability 的混合使用

目的是结合 ACL 的权限管理便利性和 Capability 的访问效率。

9. Revocation of Access Rights（访问权限撤销）

Revocation 是取消已有的访问权限。

9.1 撤销维度

分类 两种选择
时间 Immediate / Delayed（立即 / 延迟）
作用范围 Selective / General（选择性 / 普遍）
权限范围 Partial / Total（部分 / 全部）
持续时间 Temporary / Permanent（临时 / 永久）

9.2 ACL 撤销

直接修改对象的权限列表即可：

ACL 中授权较为集中，因此撤销通常比较直接。

9.3 Capability 撤销

由于 Capability 可能已经分散到多个进程，需要专门的撤销机制。

方式 原理
Reacquisition（重新获取） 周期性重新申请，已撤销则拒绝
Back-pointers（反向指针） 对象记录指向自己的 Capability 的位置
Indirection（间接引用） Capability 经由中间表指向对象；可删除中间项
Keys（密钥） 改变对象的 Master Key，使旧凭证失效

易考点： ACL 较容易撤销；Capability 因可能被分发，撤销机制更复杂。

10. Role-Based Access Control（RBAC，基于角色的访问控制）

RBAC 通过角色组织权限，而不是给每个用户逐项配置所有权限。

[ User\rightarrow Role\rightarrow Privileges ]

例如：

课件以 Oracle Solaris 10 为例：

  • Privilege 可表示执行系统调用或使用其某些选项的权限。
  • Privilege 可分配给进程。
  • 用户被分配角色，角色提供程序和权限访问。
  • 课件示例中可通过密码启用角色以获得相应特权。

作用： 降低权限配置复杂度，实现最小特权原则。

11. DAC vs. MAC（自主与强制访问控制）

11.1 DAC：Discretionary Access Control（自主访问控制）

由具有相应管理权限的用户或资源所有者配置访问规则。

典型示例：UNIX File Permissions、Windows ACL。

11.2 MAC：Mandatory Access Control（强制访问控制）

由系统实施统一的强制安全策略；包括特权用户在内的主体不能任意绕过该策略。

MAC 的基本要素：

  • Subject（主体）： 用户、进程等。
  • Object（客体）： 文件、设备等。
  • Label（标签）： 主体和客体的安全属性。
  • Policy（策略）： 决定访问是否允许。

[ Allow=Policy(SubjectLabel,ObjectLabel,Operation) ]

示例：SELinux、TrustedBSD。

11.3 对比

对比项 DAC MAC
控制依据 被授权用户/所有者设置权限 系统强制策略
灵活性 高 较受策略限制
是否可由所有者任意放宽 通常可在授权范围内调整 不可绕过强制策略
示例 UNIX Permissions、ACL SELinux、TrustedBSD

现代系统可以同时采用 DAC 和 MAC。

12. Capability-Based Systems（基于能力的系统）

区分： 前面的 Capability List 是访问矩阵的一种实现；本节重点介绍将超级用户特权拆分成独立能力的系统机制。

传统 root 可能拥有大量管理权限。Linux Capabilities 将这些权限拆分成更细的能力：

[ RootPrivileges\rightarrow{CAP_1,CAP_2,\ldots,CAP_n} ]

12.1 常见 Linux Capabilities

Capability 作用
CAP_NET_RAW 原始网络套接字等操作
CAP_CHOWN 修改文件所有权
CAP_SETUID 设置用户身份
CAP_KILL 相关进程信号操作
CAP_NET_ADMIN 网络管理操作

12.2 Ping 例子

旧式方式中，使用原始 ICMP Socket 可能需要 root 特权。通过 CAP_NET_RAW，程序可在不获得全部 root 权限的情况下完成所需操作。

12.3 三个能力集合

集合 含义
Permitted 允许持有的能力集合
Effective 当前生效的能力集合
Inheritable 参与执行继承规则的能力集合

课件使用位图（Bitmap）描述权限位，并强调可主动降低程序运行期间不再需要的权限。

核心意义： 把粗粒度 root 权限拆分，落实最小特权原则。

13. Other Protection Methods（其他保护技术）

13.1 System Integrity Protection（SIP）

Apple 在 macOS 10.11 引入的系统完整性保护机制。

  • 限制对重要系统文件和资源的修改。
  • 即使 root，也会受到部分保护规则约束。
  • 限制某些修改、调试和加载行为。
  • 课件提到代码签名内核扩展等要求。

13.2 System-Call Filtering（系统调用过滤）

类似系统调用层面的防火墙，可根据系统调用编号和参数决定是否允许操作。

Linux 机制示例：seccomp-BPF。

13.3 Sandboxing（沙箱）

将程序限制在特定运行环境中，阻止访问未经授权的资源。

  • 可在进程启动早期设置限制。
  • Java、.NET 可在虚拟机环境提供保护。
  • 系统也可基于 MAC 实现沙箱。
  • 课件提到 Apple macOS 的 Seatbelt 机制。

13.4 Code Signing（代码签名）

开发者通过哈希与数字签名提供软件来源和完整性验证。代码变化可能导致签名失效，系统可根据策略拒绝加载或执行。

注意： 签名只能辅助证明来源及完整性，不代表程序必然没有漏洞。

14. Language-Based Protection（基于语言的保护）

通过语言和运行时机制表达、落实权限策略，补充硬件及操作系统层保护。

14.1 Java 2 Protection

按照课件中的 Java 2 安全模型：

  1. JVM 加载类时为其分配 Protection Domain。
  2. 保护域表明类允许执行的操作。
  3. 执行敏感操作时，可检查调用堆栈。
  4. 类型安全与封装有助于保护数据和方法。

14.2 Stack Inspection（堆栈检查）

作用： 检查调用链上相关代码的权限，防止低权限代码借助高权限库越权执行敏感操作。

16. 高频考题与参考答案

Q1. What is the principle of least privilege?

只授予用户、程序或系统组件完成任务所需的最低权限，以减少潜在损害。

Q2. What do rows and columns represent in an access matrix?

  • Rows：Protection Domains。
  • Columns：Objects。
  • Cell：允许执行的操作集合。

Q3. What is the difference between ACL and Capability List?

  • ACL：按对象组织，说明谁能访问该对象。
  • Capability List：按域组织，说明该域能访问哪些对象。

Q4. Explain Copy / Owner / Control / Switch.

  • Copy：复制某项权限。
  • Owner：管理对象权限列。
  • Control：管理域权限行。
  • Switch：切换保护域。

Q5. Why is capability revocation more difficult?

Capability 可能已经分发到各个进程，需要追踪、间接引用或失效密钥等额外机制。

Q6. How does TrustZone protect resources?

通过硬件辅助安全隔离，将普通执行环境与可信安全环境分开，并使用受控接口请求敏感操作。

Q7. Compare DAC and MAC.

DAC 通常由授权用户/对象所有者设置权限；MAC 由系统统一策略强制限制访问。

Q8. Why are Linux capabilities useful?

将 root 权限拆分成更小的独立能力，使程序只获取实际需要的权限。

Q9. What is Stack Inspection?

通过检查调用链中相关代码的权限，决定是否允许执行敏感操作。

Q10. What are SVC / HVC / SMC?

  • SVC：请求 OS 服务。
  • HVC：请求 Hypervisor 服务。
  • SMC：请求 Secure Monitor 服务。

17. 考前速记（背诵版）

  1. Least Privilege： 只给任务需要的最低权限。
  2. Protection Rings： 内层权限高，跨层访问需受控。
  3. Protection Domain： 一组 <Object, RightsSet>。
  4. Access Matrix： 行是 Domain，列是 Object，单元格是 Rights。
  5. 动态权限： Owner 管列，Control 管行，Copy 传权，Switch 换域。
  6. ACL vs Capability： ACL 按对象，Capability 按域。
  7. Revocation： ACL 易撤销，Capability 较复杂。
  8. RBAC： User → Role → Privileges。
  9. DAC vs MAC： DAC 为授权用户决定；MAC 为系统强制策略。
  10. TrustZone： 可信/普通环境隔离，SMC 是关键入口之一。
  11. Linux Capabilities： 拆分 root 权限，落实最小特权。
  12. Stack Inspection： 检查调用链权限，doPrivileged 不会凭空赋权。

[ \boxed{Least\ Privilege\rightarrow Domain\rightarrow Access\ Matrix\rightarrow ACL/Capability\rightarrow RBAC/MAC\rightarrow Protection\ Mechanisms} ]
