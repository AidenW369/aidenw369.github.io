虚拟内存（Virtual Memory）

一、背景：为什么需要虚拟内存

程序要执行，代码必须在内存中，但整个程序很少同时被用到：

  • 错误处理代码、不常用的例程、过大的数据结构（如声明很大但只用一部分的数组）
  • 程序的不同部分不会在同一时刻都被需要

如果能执行只部分装入内存的程序，好处是：

好处 说明
不受物理内存大小限制 程序员可以面向一个很大的虚拟地址空间编程
每个程序占用内存更少 可同时运行更多程序 → CPU 利用率和吞吐量提高，而响应时间、周转时间不增加
I/O 更少 装入或换入/换出程序所需 I/O 减少 → 程序运行更快

二、虚拟内存的基本概念

定义：虚拟内存是将用户逻辑内存与物理内存分离的技术。

  • 程序执行时只需部分在内存中
  • 逻辑地址空间可以远大于物理地址空间
  • 允许多个进程共享地址空间
  • 进程创建更高效
  • 并发运行的程序更多，换入换出所需 I/O 更少

虚拟地址空间：进程在内存中存放方式的逻辑视图

  • 通常从地址 0 开始，地址连续直到空间末尾
  • 物理内存则按**页框（page frame）**组织
  • 由 MMU（内存管理单元） 负责把逻辑地址映射到物理地址

实现方式：

  1. 请求分页（Demand Paging）——本章重点
  2. 请求分段（Demand Segmentation）

📊 图示：虚拟内存大于物理内存
虚拟内存（page 0 ~ page v）→ 通过内存映射表（memory map） → 一部分页映射到物理内存，另一部分页存放在后备存储（backing store，即磁盘） 中，两者之间可以换入换出。

三、虚拟地址空间的布局

  • 栈从最大逻辑地址开始向下增长，堆向上增长 → 最大化利用地址空间
  • 两者之间的未用区域称为空洞（hole）：在堆或栈真正增长到某个新页之前，不需要分配物理内存
  • 支持稀疏地址空间（sparse address space）：为增长、动态链接库等预留空洞

虚拟内存带来的共享能力：

  • 系统库共享：把同一个库映射进多个进程的虚拟地址空间（见下图）
  • 共享内存：把页以读写方式映射进多个进程的地址空间
  • fork() 时共享页面：加快进程创建（见后文写时复制）

📊 图示：使用虚拟内存的共享库
两个进程各自的地址空间里都有一段 “shared library”，它们实际上都映射到物理内存中同一组共享页（shared pages），库代码在物理内存中只存一份。

四、请求分页（Demand Paging）

1. 基本思想

两种策略对比：

  • 装入时把整个进程都调入内存
  • 只在需要某页时才把它调入内存（请求分页）

请求分页的优点：I/O 更少（无多余 I/O）、内存需求更少、响应更快、可支持更多用户。

它类似于带交换的分页系统（图中程序 A 的页被换出到磁盘，程序 B 的页被换入），但粒度是页而不是整个进程。

访问某页时的三种情况：

  • 非法引用 → 终止（abort）
  • 合法但不在内存 → 调入内存
  • 已在内存 → 正常访问

惰性交换器（Lazy swapper）：除非某页确实会被用到，否则绝不把它换入内存。处理“页”的交换器称为调页程序（pager）。

2. 基本概念

  • 传统交换中，调页程序要猜测在再次换出前哪些页会被用到
  • 请求分页只调入真正需要的页 —— 那么如何确定这组页？→ 需要新的 MMU 功能
  • 若所需页已在内存：与非请求分页没有区别
  • 若所需页不在内存：需要检测并从存储设备调入，且要做到：
    • 不改变程序行为
    • 程序员无需修改代码（对程序员透明）

3. 有效-无效位（Valid-Invalid Bit）

  • 每个页表项都关联一个有效-无效位：
    • v → 在内存中（memory resident，驻留内存）
    • i → 不在内存中（或非法）
  • 初始时所有表项都置为 i
  • MMU 地址转换时，若页表项为 i → 产生缺页（page fault）

📊 图示：部分页不在主存时的页表
逻辑内存有 A~H 共 8 页，页表中：

  • 页 0（A）→ 帧 4，v
  • 页 2（C）→ 帧 6，v
  • 页 5（F）→ 帧 9，v
  • 其余页（B、D、E、G、H）为 i，只存在于后备存储中

注意：所有页在磁盘上都有副本，内存中只有其中 3 页。

4. 缺页处理步骤 ⭐

详细说明：

  1. 首次引用某页 → 陷入操作系统，产生缺页中断
  2. OS 查看另一张表（通常在 PCB 中）判断：
    • 非法引用 → 终止进程
    • 只是不在内存 → 继续处理
  3. 找到一个空闲帧
  4. 通过调度的磁盘操作把页换入该帧
  5. 修改表格，表明该页已在内存，有效位置为 v
  6. 重新启动导致缺页的那条指令

5. 请求分页的若干方面

  • 纯请求分页（Pure demand paging）：极端情况，进程启动时内存中一页都没有；OS 把指令指针指向第一条指令，立刻缺页；之后每个页首次访问都缺页
  • 一条指令可能访问多个页 → 产生多次缺页（例如：从内存取两个数相加再存回内存的指令，取指令、取两个操作数、存结果可能涉及不同页）
  • 由于局部性原理（locality of reference），实际情况并没那么糟

请求分页所需的硬件支持：

  1. 带有效-无效位的页表
  2. 二级存储（带交换空间的交换设备）
  3. 指令重启能力

6. 指令重启（Instruction Restart）

难点在于一条指令访问多个不同位置的情况：

  • 块移动指令（如 IBM 的 MVC）：移动一半时目标页缺页
  • 自动增/减寻址模式：寄存器已被修改
  • 能否直接重启整条指令？→ 若源和目的区域重叠，源数据可能已被覆盖，重启会出错

常见解决方法：

  • 执行前先访问块的两端，确保所有相关页都在内存，提前触发缺页
  • 用临时寄存器保存被覆盖位置的旧值，缺页时恢复后再重启

7. 空闲帧列表（Free-Frame List）

  • 缺页时 OS 需要把页从二级存储调入主存，因此要有空闲帧可用
  • 大多数 OS 维护一个空闲帧列表：head → 7 → 97 → 15 → 126 → … → 75
  • 分配时通常采用按需填零（zero-fill-on-demand）：分配前先把帧内容清零
  • 系统启动时，所有可用内存都放在空闲帧列表中

五、请求分页的完整处理过程（最坏情况）

  1. 陷入操作系统
  2. 保存用户寄存器和进程状态
  3. 判断该中断是缺页
  4. 检查页引用是否合法，并确定页在磁盘上的位置
  5. 从磁盘读入空闲帧：
    • 在设备队列中等待，直到读请求被服务
    • 等待磁盘寻道和/或旋转延迟
    • 开始把页传送到空闲帧
  6. 等待期间，把 CPU 分配给其他用户进程
  7. 收到磁盘 I/O 子系统的中断（I/O 完成）
  8. 保存另一进程的寄存器和进程状态
  9. 判断该中断来自磁盘
  10. 修改页表及其他表，表示该页已在内存
  11. 等待 CPU 再次分配给本进程
  12. 恢复用户寄存器、进程状态和新页表，然后继续执行被中断的指令

六、请求分页的性能 ⭐

1. 三项主要开销

活动 耗时
处理缺页中断 精心编码只需几百条指令，较短
读入页面 非常耗时（主要开销）
重启进程 较短

2. 有效访问时间（EAT）

设缺页率 p（0 ≤ p ≤ 1）：p = 0 无缺页；p = 1 每次访问都缺页。

EAT=(1−p)×内存访问时间+p×(缺页开销+换出页+换入页)

3. 计算示例

  • 内存访问时间 = 200 ns
  • 平均缺页服务时间 = 8 ms = 8,000,000 ns
EAT=(1−p)×200+p×8,000,000=200+7,999,800p (ns)

① 若每 1000 次访问有 1 次缺页（p = 0.001）：
EAT ≈ 200 + 7999.8 ≈ 8200 ns = 8.2 μs → 比 200 ns 慢约 40 倍！

② 若要求性能下降不超过 10%：

220>200+7,999,800p⇒p<0.0000025

即每 400,000 次内存访问中缺页少于 1 次。

💡 结论：缺页率必须保持极低，否则性能会急剧下降。

七、请求分页的优化

  • 交换空间的 I/O 比文件系统 I/O 更快（即使在同一设备上）：交换空间以更大的块分配，管理开销更小

  • 方案一：进程装入时把整个进程映像复制到交换空间，之后在交换空间中换入换出（早期 BSD Unix）

  • 方案二

    ：从磁盘上的程序二进制文件按需调页，释放帧时

    直接丢弃而不写回

    （Solaris 和当前 BSD）

    • 但以下情况仍需写入交换空间：
      • 与文件无关的页（栈、堆）——称为匿名内存（anonymous memory）
      • 在内存中被修改但尚未写回文件系统的页

  • 移动系统：通常不支持交换；改为从文件系统按需调页，并回收只读页（如代码页）

八、写时复制（Copy-on-Write, COW）⭐

1. 原理

  • 允许父进程和子进程最初共享相同的内存页
  • 只有当任一进程修改某个共享页时，才真正复制该页
  • 只复制被修改的页 → 进程创建更高效

📊 图示对比：

修改前：进程1 和 进程2 的三个页表项都指向物理内存中同一组 page A、B、C。

进程1 修改 page C 后：系统为进程1 创建 page C 的副本（Copy of page C），进程1 的映射改为指向副本；进程2 仍指向原 page C；page A、B 继续共享。

2. 相关要点

  • 空闲页通常从按需填零的页池中分配
    • 池中应始终保留空闲帧，以便快速处理缺页
    • 避免在处理缺页时还得先去释放一个帧
  • 为什么分配前要清零？ → 安全性：防止新进程读到之前使用该帧的进程留下的数据（信息泄露）
  • vfork()：fork() 的变体
    • 父进程被挂起，子进程直接使用父进程的地址空间（不使用写时复制）
    • 设计用于子进程立即调用 exec() 的场景
    • 非常高效（不复制任何页），但子进程若修改内存会影响父进程，需谨慎使用

九、页面置换（Page Replacement）

1. 没有空闲帧时怎么办？

内存中的帧会被各种用途占满：

  • 被各进程的页占用
  • 内核、I/O 缓冲区等也需要内存
  • 问题是每一方各分配多少？

解决办法：页面置换，即在内存中找一个当前没在真正使用的页，把它换出（page out）。

需要考虑：

  • 算法选择：终止进程？换出整个进程？还是置换某一页？
  • 性能目标：选出一种能让缺页次数最少的算法
  • 同一个页可能会被多次调入内存

2. 页面置换的基本思想

  • 修改缺页服务例程，把页面置换包括进去，以防止内存过度分配（over-allocation）
  • 使用修改位（modify bit / dirty bit） 降低换页开销：只有被修改过的页才需要写回磁盘，未修改的页可直接丢弃
  • 页面置换使逻辑内存与物理内存彻底分离：可以在较小的物理内存上提供很大的虚拟内存

📊 图示：需要页面置换的情形（Need For Page Replacement）

  • 进程1 的逻辑内存为 A、B、C、D，PC 指向页 1（B），但页表中 B 为 i，B 只在后备存储上
  • 进程2 的逻辑内存为 E、F、G、H，其中 G 也为 i
  • 物理内存 8 个帧已全部占满：帧 0~1 为 kernel，2=D，3=C，4=F，5=H，6=A，7=E
  • 要把 B 调入，却没有空闲帧（图中的"?”）→ 必须选一个页换出

3. 基本页面置换步骤 ⭐

  1. 找到所需页在磁盘上的位置
  2. 找一个空闲帧：
    • 有空闲帧 → 直接使用
    • 没有空闲帧 → 用页面置换算法选出一个牺牲帧（victim frame）
    • 若牺牲帧是脏的（dirty），先把它写回磁盘
  3. 把所需页读入（刚空出的）空闲帧，更新页表和帧表
  4. 重新执行引起陷阱的那条指令，让进程继续运行

⚠️ 注意：此时一次缺页可能涉及 2 次页传输（换出 + 换入），会使 EAT 增大。这正是修改位的价值：未修改的牺牲页不必写回，省掉一次传输。

📊 图示：页面置换（Page Replacement）
① 把牺牲页换出到磁盘 → ② 将其页表项改为无效（i） → ③ 把所需页换入帧 f → ④ 重置页表，新页表项为 f, v

4. 页面置换算法与帧分配算法

请求分页需要解决两个问题：

帧分配算法（Frame-allocation algorithm） 决定：

  • 给每个进程分配多少个帧
  • 置换时选择哪些帧

页面置换算法（Page-replacement algorithm）：

  • 目标是在首次访问和再次访问时都获得最低的缺页率

评估方法：在一个特定的内存引用序列（引用串，reference string）上运行算法，统计缺页次数。

  • 引用串只记录页号，不需要完整地址
  • 对同一页的连续重复访问不会引起缺页
  • 结果取决于可用帧的数量

本节所有例子使用的引用串：

📊 图示：缺页次数与帧数的关系
一般情况下，帧数越多，缺页次数越少，曲线单调下降并逐渐趋于平缓（约在 4~5 帧后接近最小值）。

5. 先进先出算法（FIFO）

原理：置换最早进入内存的页。

实现：用一个 FIFO 队列记录页的"年龄"即可，置换队头的页，新页插到队尾。

例子（3 个帧）：

引用 7 0 1 2 0 3 0 4 2 3 0 3 0 3 2 1 2 0 1 7 0 1
缺页 ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗ ✗
被置换 7 0 1 2 3 0 4 2 3 0 1 2

结果：15 次缺页

缺点：简单但性能不一定好。最早调入的页可能仍在频繁使用（如保存常用变量的页），置换后很快又要调回。

Belady 异常（Belady’s Anomaly）⭐

对某些引用串，增加帧数反而导致缺页次数增加。

经典例子，引用串：1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5

帧数 1 2 3 4 5 6 7
FIFO 缺页次数 12 12 9 10 5 5 5

📊 图示：曲线在 3 帧时为 9 次，到 4 帧时反而上升到 10 次，这就是 Belady 异常。

6. 最优置换算法（Optimal / OPT / MIN）

原理：置换未来最长时间内不会被使用的页。

例子（3 个帧）：

时刻 引用 置换 帧内容
1~3 7, 0, 1 — 7, 0, 1
4 2 7（最久之后才用） 2, 0, 1
6 3 1 2, 0, 3
8 4 0 2, 4, 3
11 0 4 2, 0, 3
16 1 3 2, 0, 1
20 7 2 7, 0, 1

结果：9 次缺页，对该例来说是最优的。

特点：

  • 缺页率最低，且不会出现 Belady 异常
  • 问题：无法预知未来的引用，因此不能真正实现
  • 用途：作为衡量其他算法性能的基准

7. 最近最少使用算法（LRU）⭐

原理：用过去近似预测未来，置换最长时间没有被使用的页。

  • 为每个页记录最后一次使用的时间
  • 可以看作"时间倒过来的 OPT"

例子（3 个帧）：结果 12 次缺页

算法 缺页次数
FIFO 15
LRU 12
OPT 9

→ LRU 比 FIFO 好，但比 OPT 差；是一种总体表现良好、被广泛使用的算法。

难点：如何实现？ 需要硬件支持，常见两种方法：

（1）计数器实现（Counter）

  • 每个页表项附带一个计数器
  • 每次通过该表项访问页时，把时钟值复制到计数器中
  • 置换时，查找计数器值最小的页
  • 缺点：需要搜索整张页表，且每次访问都要写计数器

（2）栈实现（Stack）

  • 用双向链表形式的栈保存页号
  • 页被访问时：把它移到栈顶
    • 最坏情况需修改 6 个指针
  • 栈底始终是最近最少使用的页
  • 优缺点：每次更新开销较大，但置换时无需搜索，直接取栈底

📊 图示：用栈记录最近的页访问
引用串：4 7 0 7 1 0 1 2 1 2 7 1 2

  • a 时刻之前（访问完 …1 2 后）栈从顶到底为：2, 1, 0, 7, 4
  • b 时刻访问 7 之后：7 被移到栈顶 → 7, 2, 1, 0, 4
  • 栈底的 4 就是下次要置换的 LRU 页

栈算法（Stack Algorithms）

  • LRU 和 OPT 都属于栈算法，不会出现 Belady 异常
  • 栈算法的性质：n 个帧时内存中的页集合，总是 n+1 个帧时页集合的子集，所以增加帧数不可能让缺页增加
  • FIFO 不是栈算法，因此可能出现 Belady 异常

十、LRU 近似算法及其他置换算法

1. 为什么需要 LRU 近似算法？

真正的 LRU 需要特殊硬件支持（计数器或栈），而且仍然较慢。很多系统的硬件只提供一个简单的引用位（reference bit），于是产生了各种 LRU 近似算法。

引用位（Reference Bit）

  • 每个页关联一个引用位，初始为 0
  • 页被访问时，硬件将其置为 1
  • 置换时选择任一引用位为 0 的页（如果存在）
  • 局限：只知道页有没有被用过，不知道使用的先后顺序

2. 第二次机会算法（Second-Chance / Clock）⭐

本质：FIFO + 硬件提供的引用位，也叫时钟置换算法（Clock replacement）。

页按循环队列组织，指针指向下一个候选牺牲页，检查规则：

  • 引用位 = 0 → 直接置换该页
  • 引用位 = 1 →
    • 把引用位清为 0，页留在内存（给它"第二次机会"）
    • 指针移到下一页，按同样规则检查

📊 图示：第二次机会算法

  • (a) 指针（next victim）指向一个引用位为 1 的页，其后一页也为 1，再下一页为 0
  • (b) 指针扫过的两个页引用位被清为 0，最终停在第一个引用位为 0 的页上，置换这一页

极端情况：若所有页的引用位都是 1，指针会转一整圈把全部清零，此时退化为 FIFO。

3. 增强型第二次机会算法（Enhanced Second-Chance）

同时利用引用位和修改位，组成有序对 (引用位, 修改位)，分为四类：

类别 (R, M) 含义 置换优先级
1 (0, 0) 最近未使用，也未修改 最佳置换对象
2 (0, 1) 最近未使用，但已修改 次之，置换前必须写回磁盘
3 (1, 0) 最近使用过，但干净 很可能很快再被使用
4 (1, 1) 最近使用过且已修改 很可能再用，且置换前要写回，最差
  • 仍使用时钟方式扫描，但置换最低非空类别中的页
  • 可能需要多次扫描循环队列
  • 优点：优先选择干净页，减少 I/O

4. 计数算法（Counting Algorithms）

为每个页记录被访问的次数（实际中不常用，实现代价高，且不能很好地近似 OPT）。

算法 置换哪页 依据
LFU（Least Frequently Used，最不经常使用） 计数最小的页 经常用的页计数应该大
MFU（Most Frequently Used，最经常使用） 计数最大的页 计数最小的页可能刚刚调入，还没来得及使用

💡 LFU 的问题：某页在初期被大量使用，之后不再使用，但计数一直很大而无法被置换。可通过定期将计数右移一位（指数衰减）解决。

⚠️ 讲义中 “Lease Frequently Used” 是笔误，应为 Least。

5. 页缓冲算法（Page-Buffering Algorithms）

作为置换算法的辅助手段：

  1. 始终保留一个空闲帧池
    • 缺页时直接有帧可用，不必临时寻找
    • 先把所需页读入空闲帧，再选择牺牲页并在方便时将其换出、加入空闲池
    • 好处：进程不用等牺牲页写完就能继续运行
  2. 维护一个已修改页列表
    • 当后备存储空闲时，把修改过的页写回磁盘，并将其置为干净（non-dirty）
    • 这样以后被选为牺牲页时就不需要写回
  3. 保留空闲帧原来的内容，并记录其中是哪个页
    • 若该页在帧被重用之前再次被访问，直接从池中取回，无需再从磁盘读入
    • 可以减轻选错牺牲页的代价

6. 应用程序与页面置换

  • 上述算法都是 OS 在猜测未来的页访问

  • 某些应用（如数据库）比 OS 更清楚自己的访问模式

  • 内存密集型应用可能造成

    双重缓冲（double buffering）：

    • OS 把页保留在内存中作为 I/O 缓冲
    • 应用程序也把同样的页保留在内存中供自己使用
    • → 浪费内存

  • 解决：OS 允许应用直接访问磁盘，不干预应用 → 原始磁盘模式（raw disk mode），绕过文件系统的缓冲、加锁等机制

十一、帧的分配（Allocation of Frames）

1. 最少帧数与最多帧数

  • 每个进程都需要最少数量的帧，由指令集结构决定（必须保证一条指令所涉及的所有页能同时在内存中）

  • 例：IBM 370 的

    SS MOVE

    指令最少需要

    6 个帧：

    • 指令本身 6 字节，可能跨 2 页
    • 源（from）区域可能跨 2 页
    • 目的（to）区域可能跨 2 页

  • 最多当然是系统中的全部帧数

两大类分配方案：固定分配、优先级分配，以及很多变体。

2. 固定分配（Fixed Allocation）

（1）平均分配（Equal Allocation）

  • 例：除去 OS 使用的帧后有 100 个帧、5 个进程 → 每个进程 20 个帧
  • 也可以保留一部分作为空闲帧缓冲池

（2）按比例分配（Proportional Allocation）⭐

根据进程大小分配，并随多道程序度、进程大小的变化而动态调整。

ai=siS×m
  • si ：进程 pi 的大小
  • S=∑si ：所有进程大小之和
  • m ：可用帧总数
  • ai ：分配给 pi 的帧数

例： s1=10 ， s2=127 ， S=137 ，可用帧 62 个

a1=10137×62≈4,a2=127137×62≈57

⚠️ 截图中写 m=64 ，但计算时用的是 62（教材原例为 62 个帧），以 62 为准。

3. 全局置换 vs. 局部置换 ⭐

全局置换（Global） 局部置换（Local）
选择范围 从所有帧中选择牺牲帧，一个进程可以抢占另一个进程的帧 只能从自己已分配的帧中选择
优点 吞吐量更高，因此更常用 每个进程的性能更稳定
缺点 进程执行时间可能差异很大（受其他进程影响） 内存可能利用不足

4. 页面回收（Reclaiming Pages）

一种实现全局页面置换的策略：

  • 所有内存请求都从空闲帧列表中满足
  • 不等列表降到 0 才开始置换，而是当空闲帧低于某个阈值时就触发页面置换
  • 目的：保证始终有足够的空闲内存满足新请求

📊 图示：页面回收示例
空闲内存随时间变化，设有最小阈值和最大阈值：

  • 空闲内存降到最小阈值（a、c 点）→ 内核开始回收页面
  • 回收到最大阈值（b、d 点）→ 内核暂停回收

空闲内存在两个阈值之间呈锯齿状波动。执行回收的内核例程常被称为 reaper（Linux 中是 kswapd）。

5. 非一致性内存访问（NUMA）

  • 前面假设所有内存访问速度相同

  • 许多系统是 NUMA：

    访问不同内存的速度不同

    • 系统板上含有 CPU 和内存，各板之间通过系统总线/互连相连

📊 图示：NUMA 多处理器架构
CPU0~CPU3 各自连接本地内存 memory0~memory3，CPU 之间通过 interconnect 互连。CPU 访问本地内存快，访问其他 CPU 的内存慢。

优化思路：

  • 把内存分配在线程所在 CPU 的**”附近"**
  • 修改调度器，尽量把线程调度到同一系统板上运行

Solaris 的方案：lgroups（延迟组）

  • 一种记录 CPU/内存低延迟组 的结构
  • 由调度器和调页程序共同使用
  • 尽可能将一个进程的所有线程调度在同一 lgroup 内，并在该 lgroup 中为它分配所有内存

⚠️ 讲义 “Used my schedule and pager” 是笔误，应为 used by scheduler and pager。

十二、抖动（Thrashing）⭐

1. 什么是抖动

如果进程没有"足够"的帧，缺页率会非常高：

  • 缺页 → 调入页 → 置换现有帧 → 很快又需要被置换出去的那页 → 再次缺页……

抖动：进程忙于换入换出页面，花在调页上的时间多于执行时间。

恶性循环：

  1. 大量缺页 → 进程都在等待调页设备 → CPU 利用率下降
  2. OS 发现 CPU 利用率低，误以为需要提高多道程序度
  3. 于是加入更多进程 → 每个进程分到的帧更少 → 缺页更多 → CPU 利用率更低……

📊 图示：CPU 利用率与多道程序度
随多道程序度增加，CPU 利用率先上升，达到峰值后，若继续增加进程，利用率会急剧下降 → 进入抖动区。

2. 请求分页与抖动：局部性模型

为什么请求分页有效？ → 局部性模型（Locality model）

  • 进程执行时从一个局部迁移到另一个局部（如进入一个函数，就使用该函数的代码、局部变量等）
  • 局部之间可能重叠

为什么会发生抖动？

∑局部大小>总内存大小

缓解方法：使用局部置换或优先级置换，可以限制抖动的影响（一个进程抖动不会抢走别的进程的帧），但不能根本解决问题。

📊 图示：内存访问模式中的局部性
横轴为执行时间，纵轴为内存地址（页号 18~34）。访问点集中在若干水平条带内，一段时间内只访问一小组页，然后整体迁移到另一组页，直观体现了局部性。

3. 工作集模型（Working-Set Model）⭐

  • Δ（工作集窗口）：固定数量的页访问次数，例如 10,000 条指令
  • WSSi（进程 Pi 的工作集大小）：最近 Δ 次访问中涉及的不同页的总数（随时间变化）

Δ 的选取：

Δ 结果
太小 不能包含整个局部
太大 包含多个局部
Δ = ∞ 包含整个程序

总需求帧数：

D=∑WSSi

D 是对局部性的近似。设 m 为可用帧总数：

  • 若 D > m → 抖动
  • 策略：当 D > m 时，挂起或换出某个进程，把它的帧分给其他进程；当 D 足够小于 m 时可以再启动新进程
  • 既防止抖动，又尽可能提高多道程序度

📊 图示：工作集例子（Δ = 10）
页面引用串：… 2 6 1 5 7 7 7 7 5 1 | 6 2 3 4 1 2 3 4 4 4 3 4 3 4 4 4 | 1 3 2 3 4 4 4 3 4 4 4 …

  • t₁ 时刻之前 10 次访问为 2 6 1 5 7 7 7 7 5 1 → WS(t₁) = {1, 2, 5, 6, 7}，WSS = 5
  • t₂ 时刻之前 10 次访问为 3 4 4 4 3 4 3 4 4 4 → WS(t₂) = {3, 4}，WSS = 2

说明进程从一个局部迁移到了另一个更小的局部。

十三、工作集的跟踪与缺页频率

1. 如何跟踪工作集（Keeping Track of the Working Set）

精确维护工作集代价很高，通常用定时器中断 + 引用位来近似。

例子：Δ = 10,000

  • 定时器每 5000 个时间单位中断一次
  • 内存中为每个页保留 2 个历史位
  • 每次定时器中断时：把所有页的引用位复制到历史位中，然后将引用位全部清 0
  • 缺页时检查：当前引用位和历史位中只要有一位 = 1 → 该页在工作集中

为什么不完全精确？
只能知道某页在某个 5000 单位的区间内被访问过，但无法知道是区间内的哪个时刻访问的，因此无法精确判断它是否落在最近 Δ 次访问之内。

改进：使用 10 个历史位，每 1000 个时间单位中断一次 → 精度更高，但中断处理的开销也更大。

2. 缺页频率（Page-Fault Frequency, PFF）⭐

比工作集模型更直接的防抖动方法：直接控制缺页率。

  • 设定一个"可接受"的缺页频率范围（上界和下界），并采用局部置换策略
  • 实际缺页率太低（低于下界）→ 进程帧太多，收回帧
  • 实际缺页率太高（高于上界）→ 进程帧不够，增加帧

📊 图示：缺页频率
缺页率随帧数增加而下降：

  • 高于**上界（upper bound）**的区域 → 增加帧数
  • 低于**下界（lower bound）**的区域 → 减少帧数

补充：若缺页率过高但已无空闲帧可分配，可挂起某个进程，把它的帧分给其他进程。

3. 工作集与缺页率的关系

  • 进程的工作集与其缺页率有直接关系
  • 工作集随时间变化
  • 缺页率曲线呈现峰谷交替

📊 图示：工作集与缺页率
当进程进入一个新的局部时，需要调入新工作集的页，缺页率出现峰值；工作集调入完毕后，缺页率降到很低并保持平稳；直到迁移到下一个局部，再次出现峰值。两个峰之间的区间就对应一个工作集。

十四、内核内存的分配（Allocating Kernel Memory）

内核内存与用户内存分开对待：

  • 通常从一个专门的空闲内存池中分配（不使用用户进程的分页机制）
  • 内核需要为大小各异的数据结构申请内存，很多远小于一页，要尽量减少碎片浪费
  • 部分内核内存要求物理连续，例如用于设备 I/O 的缓冲区（设备直接访问物理内存，不经过 MMU）

1. 伙伴系统（Buddy System）⭐

  • 从由物理连续页组成的固定大小段中分配内存
  • 采用 2 的幂分配器（power-of-2 allocator）：
    • 请求按 2 的幂为单位满足，请求大小向上取整到下一个 2 的幂
    • 若可用块比所需大，就把当前块一分为二，得到两个大小为下一级 2 的幂的**”伙伴"（buddies）**
    • 不断拆分，直到得到合适大小的块

例子：有 256KB 的块可用，内核请求 21KB（向上取整为 32KB）

说明
优点 可以快速合并（coalesce）：释放时相邻的伙伴若都空闲，可迅速合成更大的块（如 CL + CR → BL）
缺点 碎片：向上取整导致内部碎片，如 33KB 的请求只能用 64KB 的块，浪费近一半

2. Slab 分配器（Slab Allocator）⭐

另一种分配策略：

  • Slab：由一个或多个物理连续页组成
  • Cache（高速缓存）：由一个或多个 slab 组成
  • 每种内核数据结构对应一个独立的 cache
  • 每个 cache 中装满对象（object），即该数据结构的实例

工作方式：

  • 创建 cache 时，其中的对象都标记为空闲（free）
  • 存放结构时，对象标记为已用（used）
  • 若某 slab 中对象全部已用 → 从空 slab 中分配下一个对象
  • 若没有空 slab → 分配一个新 slab

优点：

  • 没有碎片：每个 cache 对象大小恰好等于数据结构大小
  • 分配速度快：对象预先创建好，释放后直接标记为空闲，可立即重用

📊 图示：Slab 分配
左边是两类内核对象：3KB 对象和 7KB 对象；中间各有一个对应的 cache；cache 中的对象映射到右边由物理连续页组成的 slabs 上。

Linux 中的 Slab 分配器

  • 例：进程描述符类型为 struct task_struct，大小约 1.7KB
  • 创建新任务时，从 cache 中分配一个现成的空闲 task_struct

Slab 的三种状态：

状态 含义
Full（满） 所有对象已用
Empty（空） 所有对象空闲
Partial（部分） 既有空闲也有已用

分配顺序：先用 partial slab 中的空闲对象 → 没有则从 empty slab 中取 → 都没有则新建一个空 slab

发展历程：

  • Slab 最早出现在 Solaris，现在被很多 OS 广泛用于内核态和用户态内存

  • Linux 2.2 使用

    SLAB

    ，现在同时有

    SLOB

    和

    SLUB

    ：

    • SLOB（Simple List of Blocks）：用于内存有限的系统，维护小、中、大三种对象的 3 个链表
    • SLUB：性能优化版的 SLAB，去掉了每 CPU 队列，元数据存放在 page 结构中（现为 Linux 默认）

十五、其他考虑因素（Other Considerations）

主要包括：预调页、页大小、TLB 覆盖范围、反向页表、程序结构、I/O 互锁与页锁定。

1. 预调页（Prepaging）

  • 目的：减少进程启动时出现的大量缺页（纯请求分页的问题）
  • 做法：在页被访问之前，预先调入进程将需要的全部或部分页
  • 风险：预调入的页如果没用上，就浪费了 I/O 和内存

代价分析：设预调入 s 页，其中比例 α 被实际使用

节省的缺页代价：s×αvs.浪费的预调页代价：s×(1−α)
  • α 接近 0 → 预调页不划算
  • α 接近 1 → 预调页划算

2. 页大小（Page Size）

OS 设计者有时可以选择页大小（尤其在定制 CPU 上），需要考虑的因素：

因素 倾向小页 倾向大页
碎片（内部碎片） ✓ 碎片少
页表大小 ✓ 页表小
分辨率（只调入真正需要的内容） ✓
I/O 开销（寻道/延迟占比） ✓
缺页次数 ✓ 缺页少
局部性 ✓ 更贴合局部
TLB 大小与效率 ✓
  • 页大小总是 2 的幂，通常在 2¹²（4,096 字节）到 2²²（4,194,304 字节） 之间
  • 总体趋势：页大小越来越大

3. TLB 覆盖范围（TLB Reach）

定义：通过 TLB 可以访问的内存总量

TLB Reach=TLB 大小（条目数）×页大小
  • 理想情况：每个进程的工作集都能放在 TLB 覆盖范围内，否则会有大量 TLB 未命中，需要查页表
  • 提高 TLB Reach 的方法：
    1. 增大页大小：但可能增加碎片，因为并非所有应用都需要大页
    2. 支持多种页大小：需要大页的应用可以使用大页，而不会普遍增加碎片

4. 反向页表（Inverted Page Table）

（讲义只列了标题，补充教材要点）

  • 反向页表能节省页表所占内存，但它不包含不在内存中的逻辑页的信息
  • 因此需要为每个进程额外保存一张外部页表，用于缺页时定位磁盘上的页；外部页表本身也可能被换出，导致缺页处理中再次缺页

5. 程序结构（Program Structure）⭐

程序 1：按列访问

内层循环每次访问不同的行，即不同的页 → 若进程分到的帧少于 128 个，每次访问都会缺页：
128 × 128 = 16,384 次缺页

程序 2：按行访问

先把一页（一行）全部清零，再访问下一页 → 每页只缺页一次：
128 次缺页

💡 结论：程序的访问方式与数据在内存中的存放方式一致时，局部性好、缺页少。编程语言、编译器、数据结构的选择都会影响分页性能。

6. I/O 互锁与页锁定（I/O Interlock）

  • 有时必须把页锁定在内存中
  • 例：从设备向内存中某个缓冲区读文件时，在 I/O 完成之前，这些页不能被置换算法选为牺牲页，否则设备会把数据写到已经分配给其他进程的帧里
  • 解决：钉住（pinning） 页面，即给页设置锁定位，被锁定的页不参与置换

📊 图示：磁盘驱动器正在把数据传入内存中的 buffer 区域，这部分页必须被锁住。

十六、操作系统实例（Operating System Examples）

1. Windows

  • 使用带聚集（clustering）的请求分页：缺页时，连同缺失页周围的页一起调入
  • 每个进程分配：
    • 工作集最小值：保证进程在内存中至少拥有的页数
    • 工作集最大值：进程最多可以分配到的页数
  • 当系统空闲内存低于某阈值时，执行**自动工作集修整（working set trimming）**以恢复空闲内存
  • 修整操作：从页数超过其工作集最小值的进程中移除页

2. Solaris

  • 维护一个空闲页列表，分配给发生缺页的进程
  • 三个阈值参数：
参数 含义
lotsfree 空闲内存低于此值时开始调页
desfree 低于此值时加大调页力度
minfree 低于此值时开始交换（换出整个进程）
  • 调页由 pageout 进程执行，使用改进的时钟算法扫描页
  • 扫描速率（scanrate）：在 slowscan 到 fastscan 之间变化
  • 空闲内存越少，pageout 被调用得越频繁
  • 优先级调页（priority paging）：优先保护进程代码页（不轻易置换代码页）

📊 图示：Solaris 2 页扫描器
横轴为空闲内存量，纵轴为扫描速率：

  • 空闲内存高于 lotsfree 时不扫描
  • 降到 lotsfree 时，以 slowscan（100 页/秒） 开始扫描
  • 空闲内存越少，扫描速率线性增加，接近 minfree 时达到 fastscan（8192 页/秒）

⚠️ 讲义 “threshold parameter to being swapping” 中 being 为笔误，应为 begin。

十七、补充内容

1. 请求分页的性能（复习）

讲义此处重复了"请求分页的各阶段（最坏情况）"，内容与前面第五节完全相同（陷入 OS → 保存状态 → 判断缺页 → 定位磁盘页 → 读盘 → 期间调度其他进程 → I/O 完成中断 → 修改页表 → 等待 CPU → 恢复并继续执行），此处不再重复。

2. 需要页面置换（另一版本的图示）

📊 图示：Need For Page Replacement（旧版）

  • 用户 1 的逻辑内存为 H、load M、J、M，PC 指向页 1（load M 指令），该指令要访问页 3（M），而 M 在页表中为 i，只在磁盘上
  • 用户 2 的页 B 同样为 i
  • 物理内存 8 个帧全满：monitor（操作系统）、D、H、load M、J、A、E
  • 要调入 M，却没有空闲帧 → 必须进行页面置换

与前面第八节的图意义相同，只是例子不同。

3. 优先级分配（Priority Allocation）

  • 采用按比例分配的思想，但依据优先级而不是进程大小
  • 当进程 Pi 发生缺页时，可以：
    • 从它自己的帧中选择一个置换，或
    • 从优先级更低的进程的帧中选择一个置换

4. 内存压缩（Memory Compression）

定义：不把修改过的帧换出到交换空间，而是把多个帧压缩到一个帧中，从而在不进行换页的情况下减少内存使用。是分页（换出）的一种替代方案。

例子：

压缩前：

  • 空闲帧数低于阈值，触发页面置换
  • 置换算法（如 LRU 近似算法）选中帧 15、3、35、26，先放入已修改帧列表
  • 通常做法：把这些帧写入交换空间，然后加入空闲帧列表
  • 替代做法：把其中 3 个帧（15、3、35）压缩后存入一个帧

压缩后：

  • 从空闲列表取出帧 7 存放压缩数据
  • 帧 15、3、35 被释放，加入空闲列表
  • 净效果：空闲帧从 6 个增加到 8 个，且没有任何磁盘 I/O

💡 补充：大多数移动系统（Android、iOS）不支持交换，内存压缩是其重要的内存管理手段；Windows 10 和 macOS 也支持内存压缩。压缩/解压比磁盘 I/O 快得多。

📌 本节重点总结

  1. 跟踪工作集：定时器 + 引用位 + 历史位近似；增加位数、缩短间隔可提高精度但开销增大
  2. PFF：设上、下界，缺页率过高加帧、过低减帧，比工作集更直接
  3. 工作集变化时缺页率出现峰值
  4. 伙伴系统：2 的幂分配，合并快，但有内部碎片（21KB → 32KB）
  5. Slab 分配器：每种数据结构一个 cache，无碎片、分配快；slab 有 full / empty / partial 三种状态
  6. 预调页：α 接近 1 才划算
  7. 页大小：小页碎片少、局部性好；大页页表小、缺页少、I/O 效率高
  8. TLB Reach = TLB 条目数 × 页大小，可用大页或多种页大小提高
  9. 程序结构：按行访问 128 次缺页，按列访问 16,384 次缺页
  10. I/O 互锁：I/O 缓冲页要钉住，不可置换
  11. Windows：聚集调页 + 工作集最小/最大值 + 工作集修整
  12. Solaris：lotsfree / desfree / minfree 三阈值，pageout 用改进时钟算法，扫描速率 100 ~ 8192 页/秒
  13. 内存压缩：多个脏帧压缩进一个帧，避免换出到磁盘
