哈希表与集合

11.1 映射的抽象数据类型（ADT）

映射（字典）的抽象数据类型，简单说就是定义了一组**键值对（key-value pair）**集合上的操作规范，它只告诉你“能做什么”，不关心“怎么做”。

11.1.1 核心定义

映射可看作一种特殊的集合，其中每个元素都是一对唯一键和关联值的绑定。最核心的特征是：

  • 键唯一：每个键在映射中只能出现一次
  • 键到值的单向映射：给定键，能快速找到对应的值
  • 值可重复：不同的键可以映射到相同的值

11.1.2 ADT 核心操作

操作 描述
put(key, value)、insert(key, value) 向映射中添加键值对。若键已存在，通常更新其值
get(key) 返回与键关联的值。若键不存在，可能报错或返回空
remove(key) 删除指定键及其关联值
contains(key) 检查映射中是否存在该键
size() / isEmpty() 返回键值对数量 / 判空
keys() / values() / entries() / getLength() 返回所有键、所有值或所有键值对的集合视图、或集合的长度

11.2 哈希表

11.2.1 基本概念

什么是哈希

哈希，本质是一个将任意长度的输入，通过特定算法，变换成固定长度的输出的过程。这个过程就好比给一本书配上一个唯一的国际标准书号（ISBN），无论这本书多厚，书号长度都是固定的。

这个转换函数叫哈希函数，输出的值叫哈希值。理想的哈希函数需要满足：

  • 确定性：同一个输入，无论算多少次，结果必须相同。
  • 高效性：计算速度要非常快。
  • 均匀性：不同输入得到的哈希值，应尽可能均匀分布，避免扎堆。

什么是哈希表

哈希表，也叫散列表，是一种基于哈希思想实现的高效“键 - 值对”存储结构。

它就相当于一个通过书号（ISBN）极速找书的智能书架。核心思想是，用你存储的“键”，通过哈希函数算出它对应的“值”应该存在哪个位置。它的核心思想是将键映射为数组的索引，这样查找时一步到位，理想情况下时间复杂度是惊人的 O(1)。

一个典型的存值过程：
你要存 “张三”的电话号码 138xxxx 。

  1. 哈希表用哈希函数计算“张三”的哈希值，得到一个数字。
  2. 用这个数字对底层数组的总长度取模，得到索引 3。
  3. 将这组键值对存入数组的第 3 个位置。
  4. 下次用 “张三” 查询时，通过相同的计算，就能直接去位置 3 取出号码。

11.2.2 哈希码

哈希码（Hash Code）就是一个整数。

你可以把它理解为哈希函数为一段数据（比如一个字符串、一个对象）生成的数字摘要或指纹。

  • 特点：它本身不是数据在哈希表里的最终存储位置（索引），而是生成索引的原材料。
  • 作用：它的本质是尽量用一个紧凑的数字，来代表一段可能很复杂、很大的原始数据，方便计算机后续进行高速的数学运算（比如取模）。

回到储物柜的比喻：哈希码不是“3号柜”，而是管理员看到“书包”这俩字后，脑子里蹦出的一个内部编号，比如 888。他需要基于 888 再做一步运算，才决定最终是 3 号柜。

11.2.3 哈希函数：生成和运用哈希码的规则

哈希函数（Hash Function）的范围更广，它包含了两个关键的步骤：

第一步：生成哈希码
把任意长度的输入，通过一套算法，转换成一个固定长度的整数（即哈希码）。

  • 要求：这个过程必须是确定性的，同一个输入，哪怕运行一万次，也必须生成一模一样的哈希码。
  • 例子：在Java中，每个对象都有 hashCode() 方法，它就是用来做这件事的。对于字符串 “abc”，它的 hashCode() 会永远返回 96354。

第二步：将哈希码转化为数组索引
哈希表内部是有固定大小的数组，哈希码这个整数可能非常大（比如上亿），远超数组长度。所以，需要第二步运算，把这个大范围的整数，映射到数组的有效索引范围内（比如 0 到 15）。

  • 常见方法：最直接的就是取模运算。
    index = hashcode % array_length
    这就是为什么哈希函数常被通俗地解释为“将键映射为索引的函数”，因为它最终干了这件事。

完整流程

假设你创建了一个大小为 16 的哈希表，并想存入键值对 "apple" -> 5.0。

  1. 调用哈希函数，生成哈希码
    哈希函数读取键 "apple"，根据算法（比如每个字符的ASCII值进行 31 * 前一个结果 + 当前字符值 的循环计算），得到一个整数 哈希码，假设是 96548。
  2. 转化哈希码为索引
    哈希函数继续用这个哈希码对数组长度取模：
    索引 = 96548 % 16 = 4
    最终，它返回 4。
  3. 存入哈希表
    哈希表拿到索引 4，将 "apple" 和 5.0 这个整体，存到内部数组的第 4 号槽位里。

11.2.4 哈希码、哈希函数和哈希表概念区分

核心区别：在流程中的不同角色

  • 哈希函数 (Hash Function)
    本质是规则。它是一个函数/算法，职责是接收任意长度的输入，输出一个固定长度的值。
    例如：hash("张三") 这个计算过程本身，就是哈希函数。
  • 哈希码 (Hash Code)
    本质是中间值。它是哈希函数计算后的直接产物，通常是一个整数。但它不是最终数据在内存中的存储地址。
    例如：hash("张三") 计算得出 123456，这个 123456 就是哈希码。
  • 哈希表 (Hash Table)
    本质是完整存储结构。它是一个包含底层数组、哈希函数、冲突解决策略在内的“套装”，直接用来增删改查数据。
    你可以直接对它说：map.put("张三", "138xxxx")。

协作流程：一次插入操作

当你执行 map.put("张三", "138xxxx") 时，内部会经历一个三级流转的过程：

  1. 生成哈希码
    哈希表调用哈希函数，计算Key的哈希码。
    int hashCode = hash("张三") // 得到哈希码
  2. 映射为数组索引 (压缩映射)
    哈希表拿到哈希码后，自己内部再做进一步处理，将哈希码转换为数组的具体槽位，这一步也叫压缩映射。
    int index = hashCode % array.length // 得到具体位置
  3. 存入底层数组
    哈希表将Value ("138xxxx") 存放到数组的 index 位置。如果该位置有冲突，就启动链表或红黑树等解决机制。

关键点来了：哈希函数和哈希码都不直接操作内存，只有哈希表管理真正的存储。

联系与对比总结

项目 哈希函数 哈希码 哈希表
是什么 算法 / 规则 算法输出的一个整数 基于哈希思想实现的数据结构
核心任务 把任意输入变成固定长度的输出 作为Key的”摘要”，是通往最终索引的桥梁 向使用者提供 O(1) 级别的键值存取服务
使用者 通常被哈希表或其他加密算法调用 被哈希表内部逻辑（压缩映射）使用 被软件工程师直接调用
是否有冲突 理想上希望无冲突，但实际上可能存在（碰撞） 不同对象可能有相同哈希码，这很正常 必须处理哈希码冲突导致的索引冲突

11.2.5 哈希冲突

哈希冲突，也叫哈希碰撞，可以看作是两个不同的数据，被哈希算法分到了同一个“格子”里。它是哈希表设计中无法回避、必须妥善解决的核心问题。

为什么会发生冲突？

这背后的根本原因，是两个数字上的“不对称”：

  • 无限的输入：现实世界中，可作为“键”的数据是无穷无尽的。例如，各种长度的用户名、字符串。
  • 有限的输出：无论采用哪种算法，哈希码通常都是一个固定范围的整数。在Java中，int类型的范围是-2³¹到2³¹-1。而底层数组的真实槽位数量，远比这个范围更小。

用有限的格子去映射无限的物品，冲突在数学上是必然的。这就像给全世界的人分配10个房间，无论算法多精妙，总会有人被分到同一个房间。好的哈希函数，只是让冲突尽可能均匀、尽可能少，但无法消灭它。

核心解决策略

策略一：链表法（Separate Chaining）

这是最常见、最朴素的方法。

  • 核心思想：让哈希表的每个“格子”，不再直接存单个数据，而是存一个链表（或红黑树等动态结构）的头指针。
  • 工作流程：
    • 多个数据冲突了，没关系，都挂在这个格子上的链表中。
    • 查找时，先通过哈希码找到格子，再沿着链表逐个比对**原始的“键”**本身，直到找到完全匹配的。
  • 现实应用：Java 的 HashMap 就是典型。当冲突过多、链表过长时，它还会将链表转化为红黑树，保证哪怕冲突严重，查询效率也不会退化得太难看（从 O(n) 优化到 O(log n)）。

可以理解为：一个储物柜里又加装了几个挂钩，挂所有人的包，取的时候看标签上的名字。

策略二：开放寻址法（Open Addressing）

这种方法没有链表，数据直接存在底层数组里。

  • 核心思想：当一个键算出的索引位置被占了，就按某种固定规则，去探查**“下一个”空闲的槽位**，直到找到空位并插入。
  • 探查序列：怎么找下一个？常见规则有：
    • 线性探测：index + 1，index + 2… 逐个往后找。
    • 二次探测：index + 1²，index + 2²… 减少扎堆。
  • 现实应用：ThreadLocal 的内部实现正是采用此方法。
  • 代价：删除数据时很麻烦，不能直接置空，必须设标记，否则会切断探查链，让后续数据“失联”。且当表快满时，效率会急剧下降。

11.2.6 哈希桶

哈希桶并不是一个独立的新概念，它正是链表法这种哈希冲突解决策略中，对哈希表底层数组里每一个槽位（Slot）的形象化称呼。

  • 哈希表是一组用于分类的柜子（底层数组）。
  • 这个柜子里的每一个格子，就是一个哈希桶。
  • 发生哈希冲突时，同一个桶里会像串珠子一样挂上多个数据。

为什么要叫“桶”？

如果每个格子只能存一个数据（开放寻址法），那它就是一个固定大小的“盒子”。
但如果采用链表法，这个格子的容量就变成了动态的。来一个数据就挂上去，再来一个还能挂，就像往一个桶里放东西一样，在装不下之前可以一直放。

因此，“桶”这个叫法，特指那些能够容纳多个冲突元素的容器。

哈希桶的内部结构

一个桶的内部经历了从简单到复杂的发展，主要形态有：

  1. 链表桶
    最经典的形态。每个桶是一个链表的头节点。发生冲突的元素，就依次挂在链表上。
    • 缺点：如果冲突严重，链表很长，查找会退化为 O(n)。比如存了100个冲突数据，就得遍历这100个。
    • 比喻：所有书都串在一条绳子上，找书得从头一本本翻。
  2. 红黑树桶
    这是现代哈希表（如 Java 8+ 的 HashMap）的优化态。当一个桶里的冲突元素太多，链表太长时，桶的结构会自动从“链表”切换为“红黑树”。
    • 优点：即使桶里数据很多，查找复杂度也是 O(log n)，比 O(n) 快得多。
    • 比喻：书太多了，就给这个格子单独配一个有分类索引的书架。
  3. 排序链表或二叉搜索树桶
    其他语言或库也可能使用有序链表、二叉搜索树等结构，核心思想都是让桶内查找加速。

关键状态的两种“桶”区分

  • 桶的总数 (Capacity)：
    指哈希表底层数组的长度，也就是柜子格子的总数。一个刚创建的 HashMap 默认有 16 个桶。
  • 桶内的元素数 (Bin Count)：
    指单个桶里挂了多少冲突数据。Java 中，当某个桶内元素 >= 8 个且总桶数 >= 64 时，链表就会转为红黑树，以优化性能。

简单总结，哈希桶就是哈希表解决冲突时，为每个数组槽位配备的、可动态扩容的“小仓库”。它的设计直接决定了哈希表在高冲突情况下的性能下限。

图解哈希桶的工作流

11.3 链地址法

链地址法，也叫拉链法，是处理哈希冲突最经典的方法之一。

核心思想

哈希表每个槽位不直接存单个数据，而是存一个数据结构（通常是链表）的指针。所有哈希到同一个槽位的元素，就串在同一条链表里。

工作流程

  1. 插入：对键算哈希值找到槽位，把新节点插入该槽位链表的头部或尾部。
  2. 查找：算哈希值定位槽位，然后沿着链表逐个比对键。
  3. 删除：找到槽位后，从链表中移除对应节点。

图解结构

优缺点

优点：实现简单，能容纳远超表长的元素，删除操作方便（不像开放寻址法那样有“墓碑”问题）。

缺点：需要额外指针存储开销，当链表过长时查找会退化成 O(n)。

11.3.1 链式哈希表

链式哈希表就是使用了链地址法来解决哈希冲突的哈希表。

这几乎就是同一个概念从不同角度的两种叫法：

  • 链地址法 侧重于描述解决冲突的“方法”。
  • 链式哈希表 侧重于描述使用了这种方法的“数据结构”。

两种哈希表实现对比

特性 链式哈希表 (Chaining Hash Table) 开放寻址哈希表 (Open Addressing Hash Table)
冲突解决法 链地址法 开放寻址法 (如线性探测)
数据结构 数组 + 链表（或红黑树） 仅用数组
元素存储位置 冲突的元素存在同一个槽位的链表中 冲突的元素存在数组的其他空闲槽位中
负载因子 可以大于1，元素总数可超过数组长度 必须严格小于1，数组长度决定容量上限

链式哈希表（用链地址法）

开放寻址哈希表（用线性探测）

11.4 线性探测

线性探测是一种开放寻址法的冲突解决策略，主要用于哈希表。

当你想存入一个键值对时，如果它的理想位置已被占用，线性探测就会按固定步长（通常是1）依次检查下一个位置，直到找到空位。

11.4.1 线性探测基本过程

  1. 对键 key 计算哈希值，找到初始索引 i = hash(key)
  2. 如果 table[i] 为空，就插入这里
  3. 如果已被占用，就检查 i+1，接着 i+2…… 直到找到空位
  4. 查找时同理，从 i 开始逐个比较，直到找到相同的键或遇到空位

示例

假设表大小为10，哈希函数是 key % 10。

  • 插入 15（15%10=5，位置5空）→ 直接存入位置5
  • 插入 25（25%10=5，位置5已被15占用）→ 检查位置6
    • 位置6空 → 存入位置6
  • 插入 35（35%10=5）→ 位置5、6都已被占，位置7空 → 存入位置7

查找25时，也会从位置5开始，发现是15，就继续检查位置6，找到25。

主要缺点

  • 主聚集现象：连续的占用位置会越来越长，形成“聚集区”。新元素一旦落到聚集区边缘，就会加入其中，使聚集区进一步扩大，严重拖慢查找和插入速度。
  • 删除操作不能简单置空，否则会切断探测链，导致后续查找失败。通常需要用“懒惰删除”标记来解决。

11.4.2 哈希表的线性探测

用空桶（Empty）作为“未占用”标记的线性探测实现，这是最基础、最直观的一种。

插入

插入的核心是一条带终止条件的线性搜索。

假设哈希表 table 是一个数组，每个槽有三种状态：

  • Empty（空）
  • Active（已占用）
  • Deleted（已删除，后面会讲）

  • 遇到 Empty 就停止，因为插入时遇到 Empty 也会停，所以键不可能在更后面。
  • 遇到 Deleted 不能停，必须继续探测，因为当时它被插入时这里可能还是 Active，后来才被删掉。

移除

如果直接将一个槽设为 Empty，会把探测链断开，导致后续搜索提前终止、找不到本来存在的键。

示例
假设表大小为5，依次插入 key1→桶0，key2→桶1，key3→桶1（冲突后放桶2）。
此时桶数组：[key1, key2, key3, Empty, Empty]

删除 key2 时，若把桶1直接变成 Empty：
[ key1, Empty, key3, Empty, Empty ]

现在搜索 key3，hash(key3)=1，桶1是 Empty，搜索直接停止返回“未找到”，但 key3 实际在桶2——探测链断了。

正确做法：懒惰删除
删除 key2 后，桶1标记为 Deleted：
[ key1, Deleted, key3, Empty, Empty ]

此时：

  • 搜索 key3：从桶1开始，遇到 Deleted 继续走，最终在桶2找到。
  • 插入新键：可以把 Deleted 槽当成空位来存放新键，节省空间。

11.4.3 空桶实现的局限与负载因子

这种基础的空桶实现只区分 Empty 和 Active 时，无法正确处理删除（必须引入 Deleted）。

即便引入 Deleted 解决删除问题，性能也会随负载因子升高而急剧恶化（主聚集效应）。实际工程中通常会：

  • 控制负载因子（已用槽数/表大小）不超过 0.5–0.7，超过就扩容并重新哈希。
  • 定期在负载较低时重整哈希表，清除 Deleted 标记的槽。

11.5 二次探测

二次探测是一种用于哈希表冲突解决的开放寻址法。

当你想插入一个元素，但它的哈希地址已被占用时，二次探测不是去尝试下一个紧邻的位置，而是将冲突次数平方后作为偏移量，按二次函数的序列去寻找下一个空位。

核心思想

当插入一个键发生哈希冲突（目标位置已被占用）时，二次探测不是简单地去下一个位置，而是按二次函数步长去寻找新的空位。

探测序列是：

  • 第1次冲突：找 原位置 + 1²
  • 第2次冲突：找 原位置 + 2²
  • 第3次冲突：找 原位置 + 3²
    ……
    以此类推。

举例说明

假设哈希表大小 m = 10，键 k 的初始哈希值 hash(k) = 4。

  • 插入时，位置 4 被占。
  • 第1次探测（i=1）：检查 (4 + 1²) % 10 = 5
  • 若还冲突，第2次探测（i=2）：(4 + 2²) % 10 = 8
  • 第3次（i=3）：(4 + 9) % 10 = 3
  • 第4次（i=4）：(4 + 16) % 10 = 0

发现了吗？步长（1, 4, 9, 16…）在快速增大。这让它能跳开线性探测中相邻聚集的区块。

二次探测意义

核心是为了解决线性探测的主要聚集问题。

  • 线性探测：步长固定为1，产生连续冲突链（主要聚集），性能下降快。
  • 二次探测：跳跃式查找，能缓解聚集，但也会出现“如果初始位置相同，则整个探测序列完全相同”的二次聚集。

关键注意事项

使用二次探测时有几个致命限制：

  • 表长必须是质数，且负载因子必须小于 0.5
    这是严格的理论要求。如果没有这个保证，二次探测可能永远找不到空位，陷入死循环，导致插入失败。
  • 无法直接删除
    和线性探测一样，简单删一个元素会打断探测链，导致后续查找误以为元素不存在。通常用“惰性删除”（打删除标记）替代。

优缺点

  • 优点：避免了线性探测那种严重的“连续拥挤”，缓存性能尚可。
  • 缺点：对表大小限制严格；存在二次聚集；查找时缓存命中率不如线性探测。

11.6 双重哈希

双重哈希（Double Hashing）是开放定址法中用于解决哈希冲突的一种方法。它通过使用两个不同的哈希函数来计算探查序列，从而更均匀地将冲突元素分散到哈希表中。

它的基本思想是：当插入时发现目标位置已被占用，不简单地使用线性探查（逐个找下一个），也不使用二次探查，而是使用第二个哈希函数来计算每次探查的“步长”。

双重哈希虽然分布均匀，但计算成本略高于线性探查，且对哈希函数的设计要求更高。

工作原理

假设哈希表大小为 mm。

  1. 两个哈希函数

    • h1(key)h1(k**ey)：计算初始探查位置。
    • h2(key)h2(k**ey)：计算冲突后的探查步长。这个值绝不能为0，且通常与表的大小 mm 互质，以保证探查序列能覆盖整个表。

  2. 探查序列
    插入或查找时，第 ii 次探查的位置计算公式为：

    h(key,i)=(h1(key)+i×h2(key)) mod mh(k**ey,i)=(h1(k**ey)+i×h2(k**ey))modm

    其中 ii 从 0 开始。

一个具体的例子

假设表大小 m=7m=7，哈希函数为：

  • h1(key)=key mod 7h1(k**ey)=k**eymod7
  • h2(key)=5−(key mod 5)h2(k**ey)=5−(k**eymod5) （一个常用的步长函数）

现在要插入键 1515 和 2222：

  1. 插入 key = 15
    • h1(15)=15 mod 7=1h1(15)=15mod7=1，位置1为空，直接放入。
    • 哈希表：[空, 15, 空, 空, 空, 空, 空]
  2. 插入 key = 22
    • h1(22)=22 mod 7=1h1(22)=22mod7=1，位置1已被15占用，产生冲突。
    • h2(22)=5−(22 mod 5)=5−2=3h2(22)=5−(22mod5)=5−2=3
    • 第一次探查（i=1i=1）：位置 (1+1×3) mod 7=4(1+1×3)mod7=4，为空，放入。
    • 哈希表：[空, 15, 空, 空, 22, 空, 空]

如果位置4也被占，就会继续以步长3探查下一个位置：(1+2*3) % 7 = 0，依此类推。

关键优势

  • 减少聚集：线性探查会造成“基本聚集”，二次探查会造成“二次聚集”。双重哈希产生的探查序列动态且与键本身相关，分布更均匀，能最有效地减少聚集。
  • 性能更稳定：在高负载因子下，它的查找性能通常优于其他开放定址法。

关键要求

  • *h2(key)*h*2(*k*ey*) 的值绝不能为0。
  • 为让探查序列覆盖全表，h2(key)h2(k**ey) 应与表大小 mm 互质。常通过让表长 mm 为质数，并限制 h2(key)h2(k**ey) 总是小于 mm 来实现。
  • 无法简单支持删除（这是所有开放定址法的通病），删除操作通常需要惰性删除标记。如需频繁删除，链地址法可能是更好的选择。

11.7 调整哈希表大小

在数据结构中，调整哈希表大小是指当哈希表中存储的元素数量变化到一定程度时，重新创建一个更大（或更小）的数组，然后将所有旧元素重新映射并迁移到新数组中的过程。

这是哈希表维持高效性能的核心机制。

11.7.1 为什么要调整大小

哈希表的查找、插入、删除操作，理想情况下时间复杂度是 O(1)。但这依赖于一个关键指标：负载因子。

  • 负载因子 = 元素数量 / 数组容量
  • 当负载因子过高（比如 > 0.75），哈希冲突会急剧增加，链表或红黑树变长，操作退化为 O(n)。
  • 当负载因子过低（比如 < 0.1），虽然冲突少，但大量数组空间被浪费。

因此，需要调整大小来将负载因子维持在一个合理区间，在时间和空间上取得平衡。

11.7.2 触发条件

不同实现策略不同，常见的有两种：

  • 扩容：当负载因子 大于等于 某个阈值（如 Java HashMap 默认 0.75）时，将容量扩大为原来的约两倍。

  • 缩容：当负载因子 小于 某个阈值时，将容量缩小，以节省内存。不过在并发场景下，为避免频繁扩缩容带来的性能抖动，并非所有哈希表都会自动缩容。

为什么不像数组一样原地扩容？

这是最核心的问题：哈希函数与数组大小强相关。

最常用的哈希映射是：index = hash(key) % capacity

一旦 capacity 变了，同一个 key 计算出的新下标几乎必然会变。所以不能简单地在末尾追加空间，必须为每个已存在的键值对在新数组中重新计算位置。这个过程通常称为 rehashing（重新哈希）。

11.7.3 重新哈希的过程

整个过程大致分四步：

  1. 分配新空间：创建一个容量更大的新数组。
  2. 遍历旧数组：依次取出每个桶中的元素。
  3. 重新计算并插入：对每个键，用 hash(key) % new_capacity 算出在新数组的下标，放入对应的桶中。
  4. 替换引用：将哈希表内部的数组指针指向新数组，释放旧数组。

注意：这是一个开销很大的 O(n) 操作。为了避免单次插入触发长时间卡顿，Redis 等系统采用渐进式 rehash，将重映射工作分摊到后续的每次操作中，直到全部迁移完成。

示例演示

假设一个简单的哈希表，用 key % capacity 映射，当前容量为 4：

下标 键 (key) 计算过程
0 4 4 % 4 = 0
1 1 1 % 4 = 1
2 2, 6 2 % 4 = 2，6 % 4 = 2 （冲突）
3 3 3 % 4 = 3

此时元素数量为 5，容量为 4，负载因子 = 1.25，需要扩容。

扩容到容量为 8 后，重新计算：

新下标 键 (key) 计算过程
0 -
1 1 1 % 8 = 1
2 2 2 % 8 = 2
3 3 3 % 8 = 3
4 4 4 % 8 = 4
5 -
6 6 6 % 8 = 6
7 -

可以看到，原本冲突的 2 和 6 被分散到了下标 2 和 6，哈希表恢复了高效。

11.7.4 实际实现中的优化技巧

  • 容量取 2 的幂：当容量为 2 的幂（如 16, 32）时，取模运算 hash % capacity 可以用位运算 hash & (capacity - 1) 替代，大大加快 rehash 速度。
  • 懒惰迁移：如前面提到的，Redis 的字典在扩容后会同时保留新旧两个哈希表，每次查找先在老表找，找不到再去新表。每次操作顺手将一部分数据从老表迁移到新表，把一次性的大开销均摊了。
  • 一次性扩容：像 Java 的 HashMap 在非并发场景下，就是在 resize() 方法里一次性完成所有迁移，逻辑上更简单。

总的来说，调整哈希表大小就是通过以空间换时间或回收空间的手段，配合重新哈希，来保证操作的高效性。这个过程也是很多集合类在面试和实际优化中的重点。

11.8 常用哈希函数

数据结构中常用的哈希函数主要分为几大类，它们的核心目标是将任意长度的键映射为固定长度的地址，且尽可能均匀分布以减少冲突。

11.8.1 直接定址法

取关键字或关键字的某个线性函数值作为哈希地址。

H(key)=key 或 H(key)=a×key+bH(key)=key或H(key)=a×key+b

  • 优点：简单、均匀，永远不会产生冲突。
  • 缺点：仅适用于关键字基本连续且范围不大的情况。
  • 场景：统计学生成绩（0-100分），或人口年龄统计。

11.8.2 数字分析法

如果关键字是位数较多的数字（如手机号），且若干位分布较均匀，就抽取这几位组合成地址。

例：手机号 138xxxx1234→ 取中间4位例：手机号 138xxxx1234→ 取中间4位

  • 优点：适合处理已知模式的大规模静态数据。
  • 缺点：依赖于关键字的分布特征，更换数据集需重新分析。
  • 场景：手机号、身份证号等作为键时。

11.8.3 平方取中法

先计算关键字的平方，然后取中间几位作为地址。

key=1234⇒12342=1522756⇒取中间 227key=1234⇒12342=1522756⇒取中间 227

  • 优点：得到的地址与关键字每一位都相关，分布较随机。
  • 缺点：计算量稍大。
  • 场景：关键字分布未知或位数不是很大时。

11.8.4 折叠法

将关键字分割为位数相等的几段（最后一段可短些），然后叠加求和。

  • 移位叠加：直接对齐相加。

  • 边界折叠：相邻段反转后再相加。

    key=9876543210⇒987+654+321+0=1962key=9876543210⇒987+654+321+0=1962

  • 优点：适合关键字位数特别多的情况。

  • 场景：老旧系统的注册码、长数字编号。

11.8.5 除留余数法（最常用）

这是最经典、最简单的方法，也是构建多种哈希表的基础。

H(key)=key mod p(p≤m)H(key)=keymodp(p≤m)

  • 关键：模数 pp 的选择直接影响冲突概率。一般取不大于表长 m*m* 的质数，或不包含小于20的质因数的合数。
  • 场景：几乎所有语言的字典或哈希表底层，例如 Java HashMap 的寻址基础思想。

11.9 直接哈希(Direct hashing)

在数据结构中，直接哈希是一种最理想化、最简单的哈希方法，你可以把它理解为**“完美的一对一映射”**。

它的核心思想非常直接：

键（Key）本身就直接作为数组的下标（Index），不需要经过任何复杂的哈希函数计算。

具体来说，它必须满足以下条件：

  • 键必须是整数，或者是能轻易映射成唯一整数的数据。
  • 键的取值范围是已知的、有限的，并且足够小，这样我们才能预先分配一个能容纳所有可能键的数组。

工作流程很简单：
假设有一个数组 arr，对于任意一个键 k，它的存储位置就是 arr[k]。插入、删除和查找的操作，就是直接访问数组的第 k 个位置，时间复杂度瞬间达到 O(1)，且绝对没有冲突，因为每个键都有自己专属的位置。

一个直观的例子

比如，我们要存储一所小学里，某个班级学生的考试成绩。已知这个班的学号是从 1 到 50 的连续整数。

我们可以直接创建一个长度为 51 的数组 scores（浪费掉索引0）。若学号为 25 的学生考了 98 分，就直接 scores[25] = 98。查找学号为 18 的学生成绩时，只需读取 scores[18] 即可。

直接哈希的致命缺陷

既然它这么快又没有冲突，为什么不是所有地方都用呢？因为它的限制条件在现实中太苛刻了：

  • 空间浪费惊人
    如果键的取值范围非常大，但实际存储的数据很少，就会造成巨大的空间浪费。例如，用一个 18 位身份证号直接做索引，想想这个数组得有多大。
  • 键必须是非负整数
    像姓名、字符串这类键无法直接使用，需要先转换成整数。

与其他方法的对比

实际上，正是因为以上限制，“直接哈希”更多是哈希技术的一个理想化模型。我们日常讨论的 “哈希表”，通常指的是其改进版：

  • 直接哈希：位置 = 键。键与地址是一对一的。
  • 哈希表：位置 = 哈希函数(键)。使用一个哈希函数将大范围、非整数的键，压缩映射到一个较小的地址空间内。但正因如此，就引入了哈希冲突，需要用链地址法或开放寻址法来解决。

11.10 哈希算法：密码学、密码哈希

哈希算法，简单说，就是把任意长度的数据，压缩成一段固定长度的、看似随机的“数字指纹”。

11.10.1 密码学哈希函数

这是哈希算法中安全等级最高的一类，主要不是为了快，而是为了“安全”。它必须具备以下四大核心特性，只要一个不满足，就不再安全：

  • 单向性（不可逆）
    从哈希值几乎无法反向推导出原始数据。就像看到一杯果汁，你无法还原出榨汁前水果的样子。
  • 抗碰撞性（唯一性）
    在现实中，找不到两个不同的输入 XX 和 YY，能产生相同的哈希值 H(X)=H(Y)H(X)=H(Y)。这保证了文件或数据的唯一身份。
  • 雪崩效应
    输入的任何微小改动，都会让输出结果面目全非。比如 “hello” 和 “hello!” 的 MD5 值天差地别：
    • hello → 5d41402abc4b2a76b9719d911017c592
    • hello! → 2490f7c74930feecb49b083a4d1f66a5
  • 确定性
    同样的输入，无论何时何地计算，输出永远严格一致。这是数据校验的基础。

主要应用场景：

  • 完整性校验：下载操作系统镜像时，用于验证是否被篡改。
  • 数字签名：签名前，先对文件生成摘要，实际签名的是这个摘要，效率更高。
  • Git 版本控制：用 SHA-1（现正迁移至更安全的 SHA-256）来唯一标识每个提交。

代表性算法：

  • MD5：已破解，严禁用于安全领域。
  • SHA-1：已被成功构造碰撞攻击，正被淘汰。
  • SHA-2 家族 (SHA-256/SHA-512)：当前主流，安全可靠。
  • SHA-3 家族：新一代标准，结构先进，作为后备。

11.10.2 密码哈希

这是密码学哈希在口令保护上的特定应用，专为存放用户密码设计。除了具备上述特性，还增加了针对黑客攻击的额外防护：

  • 加盐 (Salt)
    为每个用户生成一个独一无二的随机字符串（盐），拼接到密码上再计算哈希。它能有效抵御彩虹表（预计算的密码哈希字典）攻击，并让使用相同密码的用户，最终存储的哈希值也完全不同。
  • 拉伸与成本因子 (Stretching & Cost Factor)
    通过成千上万次的迭代计算，或要求占用大量内存，故意拖慢哈希运算的速度。用户的正常登录感受不到延迟，却能极大增加黑客暴力破解的成本。

特别注意： 像 SHA-256 这类通用哈希算法计算太快，不适合直接用来存密码。应该使用专门的“慢哈希”算法。

主流算法（由强到弱）：

  • Argon2：2015年密码哈希竞赛冠军，当前最强者。可以分别调节占用CPU和内存的大小，能有效对抗专业硬件（如GPU/ASIC）的破解。
  • bcrypt：经典稳健，默认自带盐和可调成本因子，依然是很好的选择。
  • scrypt：设计上极其消耗内存，同样能有效对抗硬件破解。
  • PBKDF2：老牌标准，可调节迭代次数，但相对容易被专业硬件计算，强度不如前三者。

对比总结

特性 密码学哈希函数 (如 SHA-256) 密码哈希算法 (如 Argon2)
核心目标 快速生成代表数据的唯一“指纹” 安全地储存用户凭证
关键需求 抗碰撞、确保数据完整性 单向性、故意减缓速度、抵御暴力破解
速度 极快，追求高性能 故意很慢，且能随硬件进步调高成本
加盐 不需要 必须加盐，盐通常与哈希值存储在一起
典型应用 文件校验、数字签名、Git 网站/应用的用户登录口令存储

总的来说，密码学哈希函数关注的是数据的不可篡改性，属于一次性快照；而密码哈希关注的是秘密的安全存放，是一个持续对抗破解的过程。两者虽然技术同源，但设计哲学完全不同，用途务必区分清楚。

11.11 集合的抽象数据类型（ADT）

在数据结构中，集合的抽象数据类型是一个纯粹的数学模型，它定义了数据之间的逻辑关系以及可以执行的操作，但完全不涉及这些操作在内存中如何具体实现。

简单说，它只回答“集合能做什么”，不回答“怎么做”。

11.11.1 定义与核心思想

集合的数学基础是集合论，它有两大核心特征：

  • 无序性：元素之间没有先后顺序。{1, 2, 3} 和 {3, 1, 2} 是同一个集合。
  • 互异性：集合中不允许出现重复元素，每个元素都是唯一的。

符合这两个特征的有限无序集，就是集合ADT要描述的数据对象。

11.11.2 核心操作

一个典型的集合ADT通常包含以下基本操作：

操作 功能描述
创建与销毁 Create() 建立一个空集合；Destroy() 销毁并释放资源。
基础修改 Add(S, x) 添加元素；Remove(S, x) 删除元素。
查询 Contains(S, x) 判断元素是否存在；Size(S) 返回元素个数；IsEmpty(S) 判断是否为空。
集合特有运算 Union(A, B) 求并集；Intersection(A, B) 求交集；Difference(A, B) 求差集；IsSubset(A, B) 判断A是否为B的子集。

为什么叫ADT？

关键在于，这套接口可以用多种底层技术实现，但接口本身保持稳定。

  • 可以用数组实现
    比如用位向量表示一个固定范围（如1-10）的集合，判断元素是否存在速度极快 O(1)。但空间效率差，不适合元素范围巨大或稀疏的情况。
  • 可以用链表实现
    添加删除灵活，不浪费空间。但判断元素是否存在需要遍历链表，时间复杂度为 O(n)，效率较低。
  • 理想实现：哈希表和平衡树
    • 哈希表：平均情况下，Add、Remove、Contains 操作都非常快，接近 O(1)，是大多数场景下的首选。
    • 平衡二叉搜索树（如红黑树）：所有操作的时间复杂度稳定在 O(log n)，并且能方便地进行有序遍历、查找最大最小值，更适合需要有序性的集合。

11.11.3 集合的数学基础

集合的数学基础主要来自集合论。在数据结构中，几乎你提到的所有概念，都能在数学定义里找到源头。

一、基本概念与定义

数学里的集合，是由一些确定的、彼此不同的对象构成的整体。这直接决定了数据结构“集合”的两个核心特性：

  • 确定性：对任意元素，它要么属于集合，要么不属于，边界分明。
  • 互异性：集合中不能有重复元素，每个元素只出现一次。数据结构中的集合也强制执行这个规则。

关于元素与集合、集合与集合，有三组基本关系：

  • 属于（∈∈）：表达元素和集合的关系。比如 1∈{1,2,3}1∈{1,2,3}。
  • 相等：两个集合包含的元素完全一样就是相等，和顺序无关。所以 {1,2,3} 和 {3,1,2} 是同一个集合。
  • 子集（⊆⊆）：若A的所有元素都属于B，A就是B的子集，A⊆BA⊆B。真子集（⊂⊂）则要求B中至少有一个元素不属于A。

二、核心运算

数据结构中集合ADT的经典操作，直接对应数学集合的三种基本运算：

  • 并集 (A∪BA∪B)
    由A和B中所有元素合并而成。比如 {1,2} ∪ {2,3} 结果是 {1,2,3}。
  • 交集 (A∩BA∩B)
    由A和B的公共元素组成。 {1,2} ∩ {2,3} 结果是 {2}。如果没公共元素，交集就是空集 ∅∅。
  • 差集 (A−BA−B)
    由属于A但不属于B的元素组成。{1,2} - {2,3} 结果是 {1}。

三、从数学到数据结构的关键映射

数学集合是无序的，但在计算机中，为了管理数据，需要为元素定义“序”来构建高效结构。根据元素间能否比较大小，数据结构中的集合实现分化为两类：

  • 有序集合：数学基础是全序关系。任意两个元素都能比较大小。这类结构（如红黑树、跳表）通常按中序遍历就是有序序列，支持高效的查找和范围查询。
  • 无序集合：数学基础是等价关系。只关心两个元素是否“相同”（哈希值相等），不关心大小。典型实现就是哈希表，查找效率极高但不支持顺序操作。
